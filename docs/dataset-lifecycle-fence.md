# 数据集退役与报告提交围栏

该前置供 #1015 的确认服务及 #1016 的台绑定提案复用。涵盖台库结构升级、存储级退役与恢复、现有报告绑定和首次发布。退役管理页面、短期预检票签发和报告治理提案按各自规格接入。 [退役设计](https://github.com/NelsonLongxiang/workbench-market/issues/1015#issuecomment-7136971268) · [接入顺序](report-governance-capability.md#六实现顺序方案-a)

## 数据集身份和事务

- `datasetFence(name)` 返回名称、不可复用的数据集 ID、库的恢复代次、数据集修订、状态以及视图和绑定修订。调用方在判权限后使用，终端不需要传数据库路径。列定义、数据写入及快照恢复推进数据集修订。保存、回滚视图和报告绑定切换各自推进修订，即使表面版本回到旧值也不能复用旧确认。
- `datasetLifecycle(input, mainFence)` 只供有权限的服务调用。调用方负责在拿到主库围栏后认人、核验专用权限和确认凭据。台库事务重新核对主库变更号、台登记、数据集身份及数据和引用修订。退役保留数据表、名称和容量，恢复用同一个对象。普通读写和同名定义都不能打开退役对象。公共区和当前视图或报告仍引用的对象拒绝退役。冻结报告照原规则可读。
- 同一代次中，操作号首次提交时将确认上下文摘要、理由和历史回执落在同一台库事务。调用方仍需按现况认人、判权，再尝试重放。同号同上下文回历史回执，当前状态由 `datasetFence` 另查。不同人、不同内容、不同代次不能复用。此表当前无自动清理。审计只留控制信息和摘要。

## 绑定、停用和首次发布

- `reportBindingContext(slots)` 冻结当前视图版本和切换修订、恢复代次、每个槽对应数据集的身份及修订。随后用 `reportBindingPut` 提交时传 `context`、绑定 `base` 和主库围栏。槽中的表和视图由存储层重新解析。旧上下文不会生效。
- `POST /api/bench-views/:bench/reports/:dimension/binding/stop` 只认站内同源、当前启用且覆盖全局 `bench-store.report-bind-stop` 决定动作的自然人。请求体为 `{base, reason}`。即使维度或模板已撤，也能停用登记中的最新绑定。写入带原因的新版本，旧绑定和冻结报告保留。保存或回滚视图如改变仍在用的报告槽来源，须先改绑或停用。
- `reportSlots` 取数并给出 `context`。首次 `reportInsert` 在写事务中复核该上下文、当前绑定版本、停用状态和调用方判权时的主库围栏。并发操作先完成哪次提交，就以该顺序判定。拒绝后须重新取数。读取成品不会再取源数据。

## SQLite 及备份恢复

1. 在有主库授权的提交中，调用方先通过 `captureBenchStorageFence()` 取当前状态变更号及最近授予到期时间，再认人、判权和解析对象。工作线程附着主库后使用 SQLite `BEGIN IMMEDIATE`，持两库写锁，主库只读，只有台库落写。主库权限、归属、台登记等状态发生任何变更后，旧判定一律冲突。提交不需要跨库写的原子保证。调用方不应持自己的主库写事务等待工作线程。SQLite 正在处理业务，PostgreSQL 连接、等价围栏及验收随换库交付。
2. v1 台库在单个写事务中升为 v2。旧目录变为协议守卫视图，旧句柄在查询旧目录、改现行视图或首次插报告与绑定时失败。退役还会在同一个事务内停放物理表，原表、列和行完整保留。混合版本期间先排空已开始读取或已经开始回传的旧请求，再开放上层确认。已开始的响应无法撤回。
3. 存储层用登记身份区分同名台，用随机代次区分从同一备份恢复两次。原库或已建立受围栏提交的备份可以通过 `stageBenchRecovery(source, destination, {slug, identity}, kit)` 生成新代次暂存库。临时文件在目标旁，完整性和身份匹配后独占发布到新路径。运维发布前必须关闭所有访问该台库的进程并核对主库登记身份，带入正确的备份和新代次。旧句柄发现路径的文件已替换会拒绝请求。备份源和在用文件均由独立步骤保管。主库登记身份缺失的旧备份须另做迁移，不能自行与同名台绑定。
