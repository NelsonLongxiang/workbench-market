由此本稿的前提：

- 写入全由 AI 经现有 MCP 工具完成（`dataset_define`、`dataset_upsert`、`dataset_replace`、`dataset_delete_rows`、`view_put`），人只看。
- 所以第 1 步的任务图**只读**：不做拖拽节点、画布连线、画布上改状态。
- 不新增 MCP 工具、路由、动作或权限：任务就是台里的一个数据集，图是视图里的一种组件。

## 三、数据怎么存

任务存成台里一个普通数据集，一行一个节点。不另建「边」的表：依赖写在节点自己那一行。

| 列（名字由视图描述指定） | 类型 | 用途 |
|---|---|---|
| 编号 | text 或 integer，数据集主键 | 节点 id |
| 名称 | text | 节点上的字 |
| 依赖 | text | 前置节点编号，逗号分隔；空 = 没有前置 |
| 角色 | text（`dag`、`flow` 必须指定这一列；每行可空） | `start`＝起点，`end`＝主线终点，`branch_end`＝支线终点，其余留空。AI 随时 upsert 改写哪个节点是起点、终点（D5、D6） |
| 状态 | text | 如 `todo`、`doing`、`blocked`、`done`、`failed`；说法和颜色照现有 `value_labels` 写法配 |
| 进度 | integer 或 decimal（可选） | 0～100 |
| 负责人、分组、开始、截止等 | 任意（可选） | 节点详情里显示；分组可按泳道排 |

为什么依赖放在同一行：AI 一次 `dataset_upsert` 就能同时改节点和它的依赖，不会出现「节点写了、边没写」的半截状态；也不用两次查询拼图。代价是依赖列的取值要在渲染时解析、核对（见第五节）。

**数据来源（D3）**：ygl-trees 的科技树、A2A 工单、PR 等只是 AI 采集的来源。市场不新增到 ygl-trees 的读取路径、不跨系统取数；AI 采集后经 MCP 写进台的数据集，节点可以在详情列里留来源（如科技树节点键、工单号、链接），链接照现有 `records` 的规矩只认 http(s)。

三种图共用这一张表，各取所需的列：甘特图另要 **开始**、**截止**（date 或 datetime）两列；流程图另可给 **形状** 列（`step`、`decision`；起点、终点由角色列定），依赖列的一项可写成 `编号=说法`，作为这条边上的字（如判断分支的「是」「否」）。

进度随时间的变化（「跟踪」）不需要新组件：AI 每次推进时往另一个数据集 `dataset_append` 一条（时间、完成数、总数），用现有的 line、progress、stat 组件画。本稿第六节给出一个完整视图示例。

## 四、新组件 `dag` 的契约

`BLOCK_TYPES` 加 `dag`；`BLOCK_CONTRACT.dag`：

| 键 | 必填 | 说明 |
|---|---|---|
| `type`、`title`、`span` | type 必填 | 同其它组件 |
| `query` | 是 | 查任务数据集（明细查询，不能有 group、measures） |
| `id_col` | 是 | 节点编号列 |
| `label_col` | 是 | 节点名称列 |
| `deps_col` | 是 | 依赖列（text） |
| `role_col` | 是 | 角色列（text）：`start`、`end`、`branch_end`（D5、D6） |
| `status_col` | 否 | 状态列；配 `value_labels` 给说法和色调（success / warning / danger / default，台不能自定颜色） |
| `progress_col` | 否 | 进度列（数值列） |
| `group_col` | 否 | 分组列；给了就按组分泳道 |
| `detail_cols` | 否 | 点开节点时显示的列，1～12 个 |
| `direction` | 否 | `LR`（缺省，从左到右）或 `TB`（从上到下） |
| `value_labels`、`column_labels` | 否 | 同 table |

保存视图时（`view_put` 与页面保存同一处校验）核：列都存在；`deps_col` 是文本列；`progress_col` 是数值列；查询是明细查询。这些都跟着 `BLOCK_CONTRACT` 自动进 `view_put` 的工具说明，AI 读工具说明就知道怎么写。

## 四之二、`gantt` 与 `flow` 的契约

**`gantt`（甘特图）**：键 `type`、`title`、`span`、`query`、`id_col`、`label_col`、`start_col`、`end_col`（必填）；`deps_col`、`status_col`、`progress_col`、`group_col`、`detail_cols`、`value_labels`、`column_labels`（可选）。每个任务一条横条，从开始到截止；进度画成条内填充；给了依赖就画箭头（前置的截止 → 后继的开始）；有一条「今天」竖线；截止已过、没完成的条用 danger 色调。开始、截止是必填（D5）：视图保存时核数据集里这两列已设成必填（列定义 `required: true`），写入时为空就被拒（server/src/services/bench-store-core.ts:306），图上不会有缺日期的条；日期随时可以改写。`role_col` 可选：给了就在主线终点、支线终点的条尾画终点标记。

**`flow`（流程图）**：键同 `dag`，另加 `shape_col`（可选）。和 `dag` 只有两点不同：允许回边（循环，如「审核不过 → 退回修改」），回边画成弯线、不报环；节点按形状画（开始、结束圆角，判断菱形，步骤矩形），边上可以有字。布局照 `dag`，先去掉回边再分层。

三种组件的保存校验同 `dag`：列都存在、类型对（开始、截止要是日期或时间列）、查询是明细查询。

## 五、渲染

1. **解析**：依赖列按逗号切开、去空白、去重；指向自己的忽略。
2. **核对（渲染期，因为数据随时被 AI 改）**：
   - **有环**：整个组件显示「依赖有环：A → B → A」，列出一条环，不画图、不悄悄丢边；
   - **依赖指向不存在的编号**：画虚线短边到一个灰色「缺失：X」占位节点，并在组件顶上提示「有 N 条依赖指向不存在的任务」；
   - **起点、终点（D5）**：`start` 恰好一个、`end` 恰好一个。缺了或多了，组件顶上报错（「缺起点」「有 2 个终点：X、Y」），图照画、进度仍可看，但整体完成率不算、摘要标红。起点不能有前置；所有节点都要能从起点走到，走不到的节点标出来。
   - **支线终点（D6）**：凡是没有后继的节点，都必须标成 `end` 或 `branch_end`。没标的就是「支线没确认终点」：报错，并把这条支线（从它往回到与主线分叉处）标红。流程图的回边不算后继缺失的理由，规则一样。
   - **动态改写**：改起点、终点、支线终点，就是 upsert 改角色列的值。台库写入有事务（`BEGIN IMMEDIATE`，server/src/services/bench-store-core.ts:159），实现时核对一次 upsert 的多行在同一个事务里，这样「撤旧终点、标新终点」不会露出中间态；页面经实时刷新（第五节之二）5 秒内重画。整体完成率以主线终点完成为准，摘要另列各支线终点的完成情况。
   - **节点超过上限**（建议 500）：提示「任务太多，只画了前 500 个」，并给「用筛选缩小范围」的说明；查询被截断时同样提示。
3. **布局**：分层布局，纯 TypeScript，放在 `blocks-view.ts`，不引依赖，单测直接测：
   - 层号 = 最长前置链的长度（拓扑排序）；
   - 层内次序用一到两遍重心法（按前置节点的平均位置排）减少交叉；
   - 给了 `group_col` 时，先按组分泳道，组内再排。
4. **画法**：ECharts graph 系列（包里已有，只多注册一个 `GraphChart`），坐标用第 3 步算好的，`layout: 'none'`。节点是圆角矩形：名称、状态色、进度条（文字写百分比）。边带箭头。颜色、字号只用 token。
5. **交互**：缩放、平移；点节点在侧栏看 `detail_cols`；悬停高亮它的前置和后继链。
6. **顶部摘要**：共 N 个、完成 N 个、进行中 N 个、受阻 N 个，整体完成率。
7. **等价表格**：照 docs/data-views.md「图表都有等价的表格视图」，组件右上角能切到表格（列：名称、状态、进度、前置、后继），读屏和键盘可用。

不做：拖拽、在图上改数据、自动推算关键路径（第 2 步候选）。

## 五之二、实时刷新（D2）

现状：数据视图只在点「刷新」、或离开一段时间后回到页面时重新取数（web/src/pages/BenchPage.tsx:33），没有推送。AI 实时写入时，人看到的是旧图。

做法：**轻量轮询变更游标**，不上长连接。

1. 新路由 `GET /api/bench-views/:bench/changes`，回一个游标：台库变更记录（`bs_changes`）的最大编号加当前视图版本，几十字节；实现时核对每种写入都会记一条变更。
2. 判权照取数：`who` 认人，`may(render)`，没权限 403；**不新增动作**，路由沿用 `bench-store.render` 声明（新路由进路由快照与回放）。
3. 页面可见时每 5 秒问一次游标，游标变了才重新取数、重画；页面不可见就停，回来立刻问一次。
4. 重新取数期间旧图照常显示，不闪；状态或进度变了的节点短暂高亮，让人看出「刚刚动了」。
5. 所有组件都受益（表格、统计卡也跟着刷新），不只这三种图；驾驶舱面板同样接入。

为什么不推送（SSE、WebSocket）：要长连接、反向代理配置和连接数上限，第 1 步不值；5 秒问一次几十字节的游标，开销可以忽略。日后要秒级再换推送，页面这一侧的接口不变。

## 六、AI 怎么用（示例）

1. `dataset_define` 一个 `tasks` 数据集：`id`（主键）、`name`、`deps`、`status`、`progress`、`owner`、`due`。
2. 每推进一步，`dataset_upsert` 改那一行的 `status`、`progress`；新拆出的子任务直接 upsert 新行并填 `deps`。
3. 每次推进再往 `progress_log` `dataset_append` 一行（时间、完成数、总数）。
4. `view_put` 一个视图：顶上 stat（完成率）、中间 `dag`（`tasks`）、下面 line（`progress_log` 的完成数随时间）。

数据视图技能（wm-data-views）的 `references/views.md` 要补 `dag` 的写法和这个示例；技能在哪个仓、由谁改，实现时确认。
