## 一、这篇定什么、不定什么

**定**：
1. 五项在目录里长什么样（几行、叫什么），详情给什么，调用走哪两条路；
2. 每个入口统一的判权与存在性规则；每一项请求方填什么、服务端捕获并冻结什么、确认时再核什么；
3. 复核只收活跃的人、复核邀请怎么登记和通知；
4. 和 #1016、第 16 篇各步的衔接，以及实现顺序和验收。

**不定**：
- #1016 已冻结的提案状态机、幂等、两库并发、作者回避细则（N1–N6），照 #1016 执行；
- 第 16 篇第 2 步（负责人批接入）、第 3 步（会话归属到人）本身，属身份线；
- 第 16 篇第 4 步的通用机制（能力声明、目录与详情分层、REST 与通用「调用」的转调），这里只写报告治理作为它的第一个领域要声明什么；
- 维度撤销（retire）、批量绑定、组合自动执行：#1016 不接，这里也不接。

## 三、怎么披露：目录两行，工具零个

### 1. 目录（`access_info` 默认应答）

报告治理在目录里**只占两行**，不论将来提案种类加多少：

| 能力名 | 一行说明 | 领域 |
|---|---|---|
| `report.governance-propose` | 提一项报告治理请求（登记维度、发版、请人复核、激活、台绑定），由有权的人在站内确认后才生效 | 按请求的维度或台 |
| `report.governance-result` | 查自己会话提过的治理请求现在怎样了 | 同上 |

每行照第 16 篇第三节带「本会话批没批」。不带参数表。

### 2. 详情（按名字取）

`access_info` 按能力名取一项时，给：
- `op` 的取值和每个 `op` 的入参表（第四节）；
- 出错码和「被拒时怎么办」；
- 能力说明所在的技能名：内置技能 `wm-report-governance`（随本仓 `skills/` 发，经技能市场按需读，[第 16 篇第七节之一](productization/16-progressive-capability-access.md#L145)）。现有的 `wm-capability-access` 只加一句指向它，不展开。

报告治理是市场本体的能力，不是私域，所以说明进本仓；仍按第 16 篇第六节当数据处理、限长、去控制字符。

### 3. 调用（两条路，同一套规矩）

| 能力 | REST（能写脚本的 agent） | 通用「调用」（纯聊天客户端） |
|---|---|---|
| `report.governance-propose` | `POST /api/report-governance/proposals`，体 `{ op, args, idempotency_key }` | 目标 `report.governance-propose`，参数 `{ op, args, idempotency_key }` |
| `report.governance-result` | `GET /api/report-governance/proposals/:id` | 目标 `report.governance-result`，参数只有 `{ id }`（提案或邀请编号） |

两条路走第四节第 1 小节同一道门、同一次判定、同一张审计表，渠道分别标 `rest`、`mcp-invoke`。审计按**实际被调的能力**记：提出记 `report.governance-propose` 及其 `op`；查询记 `report.governance-result` 及被查编号，不记成 propose，也不记成原提案的 op；都不记成「调用」工具本身。

**工具数**：本篇不新增任何专用 MCP 工具。`tools/list` 只会因第 16 篇第 4 步多出那一个通用「调用」，它是所有领域共用的，加一次就不再随领域增长。五项将来加 `op`、加字段，只改详情和技能正文，不动 `tools/list` 和目录行数。

### 4. 通用「调用」对本领域的界限

照第 16 篇第三节三条，落到本领域：
- 只认上面两个能力名；不能借它调 `report.dimension-set` 的 REST、`bench-store.report-bind`、四个报告 MCP 工具或任何内部路由；
- `op` 是固定枚举，`args` 按第四节第 2 小节的「请求方填」一栏严格核（多键、缺键即拒），禁止携带路由、SQL、回调地址、身份、授予（#1016「建议入口与授权模型」）；「服务端捕获」一栏的值请求里写了就拒；
- 决定类一律只产生提案：调用成功只回「编号 + 状态 pending」，业务表、生效指针、台绑定都不动，直到有权的人确认。

## 四、入口规则、入参、确认

### 1. 每个入口同一道门（REST 与通用「调用」都照此执行）

所有 `op` 和结果查询，按下面的顺序走，**前一步不过不做后一步**：

1. **认会话**：会话有效、未撤；会话有归属人（第 16 篇第 3 步）且归属人是启用的人。否则拒。
2. **解析目标范围（只在内部用，不对外说）**：
   - 维度类 `op`：请求只给维度标识。服务端在主库按标识查它所属领域，得到范围「`area:<领域>` 的维度 `<id>`」；查不到也照常往下走，只是这个范围不会被任何授予覆盖。不查台库。
   - `dimension-create`：范围取请求里的 `area`。
   - `bench-bind`：按台标识在内存登记表里查台（同取数路由的 `getBench`），得到台和台所在领域；查不到同样往下走、不被任何授予覆盖。**这一步和下一步都不打开台库。**
   - 结果查询：按编号取提案或邀请记录；取不到同样往下走。
3. **判权（严格交集）**：会话的提案授予覆盖「`op` × 第 2 步的范围」，**并且**归属人此刻对该范围有目标动作的权限：维度类（含 `review-invite`）是对该维度的 `report.dimension-set`，台绑定是对该台的 `bench-store.report-bind`。结果查询额外要求：这条记录是本会话提的，**而且**会话授予此刻仍覆盖原记录的 `op` × 原精确范围，归属人仍是原归属人且此刻仍有原动作的权限。
4. **统一拒绝**：第 1～3 步任一不过，都回同一个 403 `report_governance_forbidden`，消息相同、不带目标信息。范围查不到（维度或台不存在、编号不存在、编号属别的会话）和没有权限得到的是**同一个应答**，对外不区分存在与否。
5. **判过权才核对象**：此时才打开台库、核维度状态、核版本与摘要；对象层面的问题（标识已被占用、版本已前移、模板不适用这张台……）回 409 或 400，带原因。这些原因只给通过了第 3 步的会话。
6. **结果查询的投影**：只回状态（pending / confirmed / rejected / withdrawn / expired / conflict）、冲突原因码、确认后的结果编号（模板版本、绑定版本）。不回冻结值的全文、其他台元数据、业务行、确认人身份以外的人员信息。

和现有人工 REST 的差别：人工 REST 的 `existingSetter` 先查维度、不存在回 404，再判领域权限（[routes/report-dimensions.ts](../server/src/routes/report-dimensions.ts#L102-L110)）。那个入口面向已登录的人，照旧不改；本篇的新入口面向 agent 会话，**一律先判权再说存在**。

### 2. 入参：请求方填什么，服务端捕获并冻结什么

请求方只填「请求方填」一栏。「服务端捕获」一栏在第 3 步通过后由服务端读出、写进提案，**冻结后展示给确认人**；请求里出现这一栏的键即拒。确认时在 #1016 N4（两库提交围栏）、N5（台绑定与退役围栏）的同一个提交窗口里，把冻结值逐项和当时的事实再比一遍：**任何一项不同就冲突，提案作废，要重提；不取「最新」代替。**

| op | 请求方填（`args`） | 服务端捕获、冻结并展示给确认人 | 确认时冲突的情形 |
|---|---|---|---|
| `dimension-create` | `area`（必填）、`id`、`title` | 规范化标题；领域当时的状态 | 领域已停用；标识已被用过或退休保留 |
| `template-publish` | `dimension`、`body`、`body_sha256`、`criteria_sha256`、`expected_kind`（`criteria` 或 `layout`）、`expected_latest_version`、`note` | 按发版同一序列化口径（`addTemplate` 的 `JSON.stringify` 后 sha256，[report-dimension.ts](../server/src/services/report-dimension.ts#L223-L228)）重算的正文摘要和判据摘要；对照当时已复核判据算出的分类；当时的最新版本号 | 正文、判据摘要、分类任一与请求或冻结值不符；最新版本已前移 |
| `dimension-activate` | `dimension`、`version`、`body_sha256`、`criteria_sha256`、`expected_active_version`、`review_id`（拟使用的那一条复核记录） | 当前生效版本及其正文和判据摘要；目标版本的正文和判据摘要；`review_id` 指向的复核记录（维度、版本、判据摘要、复核人） | 当前指针已动；目标摘要不符；该复核记录被替换、不属于同维度同判据、复核人落入作者集合（N3）或已无效 |
| `bench-bind` | `bench`、`dimension`、`template_version`、`template_sha256`、`base`、`view_version`、`view_sha256`、`slots`（槽名 → 视图键与块下标） | 当前生效模板版本与摘要；当前绑定版本；视图版本与内容哈希；**逐槽**：该块查询的规范化摘要、所引数据集的身份与生命周期修订（与 #1015 对齐：名称不重用、生命周期状态）、结果列契约（列名、类型、角色） | 模板换版或摘要不符；绑定 `base` 已前移；视图版本或哈希变了；任一槽的块指向变了（含重排）、查询摘要变了、数据集身份或修订变了、列契约变了；数据集已进入退役 |

`review-invite` 不是提案，单独见第五节。

### 3. 谁确认

| op | 确认人 |
|---|---|
| `dimension-create` | 该领域持 `area-report` 的人或属主。**跨领域（不写 area）首版不开**（#1016 推荐） |
| `template-publish` | 对该维度有 `report.dimension-set` 的人。新版本作者记确认人，**起草会话的归属人记为共同作者**（#1016 N3）；生效指针不动 |
| `dimension-activate` | 对该维度有 `report.dimension-set` 的人（沿用现有激活权限，不强制第三人）。回退同此 |
| `bench-bind` | 对这张台有 `bench-store.report-bind` 的人；只在本台对此维度追加一个绑定版本 |

共同规矩：
- **按人判和按台判不互相代替**：领域的维度治理权推不出台绑定权；台的管理层、`report_generate` 授予、`bench_mcp_grants`（L18，会话 × 台 × 工具）也推不出维度治理权（第 16 篇第四节第 8 条）。
- **确认身份**只认站内同源登录的启用的人：管理口令、只是系统管理员、本机命令行、未登录的本机页面、任何会话都不能确认（#1016 N2）。命令行属主的例外只属于现有人工 REST 入口。
- **确认时重走第 1 小节的判权**：提案会话及其归属人此刻仍过第 1～3 步，确认人对目标有权；否则拒，提案作废。
- 提案的公共字段由服务端填：编号、规范化摘要、会话、归属人、作用域、过期时间（默认 7 天）。

## 五、复核：只收活跃的人；邀请是受控的站内邀请

### 1. 没有可以变成复核的路径

1. 能力里没有「提交复核」这个 `op`。`review-invite` 产生的是邀请记录，**不是提案**：它没有「确认」这个动作，也不能被任何人确认成一条复核。
2. 复核意见只经现有人工入口提交（`POST …/templates/:version/review` 或之后的站内页面），提交者必须是启用的人（[report-dimension.ts](../server/src/services/report-dimension.ts#L147)）、对该维度有权、不在作者集合里。

### 2. 邀请（#1016「复核邀请」）

| 事 | 规定 |
|---|---|
| 入参 | `dimension`、`version`、`body_sha256`、`criteria_sha256`、`invitees`（**必填**，1～5 个人的主体标识）、`idempotency_key` |
| 判权 | 走第四节第 1 小节同一道门：会话授予覆盖「review-invite × 该维度」，**且归属人此刻对该维度有 `report.dimension-set`**。作者本人可以发起邀请（请别人复核） |
| 登记 | 判权通过后，在主库写一条邀请记录：编号、维度、版本、两个摘要（与目标版本不符即 409）、发起会话、归属人、被邀请人、过期时间（默认 7 天）。和提案同一张审计表，记 `report.governance-propose` / `review-invite` |
| 收件人 | 只发给 `invitees` 里**此刻**对该维度有 `report.dimension-set` 且不在作者集合的人。有人不符时整条邀请拒绝，回一句不点名的「被邀请人里有人不符合复核条件」，不说是谁、因为什么。**不做「不写就通知全部有权的人」的广播**：那是新增的外发行为，要做先请属主裁决 |
| 通知时点与方式 | 记录写入成功后**只通知一次**，走站内待办（不发邮件、不经 A2A、不外发）。待办只是一个指向精确版本的链接，打开时重新判权 |
| 重放 | 同 `idempotency_key` 同内容：回原邀请，不再通知；同键不同内容：冲突 |
| 失效 | 过期、发起会话或归属人被撤、目标版本被后续版本取代（判据变了）、被邀请人失去权限或成了作者：邀请作废。已发出的待办打开时按当时判权，不符就看不到内容；作废不发第二次通知 |
| 不做的事 | 邀请不预占、不锁定复核名额；被邀请人可以不理；没被邀请的有权非作者照样可以复核 |

### 3. 作者集合统一落实（#1016 N3）

作者集合在领域服务里统一算，**新入口和现有人工 REST 的复核、激活共用**：
- 同维度、同判据摘要的任一版的发布者；
- 共同作者，含起草提案的会话的归属人；
- 多账户合并、身份迁移按权威主体映射归并；映射缺失或作者认不出时，复核拒绝，激活也不承认该复核为有效证据；
- 换会话、换标题、只改版式都洗不掉作者身份；版式稿可复用既有合格的同判据复核，但不生成新的复核记录。

跨领域维度只有一位属主时，发版后只能等另一位有权的人复核，当下不可激活（#1016 已定）。

## 六、实现顺序（方案 A）

| 步 | 做什么 | 归谁 | 前置 | 合入 |
|---|---|---|---|---|
| 0 | 本稿 | UI/UX 席执笔 | 无 | 纯文档，非作者复核 |

## 八、待评审定

| 事 | 推荐 | 其他做法 |
|---|---|---|
| 目录里一行还是两行 | 两行（提和查分开），与 #1016「提出请求」「查询结果」两个入口一致 | 一行 `report.governance`，用 `op: result` 查；目录更省，但「查」也要受提案授予约束，读写分不开 |

| 是否允许「不点名、通知该维度全部有权的人」 | 不允许（本篇已定被邀请人必填、整条拒绝不点名）；广播是新增外发行为 | 要做须属主裁决：收件人范围、频率上限、对外泄露谁有权的风险 |
