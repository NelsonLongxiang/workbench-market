# Odoo same-host login relay

Optional, default off. Set `WM_ODOO_LOGIN_PROXY=1` and set `WM_ODOO_URL` to the exact internal Odoo HTTP(S) origin (no credentials, query, fragment or path). An invalid origin fails startup. An enabled Odoo workbench at the same origin is still required for the tasks login entry to be advertised. The existing popup uses a relative `/web/login?redirect=...` link, so LAN and public browsers keep the host and scheme they used to reach the market. The plain `/go/<id>/` entry (no `return`) also stays on the current host: it redirects to `/web/login?redirect=/go/<id>/?state=<uuid>`, and after login Odoo returns to that portal SSO callback, which still checks the `wm_sso_<id>` state cookie before forwarding the session. Besides the return pages, the relay accepts only that exact callback shape, and only with a ticket the portal issued for that workbench: a one-time, 10-minute state bound to the workbench id and the trusted Odoo origin, re-checked against the current registry and `WM_ODOO_URL` on every use and consumed when the callback passes the state cookie check. A well-formed state for any other workbench, a forged or replayed state, or a workbench that has since moved off the trusted origin is stripped. With the relay off, the classic redirect to the upstream Odoo origin is unchanged.

The relay is restricted to the market listener. It forwards only `/web/login`, `/web/login/totp`, read-only Odoo assets, the company logo, and read-only `/website/translations`. It is **not** a general Odoo proxy. Upstream is fixed by trusted server configuration, never the request host. It passes only the Odoo `session_id` cookie upstream, filters request headers, and only accepts Odoo session cookies on login routes. The session cookie is host-only, HttpOnly, SameSite=Lax and scoped to `/`, with Secure when the forwarded protocol is HTTPS. Reverse proxies must overwrite `Host` and `X-Forwarded-Proto` with their actual values. Odoo retains responsibility for authentication and its CSRF checks. Login forms are size limited; cross-origin browser submissions and external redirect targets are rejected.

Only `/tasks`, `/login` and pages an extension registers through `ctx.odoo.addReturnPath` are valid market return paths. Odoo password login and TOTP routes are supported; external OAuth or other Odoo add-on login redirects are not forwarded (a 502 may be returned). A synthetic TOTP test is not evidence of live MFA compatibility. A real account login is needed to verify the live authentication method and the browser cookie after the actual public reverse proxy.

Enabling this option exposes the Odoo login surface through the market domain. Apply appropriate network restrictions and ensure Odoo's own login-throttling is active. Because reverse proxy/NAT may collapse source addresses, verify the actual client-address and rate-limit behavior before relying on per-client limits. This relay does not provide origin isolation for other content surfaces.

Run `node scripts/odoo-same-host-login-smoke.mjs` for isolated HTTP tests. Set `CHROME_BIN` to a Chromium executable to include the synthetic browser form, cookie and return checks. No real account or production data is used by this test.

## Odoo logout when the relay is enabled

The viewer menu provides **退出 Odoo**, including a logout control on the login page for an Odoo account that is denied market access. The explicit same-origin JSON logout clears the market-scoped root session cookie and sends only the SID to the fixed configured Odoo origin's authenticated POST JSON-RPC /web/session/destroy. It does not expose a general Odoo logout proxy or follow redirects. A 502 means the browser cookie was cleared but upstream revocation could not be confirmed; the UI warns the user rather than claiming success. Ambiguous duplicate session cookies fail closed. When relay mode is off, legacy logout behavior is unchanged.

Relay mode checks Odoo identity fresh for the login gate and administrator checks rather than retaining positive identity cache entries across an explicit logout. Requests already in flight are not retroactively cancelled. Verify real Odoo login **and logout** using the deployment's actual authentication method before enabling the relay publicly.
