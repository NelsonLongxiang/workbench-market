# 站内账号与用户管理（设计）

状态：设计，属主 2026-11-16 定方向（站内自己的用户管理：管理员、注册、创建、管理用户）。按下面的阶段分 PR 落地，每个阶段单独可用、单独验收。

## 一、要解决什么

现在能登录本站的只有外部来源：Odoo（每次请求现查它的会话）和飞书（授权码流程）。没有 Odoo、没开飞书的部署，人进不来；管理员只有两种：管理口令和 Odoo 管理员。

要加的是：

- 站内账号：用户名加密码，不依赖任何外部系统就能登录。
- 管理员在站内建人、改密码、停用和恢复，并任命管理员。
- 自己注册：填用户名和密码，等管理员核准后才能用。

## 二、不重造的东西

身份核心已经有完整的骨架。站内账号只是又一个登录方式，接在现有的东西上：

| 已有的 | 站内账号怎么用 |
|---|---|
| 登录方式插件（`LoginFlow`，`server/src/login-providers/`） | 新增插件 `local`（显示为「账号密码」） |
| `/login/<方式>` 发起、`/login/<方式>/callback` 回调：state 一次性、绑浏览器，按来源限额，发市场会话 | 原样复用，核心的这两条路由不改 |
| 主体与外部身份（`principals`、`principal_identities`） | 站内账号的外部身份是 `local` 加用户名 |
| 待对接清单（`/api/principals/pending`）与对接（`POST /api/principals/bind`，`create: true` 可新建人） | 自己注册的账号就是一条待对接的外部身份，管理员核准就是对接 |
| 停用和恢复（`/api/principals/disable`、`restore`），停用后所有入口立即不认 | 原样复用 |
| 角色与授予（`owner` 属主、`admin` 系统管理员……；授予有起草、提交、属主放行、撤销、到期） | 任命管理员就是给 `admin` 授予，走现有的放行流程 |
| 等待页（认出了人但未对接或已停用，同一页、不透露是哪种） | 自己注册还没核准的人看到的就是它 |

## 三、决定

### 1. 登录：插件 `local`

- 核心给 `LoginFlow` 加一个可选能力 `form`：插件可以提供一张站内表单页（`GET/POST /login/<方式>/form`）。核心负责路由、限额和安全头，插件只管表单内容和校验。飞书不用这个能力，不受影响。
- 流程：`GET /login/local` 由核心照常签 state，插件的 `begin` 把浏览器送到 `/login/local/form?state=…`（站内地址）。表单提交用户名和密码，校验通过后插件发一个一次性的码（60 秒、只能用一次、和这次的 state 绑定），302 到核心的回调 `/login/local/callback?state=…&code=…`。回调照常核销 state，插件的 `complete` 用码换回用户名，之后对主体、发会话都是核心原有的步骤。
- 这样做的好处：state、会话、停用、等待页全部复用核心的实现，插件里没有发会话的代码。

### 2. 密码

- 只存 scrypt 的结果（Node 自带，`N=2^15, r=8, p=1`，每个账号单独加盐，64 字节），带参数一起存，以后能升级参数。不引入新依赖。
- 长度至少 10 位，最多 128 位；不能和用户名相同。
- 校验用定长比较。用户名不存在时也算一次假的 scrypt，让「没这个人」和「密码不对」耗时相同、提示相同（「用户名或密码不对」），不暴露有没有这个账号。
- 连续 5 次输错，这个账号锁 15 分钟（再叠加核心已有的按来源 IP 限额）。管理员可以解锁。
- 管理员建人或重置密码时，系统生成一个临时密码只显示一次，账号标「下次登录必须改密码」。改之前这个会话只能访问改密码页。
- 重置密码、改密码、停用，都立即注销这个人所有的市场会话。
- 密码、临时密码、码，都不进日志、不进审计正文、不进任何应答（临时密码只在生成那一次的应答里出现）。

### 3. 用户名

- 小写字母、数字和 `. _ -`，2～32 位，以字母或数字开头。对应主体 `user:<用户名>`，规范化和撞名检查沿用主体已有的规则。
- 外部身份写成 `local` / `<用户名>`。

### 4. 注册

- 开关 `WM_LOCAL_SIGNUP`：`off`（缺省，没有注册入口）或 `approval`（开着，注册后等核准）。原先按「缺省开启」定的是 `approval`；2026-11-16 改成缺省关：自己注册是对外开的口子，部署方要明确打开。`WM_LOCAL_LOGIN` 缺省仍是开。启动日志有一行 `event: "config"` 写明登录、注册开关和待核准上限当下的值。
- 待核准上限 `WM_LOCAL_SIGNUP_PENDING_MAX`（缺省 50，1～10000）：自己注册、还没核准的账号到了这个数，注册暂停，提交回 503「注册先暂停」，不占来源的次数、不算哈希；管理员的「等你拍板」里出一条「自己注册已暂停」，核准或拒绝一些之后自动恢复。写入前再数一次，算哈希期间并发的注册也超不过。
- 注册只建一个站内账号（用户名加密码），不建主体，也不绑定。登录后核心发现这个外部身份没对接，就把它放进待对接清单，给等待页。管理员在用户管理里核准，就是把它绑到一个新建的主体 `user:<用户名>` 上。
- 不提供「注册即可用」的模式：自己开通的账号直接拿到站内访问权，等于没有门。以后真需要，再单独加开关并附对抗组。
- 注册按来源 IP 限额（每小时 5 个），用户名被占用时提示「这个用户名不能用」，不区分是已注册还是保留名。
- 已知取舍：用户名占着回 409，注册页能拿来探某个用户名有没有人用。2026-11-16 定接受：要关掉它，就得让占着的名字也假装注册成功（之后登录再失败），对真用户的困惑比这点信息大；而探测本身被两道限住——同一来源每小时 5 次，全站待核准上限（探中的不建账号，探不中的会建出一个待核准账号，占满上限注册就暂停）。用户名不是秘密（主体标识、留痕里都看得到），登录照旧不分「没这个人」和「密码错」。

- 核准注册、管理员建账号都**只新建**人（`bindIdentity` 的 `createOnly`）：`user:<用户名>` 或它的等价写法已经有人了，就拒（409「这个名字已经属于一个现有的人」），不接到那个人身上。注册时没撞名，不代表核准时还没人用这个名字（那个人可能后来第一次从别的登录方式进来）。待核准列表上这种账号带 `name_taken`。
- 自己注册的账号（`created_by` 是 `signup`）**只能**经核准新建主体：通用的对接 `POST /api/principals/bind`、`bind-batch` 不收它（按等价写法比，409，`reason: "self-signup"`），免得把一个任何人都能注册的名字绑到已有的人身上。待对接清单（`/api/principals/pending`）里这种条目带 `self_signup: true`，「等你拍板」里标「自己注册」、不给对接的答法，送去「账号」页。真是已有的那个人，让他用已有的登录方式进来，或者拒掉这个注册、由管理员给他建账号。

### 5. 管理员

- 站内管理员 = 持有生效中的 `owner` 或 `admin` 授予的主体。
- 核心改一处：市场会话认人时，如果这个主体有生效中的这两种授予，`viewer.admin` 为真。这样现有所有管理接口（`adminGuard` 等）无需改动就认它。管理口令和本机命令行照旧可用，用作应急。
- 实现（P2）：身份服务在认出人的两个出口（市场会话、主体目录对上之后）现查授予（`grants.heldAdmin`），不进任何缓存，所以收回、过期、停用下一个请求就生效；只要求范围是 `*`。因为是在认人这一层加的，经 Odoo 直接认出的人持有这两种授予同样算管理员。
- 属主 2026-11-16 定：`admin` 授予是**系统管理员**——管系统（账号、主体、授予、设置等），看不到业务数据；`owner` 授予是完整的管理员。实现：`viewer.admin` 只在 `owner` 时为真（直接读它的业务面一律不认系统管理员），`admin` 授予记 `viewer.systemAdmin`；管理门（`isAdmin`）只在落到非业务域（`roles.ts` 的 `BUSINESS_DOMAINS` 之外）的路由上认系统管理员。这一条取代上面「已知取舍」里 `admin` 授予拿到整套旧权限的说法。
- 这种管理员在留痕里记主体（`user:<名>`），`/api/admin/whoami` 回 `via: "grant"`。各管理接口把留痕对回主体时（不能停用自己、不能放行授给自己的、属主认定）统一用 `actorPrincipal`。
- 任命和撤销走现有授予流程：起草、提交、属主放行。系统管理员不能自己任命自己；授予的放行规则不变。
- 冷启动：第一个管理员用管理口令或本机命令行建账号并授予。
- 已知取舍：在细粒度判定（`WM_JUDGMENT_ENFORCE`）全面启用之前，`admin` 授予拿到的是旧的「管理员」整套权限，比角色设计里「系统管理员看不到业务」要宽。判定切换按域推进时会收回到角色设计的范围，本设计不提前做。

### 6. 用户管理（管理员）

接口都在 `/api/local-accounts` 下，要管理员，浏览器来源要同站：

| 动作 | 接口 | 说明 |
|---|---|---|
| 列出 | `GET /api/local-accounts` | 用户名、对应主体、状态（待核准、启用、停用、锁定、要改密码）、建立和最近登录时间；不含任何密码材料 |
| 建人 | `POST /api/local-accounts` `{username, display_name}` | 建账号和主体并绑定，回一次临时密码 |
| 核准注册 | `POST /api/local-accounts/:username/approve` | 把待对接的站内账号绑到新建的主体上 |
| 拒绝注册 | `POST /api/local-accounts/:username/reject` | 删掉未对接的账号 |
| 重置密码 | `POST /api/local-accounts/:username/reset-password` | 回一次临时密码，注销所有会话 |
| 解锁 | `POST /api/local-accounts/:username/unlock` | 清掉输错计数 |
| 停用和恢复 | 现有 `/api/principals/disable`、`restore` | 不新增 |
| 任命管理员 | 现有 `/api/grants` | 不新增 |

本人：`POST /api/local-accounts/me/password` `{current, next}` 改自己的密码。

页面：

- 登录页的登录方式里出现「账号密码」。
- 表单页带「注册」入口（`WM_LOCAL_SIGNUP=off` 时不出现）。
- 「谁能做什么」（`/access`）加一个页签「账号」，放上面的管理动作。

### 7. 安全面

- 对抗组：
  - 未知用户名和错误密码同应答。
  - 锁定生效。
  - 一次性码不可重放、不可换浏览器。
  - 未核准的注册登不进。
  - 停用后旧会话立即失效。
  - 非管理员调不了管理接口。
  - 跨站请求被拒。
  - 应答和日志里不出现密码材料。
  - 要改密码的会话只能去改密码页。
- 启动自检加一行：用一个不存在的用户名走一次表单登录，必须得到「用户名或密码不对」，不发会话。

### 8. 限额与并发（P1 之后补）

P1 上线后实测：同一来源、同一 state 并发 60 个错密码提交，60 个都进了 scrypt、都是 401，没有一个 429。原因有两条：按来源的失败计数在 scrypt 算完之后才记；表单的 state 只看不核销，可以反复用。scrypt 每次约 110ms、32MB，持续并发会占满 libuv 线程池。改成：

- **算哈希之前先占名额。** 这一次先记进来源的尝试数（一分钟 10 次，核对对了的退回不算），再看三道「同时在算」的上限：同一来源 1 个（同一来源的登录排队一个一个核）、同一用户名 1 个、全进程 2 个（线程池缺省 4 个线程，留一半给别的活）。来源、用户名两道超了直接 429，不进哈希；全进程那道满了先短排队（最多 16 个、每个最多等 2 秒；请求断开了——浏览器关了、客户端中止——立即出队、不算），队满或等超时才 429——正常登录碰上别人正在算时不白白被拒（只排全进程那一道时，随机间隔、到能力六成的登录实测约两成被白拒），并发攻击照样只有 2 个同时在算，进哈希的总数不超过 2 加队长。这几个计数只在内存里，单实例够用；以后多实例、换 PG 时，换成共用的存储，接口不变。
- **表单 state 一次性。** 每提交一次，核心记着的 state 就换一个新的（`loginSessions.rotateState`）：旧的作废，登录方式、next、浏览器半边、到期时间照旧。页面、一次性码、改密码票都接着用新的。用过的、重放的、伪造的、过期的都拒（400）；并发拿同一个 state 来交，只有一个换得到。账号密码那一步先占名额再换，名额占不上时 state 不动（回 429，可以稍后重交）。
- **双击、浏览器重发。** 同一个 state、填的东西一模一样的重复提交，在第一次还在算、或者刚算完 10 秒内，拿第一次的结果，不再算一遍，也不回「已过期」。浏览器显示的是最后那个应答，第一次的应答（带一次性码的跳转）被它丢了，所以要给它同一个跳转。核心对提交认「刚换掉 10 秒内」的 state（只在内存里），交给登录方式判；填的东西不一样的照旧当重放拒（400）。比对只存 HMAC（进程随机密钥），不存密码。
- **来源。** 按来源的限额用的来源 IP 只在对端是可信反代（`WM_TRUSTED_PROXIES`，缺省只认回环）时才看 `X-Real-IP` / `X-Forwarded-For`。写进可信反代的地址都能自报来源；docker 网桥网关的坑和启动自检见 README 的变量说明。即使来源被伪造，「同一用户名 1 个」「全进程 2 个」这两道上限和账号锁定照样挡着：换头能绕过按来源的计数，但绕不过并发上限，也绕不过对单个账号的猜测次数。

### 9. 锁定被拿来锁别人（取舍）

现在的锁定是按账号的：任何来源对一个账号连续输错 5 次，这个账号锁 15 分钟。知道用户名的人可以故意输错，把别人锁住（每 15 分钟 5 次就能一直锁着）。几种做法：

| 做法 | 挡猜密码 | 被人锁住 | 代价 |
|---|---|---|---|
| A. 按账号锁（现在） | 好：不管换多少来源，一个账号 15 分钟最多猜 5 次 | 容易：知道用户名就能锁 | 管理员要手动解锁；被锁的人登不进 |
| B. 按「账号 + 来源」锁 | 弱：换来源就重新数，分布式猜测不受限 | 难：只锁住攻击者自己的来源 | 来源能伪造时（见上一节）等于没锁 |
| C. 逐步变慢（每错一次，这个账号下一次核对要等更久，有上限） | 中：猜的速度被压住，但不会完全停 | 难：本人只是慢一点，进得去 | 要记每个账号的「下一次最早什么时候」；本人也会被拖慢 |
| D. A + 本人另有出路（比如锁定时本人能用一次性链接或管理员重置） | 好 | 有影响但能自救 | 要有站外联系方式（邮件、飞书），现在没有 |

取舍：**暂时保留 A**。站内账号现在只给内部的人用，用户名不对外公开，管理员能当场解锁、重置；被人恶意锁住是能看见、能处理的事，而 B 在来源能伪造的部署里等于没有锁。等有了站外联系方式（P3 之后），改成 C 或 D。在那之前，运维上要做到：

- 可信反代按 README 配，按来源的限额不被换头绕过；
- 锁定、解锁都进日志：账号被锁住时记一行 `locked`（用户名、来源、锁到几点），管理员解锁照旧记 `unlock`；被反复锁的账号能查出来源。

## 四、阶段

| 阶段 | 内容 | 可用的结果 |
|---|---|---|
| P1 | 表（`local_accounts`）、服务、插件 `local`、核心 `form` 能力、建人、重置、解锁、列出、本人改密码、要改密码的门、对抗组、启动自检 | 管理员用口令建人，人能用账号密码登录 |
| P2 | 管理员识别（`owner`/`admin` 授予 → `viewer.admin`）（已实现） | 站内账号可以当管理员，不再依赖口令 |
| P3 | 注册（`WM_LOCAL_SIGNUP`）、核准、拒绝（已实现） | 人可以自己注册，等核准 |
| P4 | 页面：登录页入口、表单和注册页、`/access` 的「账号」页签（已实现：登录页入口和表单、注册页在 P1、P3 里做了，「账号」页签在 P4） | 全部在页面上操作 |

每个阶段一个 PR，各自带测试并接进 CI，更新 README 的环境变量与接口说明，以及 `surfaces/` 快照。
