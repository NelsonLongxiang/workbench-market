# 08 · 技术路线收拢

> 阶段 0 草稿。01 ～ 07 定了产品是什么、和别的部件怎么接；这一篇定**怎么建**：每件事只有一个归属、一种做法。数字是 2026-11-10 在 main 上实测的，量法见 [09 的附录](09-constraint-system.md#附录量法)。

## 一、路线

市场只做四件事：

- **呈现**：驾驶舱、门户、自产台、SOP 执行页。
- **判定**：谁能做什么，哪些事要先问人。
- **留痕**：谁在什么时候、凭什么、做了什么。
- **索引**：事项指向各部件里的原件，市场不存第二份。

席位怎么运行、消息怎么送达、席位怎么判断、证据怎么存、业务规则是什么，都不归市场。市场消费这些部件的契约，不抄它们的实现。

技术栈就下面这一套，阶段 1 ～ 2 不换也不加：

| 层 | 选定 | 备注 |
|---|---|---|
| 运行时与语言 | Node 24；TypeScript 直接运行，只用可擦除语法，server 没有构建步骤 | 类型检查在 CI 里单独跑 |
| HTTP | Express 4，单进程 | |
| 结构化数据 | SQLite（`node:sqlite`），一个库文件，是唯一的真源 | Redis 只放 SOP 进行中的热状态，可以不配；文件放数据目录和 LayerFS；凭据库是单独的加密文件 |
| 服务层 | cordis 容器，`server/src/services/` 下按域一个 Service（已有 11 个） | |
| 前端 | 一个应用：React 18 + antd 5 + Vite；token 由 `DESIGN.md` 生成 | |
| 入口面 | REST、MCP、门户代理、A2A 入站，只有这四个 | |
| 测试 | 零框架的 node 脚本；浏览器回归用 Playwright | |
| 交付形态 | 一个组织一个实例：单进程加一个数据目录 | 实例内部的隔离边界见 [租户边界评审件](../tenant-boundary-review.md) |

## 二、现状（实测）

| 关注点 | 今天 | 后果 |
|---|---|---|

| 前端取数 | 约定的入口是 `web/src/api.ts`；它之外还有 33 处直接 `fetch`，分在 13 个文件 | 鉴权头和错误处理各写各的 |

这些数字不是哪一次改动造成的。每个 PR 单看都对，加起来路线就散了——所以收拢之后还要有东西守住它，见 [09](09-constraint-system.md)。

## 三、收拢后的形态

```
调用方      人（浏览器）     agent 席位     台页面（沙箱）     外部节点
                │               │                │                │
入口面      ┌───┴───────────────┴────────────────┴────────────────┴───┐
            │    REST         MCP         门户代理        A2A 入站     │   每条路由登记时声明访问类别
            └──────────────────────────┬──────────────────────────────┘
内核                  身份  ──→  判定  ──→  留痕                           全站各只有一处
                                       │
领域服务     workbench · app · sop · skill · mcp · vars · 事项 …           SQL 只在这一层
                                       │
存储与适配   SQLite │ 文件 │ a2a/（唯一 outbox）│ ygl-trees 上游 │ DSH 深链
```

- 请求只有一条路：从入口面进，过内核，到领域服务。领域服务不认识 HTTP，适配层不认识业务。
- `index.ts` 最后只做一件事：把这几层装起来。
- 界面同理：一个应用、一套 token、一个取数入口。

## 五、内核：身份 → 判定 → 留痕

四个入口面今天各有各的身份识别和权限判断。收拢成三步，每一步全站只有一处：

```ts
type Actor = {
  kind: 'human' | 'agent' | 'app' | 'node' | 'system';
  id: string;        // 沿用现有留痕里的写法：odoo:<登录名>、mcp:<会话名>、app:<台>、admin-token、cli；A2A 来源新增 node:<团队>
  source: 'odoo' | 'admin-token' | 'mcp-session' | 'app-token' | 'origin-claim' | 'loopback';
  verified: boolean; // 没验证过的来源只当数据，不触发动作
};

type Decision = {
  effect: 'allow' | 'ask' | 'deny';
  rule: string;      // 命中的规则 id，留痕和排障都用它
  reason: string;    // 给人看的一句话
};

// action 写成 <域>.<动词>：workbench.open、app-data.submit、sop.publish、mcp.grant、vault.read
function decide(actor: Actor, action: string, resource: { kind: string; id?: string }): Decision
```

1. **身份**：只回答「这是谁」。验签、比对口令、查会话都在这里；多种凭据同时出现时谁优先，也只在这里定一次。管理口令是共享身份，留痕照实记 `admin-token`，不冒充具体的人。
2. **判定**：只回答「这个身份能不能做这件事」。现有的判定函数不重写，原样登记成规则，换的是调用位置和结果的形状。
3. **留痕**：所有非允许的判定、所有被允许的写操作各记一行——谁、身份从哪来、动作、对象、结果、命中的规则。

路由登记时就把这三步接好：

```ts
route({ method: 'post', path: '/api/apps/:slug/data', access: 'app', action: 'app-data.submit', audit: true }, handler)
```

没声明访问类别的路由，启动时直接拒绝。访问类别从现有的 12 个守卫归并出来（候选：`public`、`viewer`、`admin`、`app`、`session`、`signed`、`loopback`），开工时定，定了写进路线清单。

收拢换来三样东西：

- **「谁能做什么」能整张读出来。** 规则是一张表，不是散在二十来个地方的 `if`。
- **「先问人」成为通用结果。** `ask` 不是新发明：变更申请、MCP 权限申请今天就是这个形状——请求落成一条待决，批准后生效。收拢之后任何动作都能配置成先问人，问题自动进「关注」。[06](06-a2a-superagent-fusion.md) 里 held、observe、auto 的逐步放权，开关就落在这里。
- **留痕不靠自觉。** 写操作只能经登记过的路由进来，经过了就一定有记录。

为什么这三步必须各只有一处：管理者要的可控就是三个问题——谁在干、凭什么、什么在等我。答案如果是从多处拼出来的，拼的地方越多越不可信。

## 六、不做清单

阶段 1 ～ 2 有效。产品层面的不做见 [01](01-product-definition.md)，这里只列构建上的：

1. 不引入第二个数据库、ORM 或迁移框架。
2. 不引入工作流引擎。流程的载体是 SOP。
3. 不拆微服务，不做一库多租户。**一个组织一个实例**，多个组织就是多个实例。
4. 不引入第二个前端框架、组件库或状态库。
5. 不自建 agent 运行时、消息总线、知识库、账号体系。
6. 市场进程不新增模型调用。
7. 不换测试框架，不给 server 加构建步骤。
8. 公开仓不放业务。

要破例，就改这张清单：PR 里看得见，由属主裁定。

## 七、顺序

| 序 | 做什么 | 性质 | 前置 |
|---|---|---|---|
| 0 | 约束先行：路线清单、体检脚本（只报告）、基线、仓库根 `AGENTS.md`（见 [09](09-constraint-system.md)） | 不改运行时 | 属主裁定红线范围 |
| 1 | 路由登记函数；按域把路由搬出 `index.ts` | 纯移动，对外行为不变 | 0 |
| 2 | A2A 适配层与唯一 outbox（[07](07-a2a-adapter-refactor.md)） | 对外行为不变 | 与 1 错开，避免同时改 `index.ts` |
| 3 | 内核：身份解析 → `decide` 外壳 → 留痕入口 | 先并行比对，零差异后切换 | 1 |
| 4 | 事项表、事项日志、「关注」读模型 | 新增 | 3 的留痕入口 |
| 5 | 配置模块、任务登记处、类型错误清零 | 持续进行，随手收 | 0 |

界面线与此并行：Token v2 → 驾驶舱 v2 外壳 → 体验版面板（[05](05-token-v2.md)、[03](03-cockpit-v2.md)）。

- **终点**：`index.ts` 只做装配，0 条路由、0 处 SQL。每个阶段收到哪，在约束的预算档打开时按当时的基线定。
- **对阶段 1 的影响**：这条线给「真实底座」加了第 1、3 两步，体验版不依赖它们。工期紧时先保 0、1、2、4；第 3 步可以只上外壳和并行比对，切换留到预演之后。

风险：

- **路由顺序**：Express 按登记顺序匹配，搬动会改变顺序。路由清单的快照带顺序，搬前搬后必须一致，再加录制回放。
- **并行冲突**：多个 PR 同时改 `index.ts`。一次只搬一个域，PR 要小，搬的那个域当天不接别的改动。
- **判定改错权限**：不重写判定逻辑，只换调用位置；并行比对零差异才切换；安全面 PR 照旧附对抗组。
