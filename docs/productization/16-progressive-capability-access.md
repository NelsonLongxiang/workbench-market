# 16 · 渐进开放：常用的走 MCP，领域能力按需申请

> 属主 2026-11-18 的方向，分两次说：
>
> 1. 「MCP 应该作为常用的功能选项。而不常用的、业务领域的，特别是私域的，应该以 REST API 来开放，通过 MCP 临时申请授权通道，采用渐进式披露的方式，对上下文的处理会更好一些。」
> 2. 「私域指的是私有的一个业务领域。授权按团队负责人批就行，团队负责人由属主授权，允许哪些权限也由属主定。这个授权跟随账户的限制条件走，没有时效。」
>
> 3. 「有团队就一定会有负责人。」（同日，更正第 15 篇的「没有负责人」）
> 4. 「我们是尽量的避免暴露更多的 MCP 工具，只暴露常用的，其他的通过渐进式披露来完成。」（同日，回答「私域批下来以后要不要也变成 MCP 工具」）
> 5. 「所以我们有必要内置一些技能在技能市场当中。」（同日）
> 6. 「技能这一块宽松一点吧，暂时不需要做什么限制。」（同日，回答「私域技能要不要按领域限制谁能读」）
>
> 本篇是设计稿，按上面六段写成模型、规则和实现顺序。领域的定义沿用 [15](15-two-layer-org.md)；授予和判定沿用 [11](11-identity-and-permission.md)。要排进路线图，由统筹在 [12](12-implementation-plan.md) 第零节加一行。

## 一、要解决什么

接进来的业务越多，agent 的上下文被吃掉得越多。吃掉上下文的有两样，要分开治：

| 吃上下文的 | 怎么来的 | 治法 |
|---|---|---|
| **工具定义** | 会话一开始，客户端就把工具名、说明、参数表全塞进上下文 | 先只给目录，用到哪个再展开哪个（渐进披露） |
| **调用结果** | 大列表、文件、报表原样回进上下文 | 大结果给引用（地址加 sha），由脚本去取，不进上下文 |

现在的状况（2026-11-18，main）：

- `tools/list` 已经按会话的授予过滤：没批的工具不出现。
- `access_info` 会一次返回**完整目录，每个工具都带参数表**，包括没批的。这是目前最大的一块上下文开销，而且和渐进披露是反着来的。
- 申请和审批已经有了：会话用 `access_request` 提申请，审批动作是 `mcp.access-approve`（类别是决定），现在由管理员批。批的是一个个工具，没有领域范围，也没有绑到账户。
- 数据视图的工具另有一条路：「会话 × 台 × 工具」的授予记在 `bench_mcp_grants`，由台的管理层批，不经统一判定（存量差异 L18）。
- 工具已经有 REST 镜像（`/api/mcp-rest/tools/<名>`，加上 `openapi.json`），和 MCP 用同一个会话令牌，审计也区分两个渠道。大文件已经有上传票和直传。

## 二、业内怎么做（2026 年的情况）

业内已经大体收敛成四层。本篇四层都用，只是侧重不同：

1. **客户端延迟加载工具定义。** MCP 官方给客户端的建议是：照常 `tools/list`，但先不放进上下文，只给模型一个搜索工具，用到再加载。OpenAI 的接口也可以给工具标「延迟加载」，按命名空间或 MCP 服务器整组延迟。主流客户端已经这样做了，所以服务端**不必**再自己做工具搜索。
2. **代码执行。** 把工具当成文件或 API 给 agent，由它写代码去调，中间数据在执行环境里过滤，不进上下文（Anthropic 的「Code execution with MCP」、Cloudflare 的「Code Mode」）。这对应本篇的「领域能力走 REST、大结果给引用」。
3. **Skill 式渐进披露。** 开局只有一行说明，用到时再读正文和参考资料。已经有人把 OpenAPI 规格直接转成这种说明，让模型按需读接口再调用。
4. **网关：发现和授权绑在一起。** 没权限的工具在「发现」时就不出现，申请走审批，凭据按人收窄。

这四层要守住同一个前提：**换通道不能换规矩。** REST 和 MCP 必须是同一套认人、判定和审计，REST 不能成为更松的旁路。

## 三、模型：三层能力，一条申请通道

```
常驻（MCP，长期有效）：目录 · 申请 · 公共区的读 · 少数高频工具
────────────── 申请 → 审批（团队负责人）──────────────
领域能力（批了才能调）：不进 tools/list；经目录 → 详情 → 调用逐步披露，REST 或常驻的「调用」工具 ＋ 一页说明
────────────── 大结果 ──────────────
按引用返回：地址 ＋ sha ＋ 摘要；由脚本去取，不回进上下文
```

| 对象 | 是什么 | 从哪来 |
|---|---|---|
| 常驻集 | 每个会话都有的那一小组：目录、详情、申请、一个通用的「调用」、读公共区（[15](15-two-layer-org.md) 第九节，读不限制），加上少数高频工具。**这是 `tools/list` 里出现的全部**（属主 11-18：只暴露常用的） | 核心声明；哪些算高频，按审计里的真实调用次数定，不靠拍脑袋 |
| 领域能力 | 一个领域对外开放的动作，以 REST 接口声明；**不注册成独立的 MCP 工具，批了也不进 `tools/list`** | 领域自己声明（公开仓只给机制，见第六节） |
| 能力说明 | **以技能的形式发布在技能市场里**（技能是它的载体；对 agent 来说它是参考资料，不是指令，见第六节）：每个领域一个，写能做什么、怎么调、注意什么，OpenAPI 片段放在它的参考资料里。目录里只有一行说明，正文用 `skill_read` 按需读 | 公共的（怎么发现、申请、调用）作为内置技能随本仓发；私域的随扩展登记进技能市场，不进本仓 |
| 申请 | 某个会话要某个领域的哪些动作，附理由 | 会话经 `access_request` 提 |
| 授予 | 批下来的结果，是 [11](11-identity-and-permission.md) 里的一条授予 | 团队负责人批 |

**发现分三步，每一步只给下一步需要的信息：**

1. **目录**：`access_info` 默认只返回目录索引，每项是名称、一行说明、所属领域、本会话批没批。**不再附参数表。**
2. **详情**：按名字取某一个工具的参数表，或者某个领域的说明和 OpenAPI 片段。
3. **调用**：批了以后，能写脚本的 agent 直接调 REST；不能执行代码的客户端（纯聊天）用常驻集里那一个通用的「调用」工具，按名字和参数转调同一个领域动作。两种调法命中同一条授予、同一次判定、同一张审计表。

通用「调用」工具守三条界限：

- **只转调领域动作**：只认已声明的领域动作（`<域>.<动词>`），不能拿它去调常驻集以外的普通 MCP 工具，也不能调市场的内部路由；
- **按目标动作判定和留痕**：判定、授予命中、审计行都记成被转调的那个动作，渠道标 `mcp-invoke`，不记成「调用」这个工具本身；
- **决定类仍走人的确认门**：目标动作是决定类的，照 [11](11-identity-and-permission.md) 不变量 2 只能生成待人确认的提议，不能因为经了「调用」就直接执行。

这样，领域再多，`tools/list` 也只有常驻那一小组；领域能力的定义只在用到时，经「详情」那一步进上下文。

## 四、授权

| 谁 | 能做什么 |
|---|---|
| 属主 | 指定每个领域（团队）的负责人；限定负责人能批哪些动作（一个上限）；随时收回 |
| 团队负责人（即 [15](15-two-layer-org.md) 的领域负责人） | 在属主给的上限之内，批或驳本领域的申请 |
| 申请的会话（agent） | 提申请、等结果；批了就用 |
| 系统管理员 | 照旧不看业务内容，只管账号、登记和配置；不因为是管理员就能批领域申请 |

规则：

1. **有团队就有负责人。** 每个领域（团队）至少一个负责人，由属主指定。批接入申请是负责人的一项权力，落成负责人授予（[领域第 1 步规格](../domains-step1.md)里的 `area-lead`）里的一个动作，范围是「域:<领域>」，带属主给的上限（允许批的动作清单），只有属主能起草和放行。**上限默认不含决定类动作**；要含，属主在上限里逐条列出。
2. **授予分两层，负责人只批会话那一层。**

   | 层 | 落在哪 | 谁批 | 内容 |
   |---|---|---|---|
   | 会话授予（接入） | 这个 agent 会话上（现在是 `mcp_sessions` 的授予，以后随 L18 一起并进授予表） | 团队负责人，在属主给的上限之内 | 这个会话可以调本领域的哪些动作 |
   | 账户授予（领域） | 账户（人）上，是 [11](11-identity-and-permission.md) 授予表里的一条，范围「域:<领域>」 | 照 [领域第 1 步规格](../domains-step1.md)按角色分档：带决定类的只有属主放行；不带的照现有两人制 | 这个人在本领域能做什么 |

   负责人**不**批账户授予，所以不会和「带决定类的授予只有属主放行」冲突。

3. **跟随账户，没有时效。** 每个 agent 会话都挂在一个账户（人）名下（怎么挂见第七节第 3 步）。会话最终能用的权限 = 会话授予 ∩ 账户授予，也就是 [11](11-identity-and-permission.md) 的不变量 3：「席位的权限不超过它的责任人」。授予本身不设到期时间。下面三种情况，会话的权限立即跟着收回：
   - 收回这个账户在该领域的授予；
   - 停用这个账户；
   - 收回负责人这条授予：之前已经批出去的保留，只是以后不能再批。
4. **不能自己批自己。** 负责人不能批自己账户名下会话的申请（[11](11-identity-and-permission.md) 不变量 4 的审批回避）。遇到这种情况，由属主或同一领域的另一位负责人批。
5. **批的是动作，不是通道。** 批下来的是「某领域的某些动作」，MCP 和 REST 都认这一条授予，不分别批。
6. **批了立即生效。** 批准后，下一次「目录」就标成已批，可以调用；`tools/list` 不变（领域能力不进 `tools/list`）。
7. **`access_request` 的应答分两种说法**，免得 agent 批了以后在 `tools/list` 里找不到就以为没批：
   - 申请的是常驻集里的普通工具（过渡期的按工具授予）：「批了以后会出现在工具列表里」；
   - 申请的是领域动作：「批了以后不会出现在工具列表里；到目录里看状态，用 REST 或通用『调用』去调」。
8. **和数据视图授予的关系**：数据视图的「会话 × 台 × 工具」授予（`bench_mcp_grants`，L18）是**台这个对象**上的授予，照旧由台的管理层批，不经团队负责人；团队负责人批的是**领域**范围的接入。两者范围不同、互不代替。以后 L18 并进授予表时，两者落在同一张表，按范围区分。

## 五、MCP 和 REST 是同一套规矩

- **认人一样**：同一个会话令牌，同一个账户。
- **判定一样**：都经 [11](11-identity-and-permission.md) 的判定，命中同一条授予。REST 没有更宽的入口。
- **审计一样**：同一张审计表，只标注渠道是 `mcp` 还是 `rest`。
- **工具不随领域增加**（属主 11-18）：MCP 只暴露常驻集。领域能力批下来以后，能写脚本的 agent 走 REST；纯聊天客户端经常驻的通用「调用」工具转调，不为领域单独注册 MCP 工具。
- **大结果给引用**：超过阈值的结果，不论走哪条通道，都只回地址、sha 和摘要。取的时候用同一个令牌，也再判定一次。

## 六、公开仓和私域的边界

本仓是公开的（见 `CONTRIBUTING.md` 红线）。所以：

- **本仓只做机制**：领域能力怎么声明、目录和详情怎么分层、申请和审批、判定、审计、按引用返回。
- **私域的具体能力不进本仓**：哪个领域有哪些动作、接口长什么样、说明怎么写，都由部署方放在仓外，经扩展目录挂进来。扩展声明自己的动作（`<域>.<动词>`，带类别）、OpenAPI 片段和说明页，核心不改。
- **按需加载进来的说明一律当数据处理。** 能力说明虽然以技能的形式发布，但对 agent 来说是参考资料。扩展的说明文字可能被人写进诱导模型的话，所以它只用来展示，不能当成给 agent 的指令。目录里的说明要限长、去掉控制字符。

## 七、实现顺序

> **进展（2026-11-20 核对 main）**：第 0 步的上下文占用已量（#871，结果见 [16a](16a-step0-measurement.md)；调用频次还在等生产数据）；第 1 步（#872）、第 5 步（#876）已合入。第 2～4 步还没有合入，前置的第 15 篇第 1 步在做（#877 已合，后续 PR 进行中）。下表是原计划，没改。

| 步 | 做什么 | 前置 | 验收 |
|---|---|---|---|
| 0 | **先量**：按真实会话量一下 `tools/list` 和 `access_info` 各占多少 token，再从审计里统计各工具 30 天的调用次数 | 无 | 一张表：现在多大、常驻集该放哪些 |
| 1 | **目录瘦身**：`access_info` 默认只给索引，参数表按名字单独取 | 无（不碰身份） | 默认应答缩到第 0 步的一小部分；老客户端带参数照样拿得到全量（过渡期） |
| 2 | **负责人批接入**：批接入作为负责人的动作，支持「域:<领域>」范围加上限；申请带领域；审批回避 | 第 15 篇第 1 步（领域对象、按领域授予、`area-lead`） | 对抗组：跨领域批被拒；超上限批被拒；批自己被拒；系统管理员批被拒 |
| 3 | **跟随账户**：先补「会话归属」——main 上的 `mcp_sessions` 现在没有归属的人（只有 `created_by` 文本），要加一列归属主体并在建会话时必填；再让会话的有效权限等于会话授予和账户授予的交集 | 第 2 步 | 撤账户授予、停用账户以后，同一会话的 MCP 和 REST 调用立即都被拒；没有归属的会话申请领域能力被拒 |
| 4 | **领域能力声明**：扩展声明动作、OpenAPI 片段和说明页；目录和详情从声明里来 | 第 2 步 | 用一个合成领域的扩展跑通：申请、审批、在目录里看见、经 REST 和通用「调用」两种方式调用、撤销；全程 `tools/list` 不变 |
| 5 | **大结果给引用**：超过阈值的结果改回地址、sha 和摘要 | 无 | 两条通道一致；拿引用去取时要再判定 |

**第 2 步的启用边界（属主 2026-11-24 定）：** 先交付领域接入的申请、上限、审批与审计。验收使用合成可信归属。实际会话在第 3 步接入可信责任人之前一律拒绝领域申请。会话创建者和席位令牌仅供原路径使用，不证明责任人。

- 同一个 `access_request` 接受领域形式 `{area, actions, reason}`。旧 `{tools, reason}` 申请照旧处理，两种形式分开。用 `access_info {ref: "area-<编号>"}` 读本会话申请状态。
- 登录的属主以 `PUT /api/areas/:id/access-limits/:grantId` 为本领域生效的负责人授予设置动作清单。动作逐条列出，空清单收回后续批准额度。上限随授权版本留痕；已有批准保留。
- 登录的属主或本领域持接入审批授予的负责人以 `GET /api/areas/:id/access-requests` 查看待批项，在 `/:requestId/approve` 或 `/:requestId/reject` 作决定。写入时重核启用身份和领域。批准还须重核当前上限和会话归属，批准人不得是该会话的责任人。按整条申请作决定。会话接入的决定单独留痕，沿用原按工具审批处理存量。
- 接入批准仅记会话层的审批结果。第 3 步补账户交集，第 4 步才按领域的可调用声明开放实际调用。批准项不出现在 `tools/list`。

- 第 3 步里老会话怎么处理：
  - **老的命名会话**：不自动认主。管理员按 `created_by` 等线索提出归属、由那个人在市场页面确认后才绑定；没绑之前照旧只按自己的会话授予，不能申请领域能力。
  - **席位换出来的会话**（node，见 [seat-token-exchange](../seat-token-exchange.md)）：归属取席位的责任人，按名册现查。
  - **system 会话**（市场自己用的）：不挂账户，也不接领域能力。
- 第 0、1、5 步不碰身份，可以先做。
- 第 2、3 步是身份与权限类改动：排在第五次上线之后，跟在身份线后面（同一时间只开一条），按 `CONTRIBUTING.md` 红线先验后合。
- 每一步新加的安全行为，都要补一行启动自检。

  1. 能力接入：目录 → 详情 → 申请 → 调用；REST 怎么调、纯聊天客户端怎么用通用「调用」；大结果的引用怎么取。随第 1、5 步一起出。
     - 2026-11-20 更新：已随 #903 出，即 `skills/wm-capability-access`；例子由 `scripts/skill-capability-access-examples-test.mjs` 在隔离实例上逐个真跑，接进了 CI。
  2. 公共区：怎么读；任务的写授权怎么拿、怎么写产出物、版本和来源怎么记；下游怎么取。随公共区落地一起出（[15](15-two-layer-org.md) 第九节）。
- **私域技能**：每个领域的能力说明由扩展提供，登记进技能市场。本仓不放任何私域技能。
- **技能暂不限制读**（属主 11-18）：沿用现在的规矩，`skills_list`、`skill_search`、`skill_read` 对任何已认证会话免授权，私域技能也一样，谁都能读。读得到说明不等于能调用：领域能力本身仍要申请、经团队负责人批。所以技能里只写「能做什么、怎么调」，不放业务数据、账号、地址和凭据；以后要收紧，再给技能加领域归属和可见范围。
- **防漂移**：照 `wm-data-views` 的做法，技能里的例子由脚本用真实实现逐个跑、接进 CI，代码改了技能没跟上就红。
- 常驻集里留 `skill_search` 和 `skill_read`，让 agent 随时能找到、读到这些技能。

## 七之二、和公共区的关系

- 本篇管的是 agent 接入某个领域的**能力**：授权跟随账户，没有时效。
- [15](15-two-layer-org.md) 第九节的公共区管的是领域之间交换**产出**：读不限制，算在常驻集里；写跟随任务，按任务批次单次授权，用完就没了。两者不要混用：不能拿接入授权去写公共区，也不能拿任务的写授权去调私域能力。

## 八、不做

- **服务端工具搜索**（只常驻一个 `search_tools`）：主流客户端已经自己做延迟加载了，服务端再做一层收益小。量过第 0 步，确有需要再说。
- **授权时效**：属主定的是没有时效，授予跟着账户走。（[11](11-identity-and-permission.md) 里访客「必须有期限」的规矩照旧，那是另一回事。）
- **按工具一个个批**：改成按领域的动作批；老的按工具授予在过渡期照旧生效。
