# 09 · 约束系统

> 阶段 0 草稿。[08](08-technical-route.md) 定了路线，这一篇定**怎么让构建不偏离路线**。三个取向：能跑的检查优先于写出来的规定；存量只减不增；闸少而硬。

## 一、要约束的是什么

约束分两层。**系统层**管部件之间：哪些部件、哪个版本、哪版契约，以及跨域的七条规范（见 [10](10-boundary-and-norms.md)）；它的清单在私有的系统定义仓。**部件层**管一个仓的内部。本篇写的是部件层在市场这个仓的落法，同一个形状可以搬到别的部件仓。

写这个系统的不是一个坐在一起的团队，而是多个并行的 agent 会话：

- 每个会话的上下文有限，读不完 5278 行的入口文件，也看不到别的会话正在改什么。
- 会话各有各的记忆，仓库之外的约定对新会话不存在。仓库里今天没有 `AGENTS.md`。
- 评审查的是对不对、安不安全（见 PR 模板），不查结构。
- 属主不读 diff。

结果就是 [08 第二节](08-technical-route.md#二现状实测)的那些数字：每个 PR 单看都对，加起来路线就散了。所以约束要落在三个地方——会话开工时读得到，合并之前机器拦得住，属主不读代码也看得懂走势。

已有的约束保留，并沿用它们的办法：

| 已有 | 作用在 | 办法 |
|---|---|---|
| 启动安全自检 | 运行时 | 必过的行不过，入口一律不放行；新增安全行为必须加自检行 |
| 安全面 PR 的对抗组 | 评审 | 至少 5 例，先红后绿 |
| 非法配置拒绝启动 | 运行时 | 每个变量各自校验 |
| server 语法检查、web 类型检查、设计 token 冒烟、93 个测试脚本 | CI | |
| 本地封闭验证器（175 条判据，见 README「开发验证器」） | 本地证据 | 判一次提交的行为、数据、安全；不在 CI |
| 隐私闸、环境变量对照、内联样式计数 | 脚本 | 三个脚本都在仓库里，**都没接进 CI** |

缺的是结构这一层：没有任何东西在看路由写在哪、SQL 写在哪、表建在哪、配置怎么读。

## 二、原则

1. **判据要能执行。** 路线上的每个决定配一个检查和一个数字。查不了的明说是约定，不冒充约束。
2. **棘轮：存量只减不增。** 现有的欠账冻结成基线，以后只许变小；新写的代码直接按目标来。不做一次性的大重构。
3. **先有落点，再开闸。** 不许往旧地方写，前提是新地方已经建好。落点没建好的检查只计数。
4. **分三档，档位看存量。** 红线：违反就失败，用在没有存量欠账的事上。预算：比基线多就失败，用在有存量的事上。计数：只报告。哪条进哪档由属主裁定（设计标准的检查已裁定为只计数）。
5. **豁免要留名。** 写进清单：哪条规则、哪一项、理由、谁批的、到哪天。过期自动变红。
6. **检查自己也要过检查。** 每个检查配一个故意违规的样本，先红后绿，证明它真拦得住。
7. **闸少，而且不自设。** 三道闸、十几个检查，全是零依赖的 node 脚本。闸只拦清单里写明的；改清单走 PR，由属主裁定。

## 三、结构：一份清单、三道闸、一张体检表

```
                 tech-route.json（路线清单：规则、档位、基线、豁免）
                                    │
        ┌───────────────────────────┼───────────────────────────┐
        ▼                           ▼                           ▼
  闸一 写的时候               闸二 合并之前               闸三 运行的时候
  AGENTS.md                   CI：tech-route-check         启动：自检、路由登记齐全、配置校验
  会话开工先读                红线 / 预算 / 计数           每次请求：身份 → 判定 → 留痕
        │                           │                           │
        └───────────────────────────┼───────────────────────────┘
                                    ▼
                  体检表（一屏：现在 / 基线 / 目标 / 变化）
```

### 路线清单

`tech-route.json` 放仓库根，和 `DESIGN.md` 并列。它是 08 的机器可读版：改路线就是改它，PR 里看得见。

```json
{
  "rules": [
    {
      "id": "sql-outside-services",
      "tier": "budget",
      "what": "SQL 只写在 server/src/services/ 与 db.ts",
      "baseline": { "server/src/index.ts": 81, "server/src/sop-run-access.ts": 36 },
      "target": 0
    }
  ],
  "waivers": [
    { "rule": "schema-only-in-db", "item": "server/src/example.ts", "reason": "…", "by": "属主", "until": "2026-12-31" }
  ]
}
```

- **基线按文件记。** 并行的 PR 各改各的文件，不会抢同一个数字。不在基线里的文件，基线就是 0——所以「存量只减」和「新文件不许有」是同一条规则。
- **PR 只要求「实际 ≤ 基线」。** 数字变小以后，由合并方在 main 上跑一条命令收紧基线。棘轮只在 main 上转，PR 之间不用为改基线打架。

### 闸一：写的时候

仓库根放一份 `AGENTS.md`（60 行以内），`CLAUDE.md` 只写一行引用它。骨架：

```markdown
路线：市场是组织中心的入口，只做呈现、判定、留痕、索引；地基是 Cordis。详见 docs/productization/08。

红线（CI 会拦）：
- 公开仓不写业务内容、内网细节、凭证。
- 新表只建在 server/src/db.ts；SQL 只写在领域服务里。
- 新路由、定时器、配置都写在插件里，不进 index.ts，不自造注册机制。
- 核心不直接引用身份的具体实现。
- 新增运行时依赖、不进 CI 的测试脚本，先登记到 tech-route.json。

新东西放哪：一个域一个插件，带自己的服务、路由、定时器和 Config；A2A 走外部节点插件。

提交前自检：node scripts/tech-route-check.mjs
```

主流宿主在会话开工时会读仓库根的这份文件，读不读由宿主决定。所以它只是第一道闸，真正拦得住的是第二道。它的另一个作用是给红线一个出处：协作规范只认写在仓库里的红线。

### 闸二：合并之前

CI 加一步 `tech-route-check`：一条命令跑完全部检查，红线和预算超了就失败，计数只进报告，体检表写进这次 CI 的摘要页。PR 模板加一行，贴体检表里的「变化」。

### 闸三：运行的时候

- **启动**：现有的安全自检；插件的依赖和 Config 由上下文校验，路由没声明访问类别和动作就注册不上。
- **每次请求**：身份 → 判定 → 留痕（[08 第五节](08-technical-route.md#五入口的三步身份--判定--留痕)）。
- **部署**：照旧钉提交；部署单附上那个提交的体检表。

### 体检表

属主不读 diff，读这一张。main 上一份全量，每个 PR 一行变化：

```
本次变化：路由 +2（已登记）· 表 +0 · 环境变量 +1（已写进 README）· index.ts 路由 139 → 131 · 类型错误 85 → 83
```

全量就是下一节那张表。等驾驶舱 v2 有了面板机制，可以把它做成一块面板（P2）。

## 五、同一套办法，管两类对象

约束有两个对象：**写系统的**（并行的开发会话）和**跑在系统里的**（AI 席位、自产台、外部节点）。两边是同一个形状：

| | 写系统的 | 跑在系统里的 |
|---|---|---|
| 规则 | 路线清单、`AGENTS.md` | 角色与授予（[11](11-identity-and-permission.md)） |
| 卡口 | CI 检查、启动自检 | 四个入口面的身份 → 判定 |
| 例外找人 | 豁免写进清单，属主裁定，带期限 | `ask` 进「关注」，人来答复 |
| 留痕 | git 历史、体检表的走势 | 留痕总账 |
| 自证 | 故意违规的样本，先红后绿 | 对抗组；新旧判定并行比对 |
| 先观察再生效 | 只报告 → 预算 → 红线 | held、observe → auto（[06](06-a2a-superagent-fusion.md)） |

产品的主张是「AI 干活，人可控」，而构建这个产品的过程本身就是 AI 在干活。约束系统是这个主张在自己身上的第一次验证；在这里磨出来的做法——规则读得出来、例外留名、先观察再生效——就是产品里授权与审批的做法。

## 七、不做，以及考虑过的备选

不做：

- 不上规则引擎、依赖图工具、monorepo 构建工具。
- 不强制提交钩子。各会话的环境不一样，CI 才是共同的必经之路。
- 设计标准不做成门禁（已裁定只计数）。
- 不加新的审批层。
- 不建第二条验证流水线。本地验证器继续判行为、数据、安全的证据；结构检查在 CI。两者不重叠。

| 备选 | 为什么不选 |
|---|---|
| 只靠评审 | 评审者也是上下文有限的会话；结构问题要跨多个 PR 才看得出来 |
| 成套的 lint 或架构检查工具 | 要先引入依赖和一套配置；要查的十几条用正则和计数就够，自己写的更贴路线 |
| 一次性重构到位 | 回归风险大，并行开发要停；重构完没有约束，还会再散 |
| 只写规范文档 | 就是今天的状态 |

## 附录：量法

范围是 2026-11-10 的 main。server 指 `server/src` 下的 `.ts`；web 指 `web/src` 下的 `.ts`、`.tsx`、`.css`；脚本指 `scripts/` 顶层的 `.mjs`、`.js`、`.py`、`.sh`。全部是正则计数，不解析语法，注释和字符串里的命中也算——数字用来看走势，不用来逐条定性。第 1 批落地后，以 `scripts/tech-route-check.mjs` 为准。

| 项 | 怎么数 |
|---|---|
| 路由 | `app`、`router`、`r`、`api` 上的 `.get(`、`.post(`、`.put(`、`.patch(`、`.delete(`，且第一个参数是路径。`app.use` 挂载的不计 |
| SQL 调用点 | `db.prepare(` 与 `db.exec(`。按文件分四区：`services/`、`db.ts`、`index.ts`、其他 |
| 表 | `CREATE TABLE`（含 `VIRTUAL`）后面的表名，去重；改表数 `ALTER TABLE` |
| 留痕类表 | 表名含 `audit`、`ledger`，或以 `_log`、`_events`、`_calls` 结尾。按名字匹配，含领域自己的事件表 |
| 环境变量 | `process.env.NAME` 的出现次数，以及去重后的名字数；`process.env[` 另计为动态读取（3 处） |
| 周期任务 | `setInterval(` |
| 守卫 | `index.ts` 里名字以 `Guard`、`Gate`、`Ok` 结尾的函数或常量定义。别的模块里的判定没有机械量法，正文只给量级 |
| 身份实现的引用 | 直接引用 `odoo-*` 模块、且自己不是 `odoo-*` 的 server 文件 |
| 类型错误 | 用临时配置跑 `tsc --noEmit`。宽松：`strict: false` 加 `erasableSyntaxOnly`；严格：`strict: true`。两者都跳过库文件检查 |
| 测试类脚本 | 文件名以 `-test`、`-smoke`、`-mutation` 结尾。在 CI：`ci.yml` 里出现 `scripts/<文件名>`。有命令：出现在某个 `package.json`。被调用：文件名出现在 `scripts/` 下另一个可执行脚本里。其余算没有执行入口 |
| README 目录 | server 文件的文件名没在 `README.md` 里出现 |
| 前端取数 | `web/src` 里的 `fetch(`，不含 `apiFetch(` |
| 内联样式、色值 | 仓库已有的 `scripts/inline-style-count.mjs` |
| 环境变量文档 | 仓库已有的 `scripts/docs-env-face.mjs`。它的口径比上面宽（含解构、别名、助手函数），所以它数出的变量比 46 个多 |
