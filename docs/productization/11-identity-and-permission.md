# 11 · 身份与权限

> 阶段 0 草稿。属主 2026-11-10 定了三件事：身份的实现从核心剥离；登录只留一层，用飞书直连；用户、角色、权限自己管。本篇是设计骨架，细节在落地时补。

## 一、定下来的

1. **登录只留一层。** 认人交给一个登录提供方，系统不存密码、不做登录页。默认的提供方是飞书。
2. **用户、角色、权限自己管。** 账号目录、角色、授予、判定都在组织中心，不依赖外部系统的权限模型。
3. **身份的实现是插件。** 核心只认一份契约；换提供方就是换一个插件。

[08](08-technical-route.md) 的不做清单相应改了一条：从「不自建账号体系」改为「不自建登录」。

## 二、现状（2026-11-10，main）

| 关注点 | 今天 |
|---|---|
| 认人 | 靠浏览器带来的外部系统会话，每次请求现查。从对方只读了一位信息：是不是管理员 |
| 实现的位置 | 4 个专属文件、409 行，写在核心里，被另外 8 个核心文件直接引用；连扩展接口用的「查看者」类型也从其中导出 |
| 管理身份 | 管理口令，或外部系统的管理员 |
| 席位 | MCP 会话：一个名字、一枚令牌、一份工具清单（33 个工具：16 读、10 写、7 管理） |
| 外部节点 | A2A 绑定表，按调用方精确匹配 |
| 按台访问 | 三档：全员、管理员、点名（评审中，未合并） |
| 合起来 | 同一个席位在网络、MCP、绑定表里是三个互不相认的身份；人的权限除了「管理员」没有别的层次 |

## 三、模型

```
登录提供方 ──→ 主体 ──→ 授予 ──→ 角色（一组权限）
（只认人，可换）  （人、席位、台、   （范围、期限、
                 系统、外部节点）   授予人、理由）
                     │
                     ▼
                   判定 ──→ 允许 ／ 先问人 ／ 拒绝        全部留痕
```

### 1. 登录

提供方插件只做三件事：

| 契约 | 说明 |
|---|---|
| 认人 | 把一次登录认成一个外部身份（提供方 + 对方的用户标识） |
| 目录（可选） | 列出人和部门，用来预先建主体 |
| 失效通知 | 人离职或被停用时告诉中心 |

默认提供方飞书的要点：

- 认人用 union_id。
- 浏览器里走标准的授权码登录；在飞书客户端里打开时免登。
- 离职要即时失效：主体是自己的，停用是本地动作，立刻生效。要解决的是「多快知道」——订阅通讯录变更事件，再加每天一次对账。
- 审批卡片是人的另一个入口：卡片上点同意或驳回，回调按同一个 union_id 认回主体。
- 应用密钥放凭据库，不放环境变量。

其余规则：

- 登录之后用市场自己的会话，有绝对期限；主体一停用，会话立即失效。
- 会话记着它是经哪条外部身份建立的。那条身份被解绑或改绑，由它建立的会话立即失效——查验时核对一次，解绑时注销一次，两道都要。
- 只认本组织的外部身份。按企业邮箱自动绑定只有在限定了租户时才能打开，没限定就拒绝启动；租户不符的身份不自动绑定，只进待对接清单。
- 席位不走登录。它的凭据由中心签发，绑定在席位主体上。
- 管理口令只留作本机应急，全程留痕，不是日常身份。

### 2. 主体

一张表，五类：

| 类别 | 标识 | 怎么来 | 责任人 |
|---|---|---|---|
| 人 | `user:<名>` | 首次登录自动建，或从目录导入 | — |
| 席位 | `seat:<名>` | 管理员登记 | 必须有 |
| 台 | `app:<slug>` | 上架时建 | 上架的人 |
| 系统 | `system:<名>` | 声明 | 必须有 |
| 外部节点 | `node:<团队>` | 管理员绑定 | 必须有 |

- **外部身份挂在主体上**，一个主体可以有多个：登录账号、A2A 句柄、MCP 会话。[10](10-boundary-and-norms.md) 的第 3 条规范（网络身份只证明来源，权限只来自绑定）就落在这里。
- **停用一个主体，所有入口立即失效。**
- 代码和历史留痕里现在用的 `odoo:<登录名>` 是旧的写法，迁移时原样对应到主体，不改历史记录。

### 3. 角色与权限

- **权限 = 动作 + 范围。**
  - 动作由提供它的插件自己声明，写成 `<域>.<动词>`，并标明类别：读、写、决定、管理。新长出来的台、SOP、工具自带动作，核心不用改。
  - 范围四种：全部；某个授权域；某个资源（台、SOP、工具）；仅本人创建的。
- **角色两层。**

| 层 | 角色 | 说明 |
|---|---|---|
| 平台内置 | 属主 | 唯一能放行管理员级授予 |
| 平台内置 | 管理员 | 管主体、普通授予、台与工具的配置 |
| 平台内置 | 成员 | 首次登录的默认角色（可配置成访客）：看市场，打开对自己开放的台，发起申请 |
| 平台内置 | 访客 | 只读被点名开放的内容 |
| 组织角色 | 每家企业自己声明 | 声明文件，随版本管理 |

组织角色的声明长这样：

```yaml
roles:
  - id: 采购专员
    permissions:
      - {actions: [app-data.read, app-data.submit, sop.run], scope: "域:采购"}
  - id: 采购负责人
    includes: [采购专员]
    permissions:
      - {actions: [proposal.decide], scope: "域:采购"}
```

角色和权限是**声明**，人写人审，改动走提交。谁有哪个角色是**数据**，见下一节。

### 4. 授予

一条授予记六样：主体、角色、范围、期限、授予人、理由。

- 状态：草稿 → 待核 → 生效 → 撤销或过期。到期自动失效。
- 不能给自己授予。
- 管理员级的授予只有属主能放行。
- **授予只有一处。** 别的部件不各建一套；需要时读中心签发的断言（见 [10](10-boundary-and-norms.md) 的入口）。

### 5. 判定

每个入口上的每次请求都过判定，按这个顺序：

1. 主体停用，或外部身份没绑定：拒绝。
2. 动作没有声明：拒绝。
3. 动作类别是「决定」，而主体不是人：转成提议，先问人。
4. 有生效的授予覆盖这个动作和范围：允许。主体是席位时，还要求它的责任人也有这项权限。
5. 没有授予，但动作声明了可以申请：先问人。
6. 其余：拒绝。

「先问人」按审批策略找人：单签、依次或会签，由声明决定；问题进「关注」，也可以发成审批卡片。

在 Cordis 里，判定是一个事件，策略是监听它的插件：内置的监听器做上面六步，企业特有的规则（比如按金额加一级审批）是另外的插件，不改核心。

## 四、五条不变量

| # | 不变量 | 怎么查 |
|---|---|---|
| 1 | 默认拒绝写和决定 | 没有任何授予的主体，对每个写动作都被拒 |
| 2 | 决定类动作只认人，席位最多只能提议 | 席位直接调用决定类动作，得到的是一条待审的提议 |
| 3 | 席位的权限不超过它的责任人 | 撤掉责任人的角色，名下席位的同一动作同时被拒 |
| 4 | 审批回避：审批人不能是提议人，各级不能是同一个人 | 提议人审批自己的提议被拒；同一个人连批两级被拒 |
| 5 | 每次非只读的判定都留痕 | 记录里有：谁、凭哪个外部身份、动作、对象、结果、命中的规则和授予 |

## 五、现有的几套怎么并进来

| 现在 | 并进来之后 |
|---|---|
| 外部会话里的「是不是管理员」 | 管理员角色 |
| 管理口令 | 本机应急 |
| 按台访问三档 | 台这个范围上的授予 |
| MCP 会话的工具清单 | 席位主体的角色；动作类别照旧 |
| A2A 绑定表 | 主体上的外部身份 |
| SOP 运行读授权、统一待办读授权 | 资源范围上的带期限授予 |
| 观测层的授权域与审批策略（不在公开仓） | 组织角色，和「先问人」的审批策略 |

## 六、过渡

| 步 | 做什么 | 性质 |
|---|---|---|
| 1 | 定身份契约；冻结存量：核心里直接引用身份实现的文件数（现在 8 个）只减不增 | 不改运行时 |
| 2 | 身份做成服务，现有实现包成它后面的一个插件（已完成，#484） | 对外行为不变 |
| 3 | 建主体表和外部身份；现有标识原样迁入 | 新增 |
| 4 | 加飞书登录插件，与旧的并存；每个人挂上飞书身份，对不上的由管理员手工对一次 | 两种登录都能用 |
| 5 | 角色、授予、判定上线：新旧判定并行比对，零差异后切换 | 安全面，附对抗组 |
| 6 | 全员对上之后，关掉旧的登录插件 | 只留一层 |

第 2 步做完之后，核心不再直接引用登录的具体实现。还剩两处写死在核心里：会话 cookie 的名字，和登录中继的开关。换登录方式时这两处仍要改，放在第 4 步一并处理。

风险：

- **把人锁在外面**：第 4 步期间两种登录并存；应急口令始终可用。
- **权限切换改错**：第 5 步不重写现有判定的结论，先并行比对；五条不变量各配对抗样本。
- **离职失效有延迟**：事件订阅之外加每日对账；会话有绝对期限。

## 七、不做

- 不存密码，不做登录页。
- 不上策略语言和规则引擎。
- 不做按属性的细粒度授权。
- 不做每个台一个角色，用范围解决。
- 稳定状态下不同时接两个登录提供方（过渡期除外）。

## 附：阶段六的落地规格

阶段五合并之后照这份做。分四个 PR，每个都由独立会话验收；前三个不改变任何人能做什么。

### PR 6a：动作登记

- 每个域模块注册路由时报上动作名和类别，写法是 `<域>.<动词>`，类别四种：读、写、决定、管理。MCP 工具沿用已有的类别（read 对读，write 对写，admin 对管理）。
- 没报动作的路由注册不上。存量路由分批补，补完之前按文件记预算，只减不增。
- 交付一份动作清单的快照，放在 `surfaces/` 下，和路由快照一样随代码提交。
- 验收：对外行为逐条不变；动作清单与路由快照能一一对上，没有哪条写路由缺动作。

### PR 6b：角色声明与授予

- 角色声明是仓库外的一个文件，位置由配置给出；仓库里只带四个平台内置角色和一份示例。启动时校验：引用了不存在的动作、角色循环包含，都拒绝启动。
- 授予是一张表：主体、角色、范围、期限、授予人、理由、状态。状态只有草稿、待核、生效、撤销、过期五种，只能按这个顺序走。
- 规则写进库的约束和服务里，不靠页面：不能给自己授予；管理员级的授予只有属主能放行；不是人的主体没有责任人就不能被授予；到期自动失效。
- 管理接口：列出、起草、提交、放行、撤销。每一步留痕。
- 这个 PR 只建结构，不接判定，所以不改变任何人能做什么。
- 验收：五种状态之外的迁移全部被拒；自授、越级放行、无责任人的授予各有对抗例，先红后绿。

### PR 6c：判定事件与并行比对

- 一个判定事件，内置监听器照第三节第 5 小节的六步判。现有的守卫不动。
- 每个请求两边都算：现有守卫的结论照旧生效；新判定的结论只记下来，和旧结论比。不一致的记一行，带上请求、主体、动作、两边的结论。
- 迁移：现有的管理员对成管理员角色；按台访问的点名名单对成台范围上的授予；MCP 会话的工具清单对成席位主体上的授予。迁移可以重复跑，结果相同。
- 验收：把现有的测试和录制回放全跑一遍，不一致为零；故意把一条授予撤掉，比对里必须出现对应的不一致。

### PR 6d：切换

> 属主 2026-11-11：飞书相关的延后，不成为阻塞。所以这一步拆成两半：判定切换在旧登录上先做；「关掉旧登录」等飞书登录真机验过、启用之后另排。

- 不一致连续为零之后，判定结论改由新判定给出，旧守卫逐个下线。一次只切一个域，切完观察再切下一个。
- 留痕总账上线：所有非允许的判定、所有被允许的写操作各记一行。
- 「先问人」接到现有的变更申请和 MCP 权限申请上，不新建第三套。
- 验收：五条不变量各有对抗例并通过；切换前后，每个域的录制回放零差异。

### 两处先按建议做、标为待确认的

- **组织角色的初始集合**：用观测层现成的授权域。写在仓库外的声明文件里，不进公开仓。
- **观测层现有的授权怎么并**：它改成读中心签发的断言，断言里带主体和角色；它自己那套授权状态机退役。这要它那边一起改，所以 6d 只做到中心这一侧，两边对接另排。
