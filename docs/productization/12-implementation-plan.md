## 三、执行规则

1. **一个阶段一次验收，由并行的独立会话来验。** 阶段做完，实现方逐条给出验收判据的结果；另起一个不带实现方上下文的会话，自己跑、自己看，在 PR 上逐条写 PASS 或 FAIL。全过且 CI 全绿就合并。不等属主（属主 2026-11-10）。
2. **PR 小而单一。** 搬路由时，小域可以合在一个 PR 里：最多 3 个域、合计不超过 12 条路由，每个域单独一个提交、单独一份录制；大的或纠缠的域一个 PR 一个。实现方开 PR，独立的验收会话验过之后合并。
3. **先红后绿。** 每个新检查、每条不变量都先给出会失败的样本，再给出通过的结果。安全面的 PR 照旧附对抗组。
4. **对外行为不变的阶段，用比对来证明。** 路由快照和录制回放必须零差异，不靠「看起来一样」。
5. **公开仓不写业务。** 涉及私有细节的，写在私有仓。
6. **生产部署不在本计划内。** 需要部署时，照旧由协同开发发部署单。

### 实现下来和设计不一样的地方（阶段一、二）

独立验收逼出来的改动，设计文档 [09](09-constraint-system.md) 里没有写到：

- **清单自己也要被检查。** 清单缺失、缺规则、档位写错、豁免五项不全，体检直接报错，不往下跑。否则合并冲突解坏一次，一条规则就无声地关掉了。
- **CI 用严格模式。** 预算档和红线档的检查量不出来（依赖没装、被调的脚本不在）也算失败。
- **清单被放宽要看得见。** 体检表末尾有一行「清单变化（相对 main）」：档位调低、基线调大、加豁免，都列出来。
- **类型检查带空值检查。** 不带的话，TypeScript 会把正确的写法判成错误。
- **快照取「前端已构建」的形态。** 有没有构建，路由会差三层；没构建时临时放一个占位目录。
- **检查项是 19 个**（设计里是 17 个）：分层拆成两项，加了「README 里已失效的路径」和「快照」。

还没做、已知的限度：体检只在 PR 上跑，main 上没有；表结构快照不含约束和视图，MCP 工具快照不含入参；隐私检查只认通用模式；量法是正则，换个写法能绕开。

### 阶段四做完之后还剩什么

核心不再直接引用登录的具体实现，体检里 `identity-in-core` 是 0，已转成预算档。但这不等于完全解耦：核心里还写死着会话 cookie 的名字和登录中继的开关，换登录方式时这两处仍要改。留给阶段五（主体与飞书登录）一并处理。

验收方用同一串请求对照了改前改后两个实例（约 1.2 万条请求，19 种部署方式），零差异；又把 6 万多种身份来源的回答喂给改前改后的身份服务，认人的结果零差异。
