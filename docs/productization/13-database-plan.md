# 13 · 数据库：轻量部署用 SQLite，企业部署用 PostgreSQL

> 属主 2026-11-11：「后面肯定会换成 pg，你做好规划吧，sqlite 轻量部署，pg 是企业级生产部署。」本篇是规划，不是已经开工的东西。什么时候开工、每一步怎么算过，写在第五节。

## 一、定下来的

- 两种部署形态长期并存，同一份代码：
  - **轻量**：SQLite，一个文件，不依赖任何外部服务。给试用、单机、开发和测试用。
  - **企业**：PostgreSQL。给正式生产用。
- 换的只是「数据放在哪」，对外行为不变。验收办法和搬路由时一样：同一组请求，两种库上的应答必须逐字节相同。

## 二、现状（2026-11-11，main）

市场只有一个 SQLite 文件，通过 Node 自带的同步接口直接访问，全局只有一个连接对象。

| 量什么 | 数 |
|---|---|
| 直接写 SQL 的地方 | 470 处，分布在 38 个文件 |
| 其中不在领域服务里的 | 158 处（已经有一项检查在管，只减不增） |
| 表 / 触发器 / 索引 | 65 / 29 / 45 |
| 在 SQL 里取当前时间 | 117 处 |
| SQLite 特有的写法 | 「插入或替换、插入或忽略」15 处；读表结构的指令 31 处；取刚插入那行的编号 37 处；JSON 函数 7 处 |
| 事务和保存点 | 55 处 |
| 直接打开库文件的测试脚本 | 106 个 |

除了主库，数据目录里还有：流程运行的热状态（可选的 Redis）、台页面和技能的文件内容、凭据库、新旧权限判定的比对记录。这些不在本篇范围内，第六节单独说。

## 三、难在哪

按工作量从大到小：

1. **同步改异步。** 现在的接口是同步的：一句 SQL 写完，下一行就拿到结果。PostgreSQL 的访问是异步的。所以不是换一个驱动，而是 470 处调用和它们上面的每一层函数都要改成异步。这是最大的一块，也是唯一绕不过去的一块。
2. **事务要显式传下去。** 同步的时候，一个事务里的代码天然不会被别的请求插进来。异步之后，谁在哪个事务里要明说。今天有不少「在别人的事务里接着做一步」的写法（比如事项服务在事件来源的事务里用保存点记一笔），这些要有一个统一的办法把事务带过去。
3. **表结构和迁移。** 现在的迁移是启动时「看一眼有没有这一列，没有就加」，靠的是 SQLite 特有的指令。要改成带版本号的迁移，两种库各一份。29 个触发器（只增不改的日志、一经写入不能改的字段）要在 PostgreSQL 里各重写一遍。
4. **方言。** 取当前时间、插入或替换、自增编号、JSON 函数，两边写法不同。其中「在 SQL 里取当前时间」今天已经咬过我们两次：时间只精确到秒，同一秒内的先后分不清。把时间改成由代码生成、作为参数传进去，既解决方言，也解决这个老问题。
5. **测试脚本。** 106 个脚本自己打开库文件造数据、查结果。它们要改成经过同一个入口，才能在两种库上跑。

## 四、做法

### 1. 数据访问做成一个服务

和这次产品化别的部分一样，落在 Cordis 上：数据访问是一个服务，两种库各是它后面的一个实现。领域服务只和这个服务说话，不知道后面是哪种库。接口是异步的；SQLite 的实现把同步的调用包成异步的。

事务用「当前事务跟着调用链走」的办法：进入事务时登记，链上任何一层取到的都是同一个事务，不用每个函数多传一个参数。保存点照旧支持。

### 2. SQL 还是手写，只用两边都认的写法

不引入对象映射。理由：这个仓库的纪律一直是「SQL 原文搬运」，录制回放钉的也是 SQL 的实际行为；换成对象映射等于把 470 处查询重写一遍，没法用比对来证明没变。

做法是定一个「两边都认」的子集，每个方言差异收进数据访问服务里的一个小函数（当前时间、插入或更新、取新行编号、JSON 取值），领域服务里不出现任何一边特有的写法。

开工前留一个决定：Cordis 生态里有自己的数据库层，支持这两种库。它的好处是和整套架构同源，代价就是上面说的重写。开工的第一步是拿一个小的域用两种办法各做一遍，按「改动量、能不能用回放证明没变、两种库上的性能」比过再定。本篇先按手写 SQL 来排。

### 3. 表结构只写一处，两种库各生成一份

表、索引、约束用一种中立的写法登记一次，生成两种库的建表语句。触发器没法自动转，两边各写，但成对登记、成对测试：每个触发器在两种库上都要有「该拦的拦住了」的例子。

迁移改成带版本号的：库里记着自己在第几版，启动时按顺序补到最新。现有的「缺列就加」整体算作第一版。

### 4. 两种库上跑同一套测试

CI 里每个 PR 的测试和录制回放在两种库上各跑一遍，应答逐字节相同才算过。这一条从数据访问服务落地的第一天就开，之后每搬一个域，它在两种库上都得是绿的。

### 5. 搬数据的工具

从 SQLite 导到 PostgreSQL：逐表搬、逐表核对行数和内容摘要，可以重复跑，中断了能接着跑。上线前照这次升级预演的办法演一遍：拿生产的库形态搬过去，起得来、回放零差异、能回退。

## 五、顺序和验收

排在阶段三（路由进插件）和阶段六（权限切换）之后。原因：现在入口文件和各域还在大规模搬动，同时把每一层改成异步，两边会一直撞。

| 步 | 做什么 | 怎么算过 | 现在能不能做 |
|---|---|---|---|
| 0 | 止住新增：体检加两项计数——SQL 里取当前时间的处数、SQLite 特有写法的处数，只减不增；新代码的时间一律由代码生成 | 体检表里多这两行；新 PR 不让它们变大 | 能，不和别的线冲突 |
| 1 | SQL 全部收进领域服务（158 → 0） | 已有的那项检查归零 | 在做，随阶段三 |
| 2 | 选型：一个小域用两种办法各做一遍 | 一份对比，定下用哪种 | 阶段三做完后 |
| 3 | 数据访问服务，SQLite 实现；事务随调用链走 | 对外零差异；全局那个连接对象不再被直接引用 | 第 2 步之后 |
| 4 | 按域改异步，一个域一个 PR | 每个 PR：快照零差异、回放零差异 | 第 3 步之后 |
| 5 | 带版本号的迁移；表结构登记一处 | 生产形态的库升上来，表结构和数据与今天的办法逐项相同 | 可以和第 4 步并行 |
| 6 | PostgreSQL 实现；CI 两种库都跑 | 全部测试和回放在两种库上应答逐字节相同 | 第 4 步过半就可以开始 |
| 7 | 测试脚本不再直接开库 | 直接开库的脚本数归零 | 随第 4 步 |
| 8 | 搬数据的工具和预演 | 生产形态的库搬过去，起得来、回放零差异、能回退 | 第 6 步之后 |
| 9 | 生产切到 PostgreSQL | 由属主定时间；切换单、回滚点、回读 | 第 8 步之后 |

## 六、不在这一篇里的

- **多实例和高可用。** 换成 PostgreSQL 之后数据库本身可以做主备，但市场进程里还有只存在内存里的东西（缓存、定时任务、限频计数、签名的已用记录）。要起多个副本，得先把这些列出来、逐个挪走。这是换库之后的下一件事，另写。
- **别的存储。** 文件内容、凭据库、流程运行的热状态、比对记录，各自的去处另定。换库这件事不动它们。
- **席位和节点一侧。** 它们的数据归它们自己。
