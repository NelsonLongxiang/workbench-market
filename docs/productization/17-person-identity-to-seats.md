# 17 · 让席位认得出是哪个人：人在市场确认，市场签名送达

> 状态：**设计稿**（2026-11-19 起草）。只写设计，不含代码。进度以 [12](12-implementation-plan.md) 第零节为准。

## 属主原话（2026-11-19）

1. 「对于业务同事方面，这个我们后续会做一个 dsh 插件 与工作台协同的 登录认证插件，来识别 人的身份注入，可以先标记下来，做调查和分析」
2. 「当然，我们优先考虑避免新增一个插件，避免增加运维成本」

## 要点

1. **问题。** 有人在席位（DSH 实例）的网页界面里打了一句话，席位和下游都分不出这是哪个人打的。
   - DSH 的网页界面只有一把进程令牌，打开界面的人一律算「这台机器的主人」。
   - 所以凡是要认人的事，比如生产批准、业务确认，现在只能靠消息里的文字标签声明，代码分辨不出真假。
2. **结论：不加插件。**
   - 人只在市场里表态：用已登录的市场页面打字确认。
   - 市场把「谁、确认了什么、确认编号」签好名，经 A2A 送给席位。
   - 席位和下游核对签名后，按这条记录认人。
   - DSH 一个插件都不用加，用的都是已经在跑的部件：市场的登录、[一人一助理](../assistant-phase1.md)的「待你确认」门、A2A 的 OriginClaim 签名。
3. **插件只是后备。** 只有「人必须直接在 DSH 界面里打字、又要认出是谁」时才需要。DSH 已经留好了扩展点，见第四节，但这要多一个部件去装、去升级、去排障，所以不优先。
4. **它补的是哪一块。** 第 11 篇的不变量 2「决定类动作只认人」，在市场里是成立的；但决定一旦要送到席位上执行，就只剩一句文字。本篇让这句话带上市场核过的「人」。

## 一、问题

### 1. 现在是怎么认人的

| 在哪里表态 | 怎么认人 | 能分辨真假吗 |
|---|---|---|
| 市场页面 | 站内账号登录，主体表，授予现查 | 能 |
| 市场 MCP | 会话令牌，落在席位或助理的主体上 | 能认出席位，认不出人 |
| DSH 网页界面 | 一把进程令牌，换成签名 cookie，一律是 `owner` | 不能 |
| 别人代打字（贴标签「代某某输入」） | 只看文字标签 | 不能 |

### 2. 为什么这是个问题

- 有些事必须由某个具体的人点头，比如生产切换的批准、业务数据的确认。点头之后，执行它的是席位。
- 席位手上只有一句文字。这句话是本人打的、别人代打的，还是 AI 照着格式拼的，代码分不出来。
- 现在的补法是：在文字里加固定标签，执行的人工判断真假，并把文字的 SHA 记下来，防止被改、防止重复使用。完整性有了，**发件人是谁仍然没有**。

## 二、调查

### 1. DSH 现状（按 DSH 公开文档和类型定义）

- **网页界面的认证**：一把进程令牌。带令牌的地址换一次签名 cookie，之后这个浏览器就是这台宿主的 `owner`。没有「哪个人」的概念。
- **主体**：`PrincipalMap` 里只内置了 `owner` 一种（「拥有这台宿主的本地用户」）。
- **身份包**：只有一个匿名的安装编号，给遥测和反馈用，故意不识别人。
- **已经留好的扩展点**：
  - `PrincipalMap` 可以用声明合并加新的主体种类；
  - `ctx.connection.createPeer({ principal })` 由进程内代码定下一个连接的身份，任何网络字段都改不了；
  - 远程访问可以给非 `owner` 的主体登记授权策略；
  - **用户消息的来源记录 `{ kind: "user", rpcId, principal? }` 已经有可选的 `principal` 字段，并且写进会话日志。**
- **结论**：DSH 认人要靠进程内代码，也就是插件；但「消息带上是谁发的」这个位置已经在了。

### 2. 市场现状

- **认人**：站内账号，加上登录提供方插件（`server/src/login-providers/`）；认人统一走身份服务，停用立即生效。
- **本人确认**：[一人一助理第 1 期](../assistant-phase1.md)已经设计了「待你确认」门：
  - 服务端生成描述，5 分钟时限，只能用一次；
  - 只认本人的市场会话，确认时按本人当下的权限重判；
  - 能防住客户端钩子，也能防住拿着令牌自己当客户端的 AI。
  - 它还是设计，排在 Odoo 下线和登录持久化之后。
- **对外签名**：市场经 A2A 出站时，用本节点密钥签 OriginClaim（绑定形式 v2）；接收方只认绑定形式、根路径名片、origin 和团队配置的市场 origin 完全一致的事件（[06](06-a2a-superagent-fusion.md)）。
- **席位到市场**：席位用宿主签名换 1 小时的 MCP 令牌（[seat-token-exchange](../seat-token-exchange.md)）。它是按宿主隔离的，不按团队隔离（存量差异 L22）；但这是席位到市场的方向，和本篇讲的市场到席位无关。

## 三、方案：人在市场确认，市场签名送达

### 1. 流程

```
人（已登录市场）
  │ ① 在市场页面看到服务端生成的描述，打字确认
  ▼
市场：确认记录（谁、哪条事项、描述摘要、编号、时间、只能用一次）
  │ ② 生成「人的表态」事件，用市场节点密钥签 OriginClaim，经 A2A 投给席位
  ▼
席位（DSH + a2a-net）
  │ ③ 核对：OriginClaim 绑定形式、市场 origin、名片；事件里的确认编号没用过
  ▼
席位按「某人已确认某事」执行；需要时经 MCP 回读这条确认记录
```

### 2. 「人的表态」事件里带什么

| 字段 | 说明 |
|---|---|
| `confirm_id` | 市场确认记录的编号，只能用一次 |
| `principal` | 表态的人的主体标识，例如 `user:…` |
| `subject` | 表态针对的对象：事项编号，或者一份待批准文本的摘要 |
| `description_sha256` | 人看到的那段描述的摘要。描述由服务端生成，人改不了，AI 也写不进去 |
| `answer` | `confirm` 或 `decline` |
| `confirmed_at`、`expires_at` | 确认时间和有效期 |

- 原文不随事件送出。席位要看原文，经 MCP 读确认记录，读的时候照常判权限。
- 事件走 A2A 现有的幂等和回执，不另造通道。

### 3. 席位怎么核

- 只认 OriginClaim 绑定形式、origin 是团队配置的市场 origin 的事件。这是 a2a-net 本来就在做的，不用加代码。
- 按 `confirm_id` 去重，用过就拒。执行侧要有一本只追加的台账。
- 要核内容时，经 MCP 读确认记录，比对 `description_sha256` 和要执行的东西是否一致。

### 4. 为什么不加插件也够

- 认人在市场里已经能做到，加一个 DSH 插件只是把同一件事在另一个地方再做一遍。
- 签名送达用的是 a2a-net 已有的签名和核对，节点上本来就装着它。
- 按「人只用市场」的定位，人本来就不该在 DSH 界面里替别人表态。

## 四、后备：什么时候才需要 DSH 插件

- **只在一种情况下需要**：人必须直接在 DSH 网页界面里打字，比如在席位上排障时顺手批一件事，又要席位认出是谁。
- **做法**：
  - 插件在 DSH 里登记一个新主体种类，比如 `market-person`；
  - 浏览器先在市场登录，拿到市场签发的短期「人」凭证；
  - 插件核对凭证以后，用 `createPeer` 建一个带这个主体的连接；
  - 这个连接发出的每条消息，来源记录里的 `principal` 就是这个人，并写进会话日志。
- **代价**：多一个部件要安装、随 DSH 升级、排障，这就是属主说的运维成本。
- **动手前要先问 DSH 上游**：现在浏览器的 cookie 只对应 `owner`，自定义主体能不能经浏览器这条路建连接。

## 五、威胁和限度

| 情形 | 结果 |
|---|---|
| 有人照着格式手打一条「某某已批准」 | 席位拒收：没有市场签名，或者 `confirm_id` 查不到 |
| AI 拿着自己的令牌去确认 | 拒：确认只认本人的市场浏览器会话，令牌提交不了确认 |
| 同一条确认被重放 | 拒：`confirm_id` 只能用一次，市场和席位两边都记 |
| 描述被人或 AI 改写 | 摘要对不上，席位拒收 |
| **本人的电脑被拿下** | **防不住**：本机代码能读出浏览器会话。这和一人一助理第 1 期接受的风险相同（不加通行密钥） |
| **市场节点密钥泄露** | **防不住**：能伪造任何人的表态。密钥保管照 A2A 现行规矩；以后可以加轮换和吊销 |

## 六、和其他文档的关系

- [11](11-identity-and-permission.md)：不变量 2「决定类动作只认人」从市场延伸到席位；不变量 5「每次判定都留痕」照旧，确认记录就是留痕。
- [15](15-two-layer-org.md)：人触发、定规范，AI 按领域执行。本篇就是「人触发」怎么可信地送到 AI 那边。
- [16](16-progressive-capability-access.md)：负责人审批领域能力的申请，也可以走同一个确认门，审批结果送到席位时带上负责人的主体。
- [一人一助理第 1 期](../assistant-phase1.md)：「待你确认」门是本篇的前置，本篇只是在它后面加「送达席位」这一步。

## 七、步骤

| 步 | 做什么 | 前置 |
|---|---|---|
| 0 | 本篇 | 无 |
| 1 | 一人一助理第 1 期的「待你确认」门落地 | Odoo 下线、登录持久化 |
| 2 | 确认记录可以对外引用：加「人的表态」事件，经 A2A 签名投递；MCP 能按编号读确认记录 | 步 1 |
| 3 | 席位侧的约定：只认市场签名的表态事件，按 `confirm_id` 去重；写进 a2a-net 的接收说明，不改 DSH | 步 2 |
| 4 | 第一个用户：生产切换的批准改走这条路，替掉文字标签声明 | 步 3 |

## 八、待确认

1. 步 4 的第一个用户，定为生产切换的批准是否合适。

## 不做

- 不在 DSH 里另做一套账号或登录。
- 不让席位自己认人：席位只核市场签名。
- 不把确认原文放进 A2A 事件。
- 不为认人新增网络通道或身份服务。
