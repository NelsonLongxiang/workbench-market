# 17 · 让席位认得出是哪个人：人在市场确认，席位到市场核销

> 状态：**设计稿**（2026-11-19 起草，同日按 #864 评审意见改）。只写设计，不含代码。进度以 [12](12-implementation-plan.md) 第零节为准。

## 属主原话（2026-11-19）

1. 「对于业务同事方面，这个我们后续会做一个 dsh 插件 与工作台协同的 登录认证插件，来识别 人的身份注入，可以先标记下来，做调查和分析」
2. 「当然，我们优先考虑避免新增一个插件，避免增加运维成本」

## 要点

1. **问题。** 有人在席位（DSH 实例）的网页界面里打了一句话，席位和下游都分不出这是哪个人打的。
   - DSH 的网页界面只有一把进程令牌，打开界面的人一律算「这台机器的主人」。
   - 所以凡是要认人的事，比如生产批准、业务确认，现在只能靠消息里的文字标签声明，代码分辨不出真假。
2. **结论：不加插件。**
   - 人只在市场里表态：用已登录的市场页面打字确认。
   - 席位动手之前，用自己的 MCP 令牌到市场**核销**这条确认。只能用一次、只给指定的席位、过期作废，这几条都由**市场的代码**保证，不靠席位上的 AI 照说明去做。
   - A2A 事件只用来通知席位「有一条确认在等你」，不作为凭据。
   - DSH 一个插件都不用加，用的都是已经在跑的部件：市场的登录和判定、市场 MCP、A2A 投递。
3. **插件只是后备。** 只有「人必须直接在 DSH 界面里打字、又要认出是谁」时才需要。DSH 已经留好了扩展点，见第四节，但这要多一个部件去装、去升级、去排障，所以不优先。
4. **它补的是哪一块。** 第 11 篇的不变量 2「决定类动作只认人」，在市场里是成立的；但决定一旦要送到席位上执行，就只剩一句文字。本篇让席位执行前能从市场拿到核过的「人」。

## 一、问题

### 1. 现在是怎么认人的

| 在哪里表态 | 怎么认人 | 能分辨真假吗 |
|---|---|---|
| 市场页面 | 站内账号登录，主体表，授予现查 | 能 |
| 市场 MCP | 会话令牌，落在席位或助理的主体上 | 能认出席位，认不出人 |
| DSH 网页界面 | 一把进程令牌，换成签名 cookie，一律是 `owner` | 不能 |
| 别人代打字（贴标签「代某某输入」） | 只看文字标签 | 不能 |

### 2. 为什么这是个问题

- 有些事必须由某个具体的人点头，比如生产切换的批准、业务数据的确认。点头之后，执行它的是席位。
- 席位手上只有一句文字。这句话是本人打的、别人代打的，还是 AI 照着格式拼的，代码分不出来。
- 现在的补法是：在文字里加固定标签，执行的人工判断真假，并把文字的 SHA 记下来，防止被改、防止重复使用。完整性有了，**发件人是谁仍然没有**。

## 二、调查

### 1. DSH 现状（按 DSH 上游的文档、类型定义和源码）

- **网页界面的认证**：一把进程令牌。带令牌的地址换一次签名 cookie，之后这个浏览器就是这台宿主的 `owner`。没有「哪个人」的概念。
- **主体**：`PrincipalMap` 里只内置了 `owner` 一种（「拥有这台宿主的本地用户」）。
- **身份包**：DSH 的 `packages/identity`（`anonymous-user-id`）只给每个 harness home 一个匿名编号，供遥测、反馈和模型请求标记来源，故意不识别人。
- **已经留好的扩展点**：
  - `PrincipalMap` 可以用声明合并加新的主体种类；
  - `ctx.connection.createPeer({ principal })` 由进程内代码定下一个连接的身份，任何网络字段都改不了；
  - 远程访问可以给非 `owner` 的主体登记授权策略；
  - **用户消息的来源记录 `{ kind: "user", rpcId, principal? }` 已经有可选的 `principal` 字段，并且写进会话日志。**
- **结论**：DSH 认人要靠进程内代码，也就是插件；但「消息带上是谁发的」这个位置已经在了。

### 2. A2A 签名能证明什么

- OriginClaim 有两种绑定形式，见上游 `src/origin-claim.ts`：
  - **v2（`X-A2A-Caller-Sig2`）**：签的是调用方、时间、audience、方法和路径，**不签正文**；
  - **v3（`X-A2A-Caller-Sig3`）**：在 v2 的基础上把正文摘要也签进去。接收方一旦看到 Sig3，就要求正文逐字节对得上，不许降级。
- 接收方现在**不强制要求 Sig3**：没有 Sig3 时，验过 Sig2 就算来源可信。所以正文里写的「谁、确认了什么」，单靠 A2A 签名证明不了。
- audience 只到宿主一级。同一台宿主上的几个团队都能验过同一条消息，签名本身分不出是发给哪个团队、哪个席位的。
- **结论**：A2A 签名适合用来证明「这是市场发的通知」，不适合当「某人确认了某事」的凭据。凭据要放在市场这边，由席位来取。

### 3. 市场现状

- **认人**：站内账号，加上登录提供方插件（`server/src/login-providers/`）；认人统一走身份服务，停用立即生效。
- **本人确认**：[一人一助理第 1 期](../assistant-phase1.md)设计了「待你确认」门：
  - 服务端生成描述，5 分钟时限，只能用一次；
  - 只认本人的市场会话，确认时按本人当下的权限重判；
  - 能防住客户端钩子，也能防住拿着令牌自己当客户端的 AI。
  - 它还是设计，排在 Odoo 下线和登录持久化之后。
- **席位到市场**：席位用宿主签名换 1 小时的 MCP 令牌（[seat-token-exchange](../seat-token-exchange.md)），令牌落在席位的主体上。它按宿主隔离，不按团队隔离（存量差异 L22），这一点在第五节的威胁表里单列。

## 三、方案：人在市场确认，席位到市场核销

### 1. 流程

```
发起方（AI 席位、助理或人）
  │ ① 在市场提出「需要某人确认某事，交给某个席位执行」
  ▼
市场：建一条送达类确认（发起方、确认人、对象、目标席位、描述、有效期）
  │ ② 确认人在市场页面看到服务端生成的描述，打字确认
  │    市场按确认人当下的授予重判，并做审批回避
  ▼
市场：确认记录变成「已确认、待核销」
  │ ③ 经 A2A 通知目标席位（只是通知，不是凭据）
  ▼
目标席位
  │ ④ 动手之前，用自己的 MCP 令牌调用「核销」
  ▼
市场：原子核销（席位对得上、没过期、没用过）→ 返回确认人、对象、描述摘要
  │
  ▼
席位按「某人已确认某事」执行；核销失败就不执行
```

### 2. 送达类确认

和第 1 期的 `assistant_confirms` 分开，另起一种「送达类」确认。原因是两者的发起方、用途和生命周期都不一样：

- 第 1 期的确认，发起方只能是本人的助理，确认之后由市场自己执行；
- 送达类确认，发起方可以是 AI 席位、助理或人，确认之后由**另一个席位**执行，中间还隔着一次投递和核销。

送达类确认记录里带：

| 字段 | 说明 |
|---|---|
| `id` | 确认编号 |
| `initiator` | 发起方的主体：席位、助理或人 |
| `confirmer` | 被请求确认的人的主体，必须是 `kind = 'person'` |
| `action` | 要确认的决定类动作，按第 11 篇登记在判定里 |
| `subject` | 对象：事项编号，或者一份待批准文本的摘要 |
| `target` | 目标席位的主体。只有这个主体能核销、能读 |
| `description`、`description_sha256` | 服务端生成的描述及其摘要。发起方写的自由文本只能作为引用出现，并标明出处 |
| `status` | `pending` → `confirmed` → `consumed`；另有 `declined`、`expired`、`cancelled` |
| `confirm_expires_at` | 等人确认的时限，默认 5 分钟，和第 1 期一致 |
| `consume_expires_at` | 确认之后等席位核销的时限，必须长过 A2A 投递的重试周期，见第 3 小节 |
| `consumed_at`、`consumed_by` | 核销的时间和核销的主体 |

### 3. 规则

- **谁能发起**：发起方要有「提议这个动作」的授予。席位最多只能提议，这本来就是不变量 2。
- **谁能确认**：
  - 确认人在确认的那一刻，必须有这个决定类动作的授予，判定现查，不缓存；
  - **审批回避（不变量 4）**：确认人不能是发起方本人，也不能是发起方助理的责任人；同一件事要两级确认时，两级不能是同一个人。
- **送给谁**：
  - `target` 必须写明到席位，不能只写到宿主或团队；
  - 核销和读取都只认 `target` 这个主体的 MCP 会话，其他席位，包括同一台宿主上的，一律拒绝。
- **只用一次**：核销是一条原子更新（`status = 'confirmed' AND consume_expires_at > now AND target = 调用方` → `consumed`）。两个并发核销只有一个能成功。
- **时限**：
  - 等确认用 `confirm_expires_at`，默认 5 分钟；
  - 等核销用 `consume_expires_at`，默认取 A2A 投递最长重试周期的两倍，可以按动作另定，但不能短于重试周期。否则重试送到的时候，确认已经作废了。
- **留痕**：建、确认、拒绝、过期、核销，每一步都记一行，记下谁、哪个外部身份、结果（不变量 5）。

### 4. MCP 和 A2A 各做什么

- **MCP（凭据）**：
  - `confirm_consume(id)`：原子核销，返回确认人、动作、对象、描述摘要、确认时间；
  - `confirm_get(id)`：只读，只有 `target` 能读。
  - 两个都是常驻集以外的能力，按[第 16 篇](16-progressive-capability-access.md)的渐进开放方式申请。
- **A2A（通知）**：
  - 投给目标席位一条「有确认待核销」的事件，里面只放 `id` 和目标席位，不放原文；
  - 出站带 Sig3，把正文签进去；
  - 即使接收方只验了 Sig2，或者事件被伪造，最坏的结果也只是席位来核销一次、失败，不会被当成批准。

### 5. 为什么不加插件也够

- 认人和判定在市场里已经能做到，加一个 DSH 插件只是把同一件事在另一个地方再做一遍。
- 只用一次、只给指定席位、过期作废，都由市场代码在核销时保证，席位侧不需要新代码，只需要一条「动手前先核销」的约定。
- 按「人只用市场」的定位，人本来就不该在 DSH 界面里替别人表态。

## 四、后备：什么时候才需要 DSH 插件

- **只在一种情况下需要**：人必须直接在 DSH 网页界面里打字，比如在席位上排障时顺手批一件事，又要席位认出是谁。
- **做法**：
  - 插件在 DSH 里登记一个新主体种类，比如 `market-person`；
  - 浏览器先在市场登录，拿到市场签发的短期「人」凭证；
  - 插件核对凭证以后，用 `createPeer` 建一个带这个主体的连接；
  - 这个连接发出的每条消息，来源记录里的 `principal` 就是这个人，并写进会话日志。
- **代价**：多一个部件要安装、随 DSH 升级、排障，这就是属主说的运维成本。
- **动手前要先问 DSH 上游**：现在浏览器的 cookie 只对应 `owner`，自定义主体能不能经浏览器这条路建连接。

## 五、威胁和限度

| 情形 | 结果 |
|---|---|
| 有人照着格式手打一条「某某已批准」 | 席位去核销时，市场查不到这个编号，或者状态不是「已确认」，核销失败，不执行 |
| 伪造或重放 A2A 通知 | 同上：通知不是凭据，核销那一步失败 |
| AI 拿着自己的令牌去确认 | 拒：确认只认本人的市场浏览器会话，令牌提交不了确认 |
| 同一条确认被用两次 | 拒：核销是原子的，第二次失败 |
| 别的席位（包括同一台宿主上的）来核销或读取 | 拒：只认 `target` 的 MCP 主体 |
| 发起方自己去确认，或者两级确认是同一个人 | 拒：审批回避 |
| 确认人在确认之前被停用，或者被撤了授予 | 拒：确认时现查 |
| **AI 写的待批文本拿给人看** | 描述由服务端从库里的数据生成；发起方写的自由文本只能作为引用，标明是谁写的。仍然要人自己读懂再确认，这一条防不了人看漏 |
| **同一台宿主上的几个团队共用一把签名键（L22）** | 持有这把键的人能换出这台宿主上任一席位的 MCP 令牌，也就能以那个席位的身份来核销。范围是一台宿主，跨宿主做不到。等上游给团队发了自己的键，这一条随 L22 一起关掉 |
| **席位核销之后不照做，或者多做** | 防不住：核销只证明「这个人确认过这件事」，席位执行时要不要照做，靠席位自己的规矩和执行留痕。生产类动作另有执行侧的门 |
| **本人的电脑被拿下** | **防不住**：本机代码能读出浏览器会话。这和一人一助理第 1 期接受的风险相同（不加通行密钥） |
| **市场被拿下** | **防不住**：凭据就在市场 |

## 七、步骤

| 步 | 做什么 | 前置 |
|---|---|---|
| 0 | 本篇 | 无 |
| 1 | 一人一助理第 1 期的「待你确认」门落地 | Odoo 下线、登录持久化 |
| 2 | 送达类确认：表、状态机、确认页面、审批回避、留痕 | 步 1 |
| 3 | MCP `confirm_consume`、`confirm_get`；A2A 通知（带 Sig3） | 步 2 |
| 4 | 席位侧的约定：执行需要人点头的动作之前，先核销，核销失败就不执行；写进席位的说明 | 步 3 |
| 5 | 第一个用户：生产切换的批准改走这条路，替掉文字标签声明 | 步 4 |
| 后备 | 真有「必须在 DSH 界面里认人」的需求时，再按第四节评估插件 | 属主另批 |
| 另议 | 如果以后要让席位只凭 A2A 事件就能认人，不再回市场核销，就要改 a2a-net 接收侧：这类事件强制要求 Sig3，并且把 audience 收窄到团队或席位。这要和上游商量 | 上游 |

身份类改动按 CONTRIBUTING 的「先验后合」走：对抗组先红后绿，作者以外的会话验收。

## 八、待确认

1. 步 5 的第一个用户，定为生产切换的批准是否合适。
2. `consume_expires_at` 的默认值：按 A2A 最长重试周期的两倍，还是按动作另定。

## 不做

- 不在 DSH 里另做一套账号或登录。
- 不让席位自己认人：凭据在市场，席位只来核销。
- 不把 A2A 通知当凭据，不把确认原文放进 A2A 事件。
- 不为认人新增网络通道或身份服务。
