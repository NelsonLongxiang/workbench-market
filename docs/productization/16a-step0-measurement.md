# 16a · 渐进开放第 0 步：先量

状态：上下文占用已量（2026-11-20，main `8dd8b231`）；调用频次等生产数据。常驻集名单交统筹裁定。

依据是 [16](16-progressive-capability-access.md) 第七节第 0 步：「按真实会话量一下 `tools/list` 和 `access_info` 各占多少 token，再从审计里统计各工具 30 天的调用次数」。

## 一、怎么量

| 量什么 | 用什么 | 数据从哪来 |
|---|---|---|
| 上下文占用 | `scripts/mcp-context-size.mjs` | 本机隔离实例（`NODE_ENV=test`，和 main 同一份代码）。建两种会话：全授（能按会话授予的工具全给），缺省（新会话，授予为空）。原样抓 `initialize`、`tools/list`、`access_info` 的应答 |
| 调用频次 | `scripts/mcp-usage-report.mjs` | 生产库的审计表 `mcp_calls`，最近 30 天。以只读方式打开库文件，只输出聚合数字 |

- **token 是估算**：中日韩字符按 1 个/字，其余按 4 字符/个。只用来比大小、看占比，不当计费依据。
- **本机量不到的部分**：生产实例聚合的上游工具（名字带「前缀__」的）本机没有，要另加。
- **频次报告输出什么**：只输出工具名、方法名、渠道和计数。会话只分「命名会话 / 席位换来的会话」两类计数，不出会话名、参数、错误原文、令牌摘要，可以原样贴进本篇。

## 二、上下文占用（本机实测）

目录共 49 项，其中数据视图 15 项（要限定到台授予）。

| 会话 | 应答 | 字节 | 估算 token |
|---|---|---|---|
| 缺省（新会话） | `initialize` | 816 | 231 |
| | `tools/list`（5 个免授权工具） | 4,001 | 1,193 |
| | `access_info` | 128,345 | **34,101** |
| 全授 | `tools/list`（34 个工具） | 24,418 | 7,044 |
| | `access_info` | 128,975 | **34,258** |

拆开 `access_info`（全授会话）：

| 同一份应答 | 估算 token | 占原来的 |
|---|---|---|
| 原样（现在的输出） | 34,258 | 100% |
| 不缩进 | 17,734 | 52% |
| 不缩进，再去掉每项的参数表 | 6,091 | 18% |

**看到的三件事：**

1. **最大的一块是 `access_info`，不是 `tools/list`。** 新会话按指引「缺工具先调 `access_info`」，一调就是约 3.4 万 token，是 `tools/list` 的近 30 倍。和 16 篇第一节的判断一致。
2. **所有工具结果都按缩进 2 格输出。** 应答的 `text` 是 `JSON.stringify(结果, null, 2)`，单这一项就让 `access_info` 大了将近一倍，其他工具的结果也一样。改成不缩进，内容一字不差，token 约省一半。**建议**：作为第 1 步的一部分，或者单开一个小 PR。改了以后，`mcp` 域的录制回放要重录（应答的文字变了，结构不变）。
3. **参数表集中在少数几个工具上。** `view_put` 一个工具的参数表就有约 6,400 token，占全部参数表的一半以上；其次是 `dataset_query`（约 780）、`dataset_define`（约 390）。第 1 步把参数表挪到「详情」以后，这几个只在真要用时才进上下文。

**第 1 步的目标**：`access_info` 默认只给目录索引（名称、一行说明、类别、批没批），不带参数表，不缩进。说明压成一行之后，估计在 2,000 token 以内（不到原来的 6%）。参数表按名字单独取。老客户端带参数照样能拿到全量。

## 三、调用频次（待生产数据）

要在生产机上，对生产库跑一次：

```bash
node scripts/mcp-usage-report.mjs --db <生产库文件> --days 30 --json mcp-usage-30d.json
```

- 只读，不停服务；输出就是本节要贴的表。
- 由统筹安排有生产访问的会话代跑。

拿到之后补三张表：

1. 各工具 30 天的调用次数、占比、累计占比、失败数、会话数、活跃天数、渠道分布；
2. 每个会话用过几个不同的工具；
3. 各工具被多少个会话授予过。

## 四、常驻集候选（频次验证前的初稿）

常驻集就是 `tools/list` 里出现的全部（属主 11-18：只暴露常用的）。分两档：

**机制必需（不看频次）**：

| 工具 | 为什么 |
|---|---|
| `access_info` | 目录；第 1 步之后兼做「详情」（按名字取参数表） |
| `access_request` | 申请 |
| `skill_search`、`skill_read` | 能力说明以技能的形式发布，要随时能找到、读到（16 篇第七节之一） |
| 通用「调用」 | 纯聊天客户端转调领域动作（16 篇第三节）。第 4 步才有 |
| 读公共区 | 15 篇第九节。公共区落地才有 |

**高频工具（按频次定，下面只是按用途列的待验证候选）**：

| 候选 | 理由 | 等什么数据 |
|---|---|---|
| `workbench_list` | 找台的入口，大多数任务的第一步 | 调用次数、会话覆盖面 |
| `sop_run_list`、`sop_run_get` | 跑 SOP 的会话每次都要读 | 同上 |
| `app_data_list` | 读台数据 | 同上 |
| `skills_list` | 现在免授权；和 `skill_search` 有重叠，可能不必常驻 | 两者各自的调用量 |

**判定规则（建议）**：

- 30 天调用量累计占到 80% 的那几个工具，并且使用会话数不少于全部活跃会话的一半，才进常驻集。
- 其余一律走「目录 → 详情 → 调用」。
- 有一种例外要单列出来交裁定：调用多，但只有一两个会话在用。这种更适合给那几个会话单独授予，而不是常驻。
