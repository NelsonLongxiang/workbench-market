# 19 · 报告：人机协同的协议

> 属主 2026-11-21 的方向：
>
> 「报告能做的事情有非常多……它是人机协同的一个基础，是标准化的协议。数据视图只是为了便于大家实现自己想要的看板，但报告模板才是真正的核心所在。」
>
> 「业务在看到一个报告之后，他可以写自己的评价，可以认可与反驳。同一件事物，它的角度和看法是有多个维度的。那么每个维度有一个报告模板，这势必就变得非常重要，是人机协调友好良好的基础。」
>
> 属主同时指出，这是 RSI（递归自我改进）的一根支柱。RSI 的定义见 agent-atelier 的设计讨论稿「RSI：我们的理解」和「化的边界、度量与验证」（2026-11-21，在该仓分支 `docs/experience-theory-design` 上，还没进 main）。
>
> **状态：设计讨论稿。** 本篇只写模型、规则草案和实现顺序，不写代码。第八节是属主已定的；其余各节里标「草案」的，以第八节为准。

## 一、要点

1. **报告是交付物，不是看板。** 数据视图回答「现在数是多少」；报告回答「从这个角度看，我的判断是什么，你同不同意」。前者方便人看数，后者让人和 AI 能就同一件事对话。
2. **报告模板是协议。** 它规定一个维度要回答什么、用什么数据、结论怎么写、人怎么回应。AI 按它产出，人按它回应，双方说的是同一种话。
3. **一件事有多个维度，一个维度一份模板。** 同一件事从几个角度各出一份报告，并排看；维度之间的矛盾本身就是信号。
4. **回应是一等公民。** 人对报告里的每一条论断认可、反驳或补充，并写理由。回应只追加，不改报告。
5. **模板就是判据，归属主和领域负责人。** 写报告的 AI 不能顺手改模板让自己好过关。按回应修订模板的决定外置（第五节）。

## 二、报告在 RSI 回路里的位置

RSI 的回路是：体 → 行 → 验 → 意 → 化 → 复体，验要有「他」，并且**验放在交付物上**（不跟踪 AI 自己说改没改，看交付物经不经得住外部检验）。报告就是这个回路在人和 AI 之间落地的那张纸：

| RSI 环节 | 报告里对应什么 |
|---|---|
| 行 | AI（或人）按模板产出一份报告，这就是交付物 |
| 验、他 | 业务看完后逐条认可、反驳、补充。这是人对交付物的外部检验，不是 AI 的自我报告 |
| 位 | 一个维度就是一个看问题的位置；同一个模型站在不同的位置，看到的东西不同 |
| 言、规 | 模板是协议：这个维度该回答什么、什么算一条合格的论断 |
| 意 | 反驳带着理由，是归因的原料：错在数据、口径、推理，还是这个维度本身就问错了 |
| 化、复体 | 按一份模板积累的认可和反驳，修订模板或 AI 的做法；修订发新版本，成为下一轮的起点 |

这也补上了[第 01 篇](01-product-definition.md)核心闭环里「人审 → 沉淀」这一段：现在的人审是事项上一次「验收 / 退回」（[02](02-concept-model.md) 第三节 ready → done 或 progress），只有一个结果、没有理由的结构。报告把它细到每一条论断，理由可以累积、统计，才能沉淀。

## 三、对象

| 对象 | 是什么 | 谁写 | 改法 |
|---|---|---|---|
| **事物** | 被报告的那件事：一个事项、一批产出物、一个台上的一段时间、一个对象（某个 SKU、某条流程） | 系统按引用认，不另建实体（见下） | — |
| **维度** | 看一件事的一个角度，例如「经营」「风险」「客户体验」 | 定义维度的人（第六节） | 版本化 |
| **报告模板** | 一个维度的协议：参数、数据槽、文档结构、**论断要求**、**回应要求** | 同上 | 版本化；判据级的改动见第五节 |
| **报告** | 按某一版模板、针对某一件事物生成的一份成品，生成时冻结 | 产出方（AI 或人） | 不改；更正就出新报告，链到旧的 |
| **论断** | 报告里一条可以被回应的判断：结论、依据（指向数据槽、行或上游产出物）、置信程度 | 产出方，随报告一起冻结 | 不改 |
| **回应** | 对一条论断的认可、反驳或补充，带理由 | 读到报告的人（第六节） | 只追加；改主意就再追加一条，最新的生效 |

**事物不另建实体**：报告记一个引用，指向已有对象（事项 `item_id`、产出物、台的卡片 id 加时间范围、业务对象标识）。同一个引用下的报告就是「这件事的多个维度」。业务对象标识怎么写由领域定，市场只做相等比较，不解析。

**论断为什么要单独成对象**：业务要对「第三条结论」表态，报告里的判断就不能是一整段正文。论断有编号，回应挂在编号上；模板规定这个维度至少要给哪几类论断（例如「结论」「风险」「建议」），没有就不算合格的报告。

和 ygl-trees 的 claim 的关系：概念相近（都是可检验的断言），但这里的论断是业务层、给人回应的；ygl 的 claim 是研究证据层的。论断可以带一个 ygl claim 的 id 作依据，不合并成一个对象。

## 四、和已有的东西怎么接

| 已有的 | 关系 |
|---|---|
| 数据视图（[data-views](../data-views.md)） | 报告的数据从视图来：模板里的数据槽绑定到台的视图块。视图是活的，报告冻结时把数据复制进去，并记下来源的版本、哈希和行数 |
| 报告模板 P0（[report-template-p0](../report-template-p0.md)） | 已证明「模板 → 数据槽绑定 → 冻结 → 连续阅读与打印」；模板里的参数、文字字段、数据槽、文档结构四块照用。P0 缺的是：论断、回应、维度、事物引用、持久化、权限 |
| 事项的验收（[02](02-concept-model.md) 第三节） | 不取代。一个事项可以挂几份报告；验收仍是事项上的一次「决定」。不强制要求报告；维度的模板可以声明「有未处理的反驳时不能验收」（属主 2026-11-21 定，见第八节） |
| 公共区与产出物（[15](15-two-layer-org.md) 第九节） | 同构：只追加、带版本和来源、读不限制。**报告就是一种产出物**：写进公共区时走同一道任务写授权、同一套来源列（`_area`、`_task`、`_upstream`、`_supersedes`，#919 已有存储前置）。回应不算产出物，挂在报告上，不占写授权 |
| 关注队列与「决定」（[02](02-concept-model.md) 第五节） | 有新报告等人回应时进关注队列；回应本身不是「决定」（不放行、不拍板），只是检验 |
| 观察者（[18](18-observer.md)） | 反驳的理由可以按观察者的卡点标签归类，同类反驳计数，够了就是「固定解法」的候选 |

## 五、模板的修订：判据归谁

agent-atelier 的「化的边界」草案有一条总原则：**被测与判据不由同一方在同一次改动里改。** 模板定义了一个维度该回答什么、什么算合格，它就是判据。所以：

| 改动 | 相当于 | 谁能做 |
|---|---|---|
| AI 按模板写报告、改进自己写报告的做法 | L0、L1：当下做法、项目能力 | AI 自主 |
| 模板的版式、措辞、组件，不改论断要求和回应要求 | L3：规则正文 | 定义维度的人起草，作者以外的人看过再发版 |
| 模板的论断要求、回应要求、数据口径，新增或撤掉维度 | L4：判据与边界 | 只有定义维度的人（第六节）；AI 只能提案，并附「改前改后同一批报告的判定差异」 |

- **按回应改模板，决定外置。** 反驳统计是证据，「据此改模板」由定义维度的人决定，不由产出报告的一方决定。
- **判据和行为分开提交。** 一次修订同时改了模板的判据和 AI 的做法，拆成两次，判据先定。
- **旧版本保留。** 报告绑定生成时的模板版本；模板发新版不追溯旧报告，旧报告上的回应仍按旧版读。

风险就在这里：一旦写报告的一方能改模板，「做得更好」会被悄悄换成「更容易被认可」。

## 六、权限（「定义维度」「回应」两行属主 2026-11-21 按推荐定了，其余仍是草案；见第八节）

| 动作 | 推荐 | 理由 |
|---|---|---|
| 定义维度、发模板 | 领域负责人定本领域的维度；跨领域的维度由属主定；单独授予这个动作，和「定规范」一样（[15](15-two-layer-org.md)「已确认」第 1 条） | 模板决定 AI 在这个维度上怎么交代，和领域规范同类 |
| 产出报告 | 持有这个领域生效授予的 AI 成员或人；写进公共区时另要任务写授权 | 沿用领域授予和公共区的规矩，不另开 |
| 读报告 | 写进公共区的，读不限制；没进公共区的，按所在台的读权限 | 沿用 |
| 回应 | 人和 AI 都能回应，**回应上标明回应者是人还是 AI、站在哪个位置**；统计时分开算 | 只有人的回应算「他」的检验；AI 的回应是参考，不能替人验 |
| 改、删回应 | 不能。改主意就追加一条新的 | 留痕；最新的那条生效，历史可查 |

每一项都是身份与权限类改动，落地时按 CONTRIBUTING 红线先验后合。

## 七、实现顺序（草案）

每一步一个 PR，前一步合了再开下一步。

0. **P0 的测试欠账：已由 #830 补上**（#817 验收建议）。拒收用例已改为同时核错误码，截断标志、列类型兼容、form 和 filter-bar 块拒收、展开上限、`b.columns` 的自有键检查各有一条只触发单一原因的用例；`node scripts/report-template-p0-test.mjs` 在 main `903e840d` 上 33 条全过（2026-11-21 本机，Node 22）。还剩三条用例只断言抛错、不核错误码：重复行键、repeat 上限、图片地址。逐条实跑，它们分别拦在 `duplicate_row_key`、`repeat_limit`、`invalid_asset` 上，都是预期的那道检查；改成核错误码是顺手的小事，随第 2 步一起做。
1. **规格**：报告、论断、回应、维度四个对象的表结构和接口，按 [领域第 1 步规格](../domains-step1.md) 的格式写。草案见 [报告第 1 步实施规格](../report-step1.md)（2026-11-21），只写文档。
2. **模板与报告落库**：模板存主库（维度属于领域，一个模板给多个台用），台对模板的绑定和报告存台库（规格第二节）；模板版本建好不改不删、不修剪；生成时由服务端解析数据来源、填来源版本、哈希和行数（不再信调用方给的夹具证据）。只读本台的数据，跨台排在后面。
3. **论断与回应**：论断随报告冻结；回应只追加、标人或 AI；报告页上逐条回应。
4. **维度与事物**：维度的授予（定义维度单独授予）；同一事物下几个维度的报告并排看。
5. **和公共区合流**：报告作为产出物写进公共区，走任务写授权；排在公共区（领域第 1 步 PR5）之后。
6. **统计与修订提案**：按模板版本统计认可、反驳和理由分类；AI 可以据此提修订提案，由定义维度的人决定。

## 九、不做

- 不做模板的可视化编辑器（先用结构化 JSON，和视图描述一样经 MCP 和页面改）。
- 不做定时出报告（先只做 AI 或人手动出）。
- 不做跨台的报告（第 2 步只读本台）。
- 不做正式的 PDF 服务（P0 的浏览器打印够用）。
- 公开仓不写任何具体业务维度；维度和模板的实例放在部署方的私有仓。
