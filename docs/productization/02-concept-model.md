# 02 · 概念模型

> 阶段 0 草稿。目的：同一件事在五个部件里叫法不同，先对齐，再谈界面和契约。

## 一、各部件的对象怎么对应

| 统一叫法（本产品） | 市场现在 | A2A（dsh-open-a2a-net） | superagent | ygl-trees | DSH |
|---|---|---|---|---|---|
| **事项**：一件要办的事，从下达到沉淀 | 分散：任务中心任务、`workbench_events`、SOP run 的上下文行 | — | 最接近 Ticket，但只在单机内 | task（跟踪） | — |
| **事件**：事项被投递出去的那一次 | `workbench_events` + `workbench_event_deliveries` | 一条带 `task_id` 的 direct 投递 | Trigger（不可变，按 id 幂等） | — | — |
| **接单判断** | 无 | 入站准入（签名、成员关系、名额） | Eval：accept / stop / ignore / unavailable | — | — |
| **授权** | 绑定（admits / notify / both）、MCP 授权、变更申请 | 协作规范档位 | Mandate（不可变，范围变大就开新工单） | — | 权限预设、审批 |
| **执行** | SOP run | — | Ticket + Assignment | — | 会话、子代理、工作流 |
| **进展** | 无（只有终态） | 无（回执只表达终态） | Report 六态：progress / waiting / ready / blocked / failed / dropped | — | 计划、目标 |
| **提问** | 无 | 无 | Attention（结构化，一次一件） | — | 用户提问（ui-user-questions） |
| **回执** | SOP 完成回执 outbox | `[A2A receipt] task <id>` + JSON 信封；终态，不对回执再回执 | Channel 发送（先存后发、幂等） | — | — |
| **产物** | 台数据、文件、SOP run 数据 | — | 工单产出 | artifact | deliverables |
| **证据** | 无 | — | — | source / evidence / claim / verify run | — |
| **沉淀** | 工作台变量与常量、技能市场 | — | — | kb、skill promote | 技能 |
| **线程** | `context_id` ↔ run 映射 | `context_id`（只管续接） | Thread（同一线程同时只跑一个 Eval，保存决定历史） | — | 会话 |

读法：一行就是一个概念，空格表示这个部件没有对应物。市场的问题是「事项」这一行最散，而「进展」「提问」「证据」三行是空的。

## 二、统一对象：事项（Work Item）

市场新增一张表，把一件事的全部痕迹串起来。界面（驾驶舱时间线、关注队列、统一待办）只读它，不再各自拼。

| 字段组 | 字段 | 说明 |
|---|---|---|
| 身份 | `item_id`、`title`、`created_at`、`created_by` | `created_by` 用主体标识（`user:<名>` / `seat:<名>`，见 [11](11-identity-and-permission.md)） |
| 来源 | `source_kind`（task-center / app-data / agent / cockpit）、`source_ref` | 指向原始提交 |
| 场景 | `context`（JSON：店铺、SKU、PD、日期等） | 来自驾驶舱的场景上下文（见 [03](03-cockpit-v2.md)） |
| 投递 | `event_id`；每次投递的 A2A `task_id`（多次） | 沿用 `workbench_events`，不另建 |
| 承接 | `target_team`、`seat`、`eval`（accept/stop/ignore/unavailable + 理由） | 接单判断来自 superagent 的 report（见 [06](06-a2a-superagent-fusion.md)） |
| 状态 | `state`：draft / held / delivered / accepted / progress / waiting / ready / blocked / done / failed / dropped / cancelled | 见下面的状态机 |
| 进展 | 最近一条 report 的摘要与时间 | 全量在事项日志 |
| 提问 | 未答的 ask 列表 | 进关注队列 |
| 回执 | 终态回执的 outcome 与时间 | 回执是终态 |
| 产出 | 台数据 id、文件 id、SOP run id | |
| 证据 | ygl-trees 的 claim / verify run id | 只存 id，不存正文 |

**事项日志**：每次状态变化、report、ask、answer、回执各记一行（追加式，不改写），驾驶舱时间线直接渲染它。

## 三、事项状态机

| 从 | 事实 | 到 |
|---|---|---|
| draft | 提交，派发开关没全开 | held |
| draft / held | 提交且开关全开，或管理员 release | delivered |
| draft / held | 撤回 | cancelled |
| delivered | 投递 dead（重试耗尽或终止码） | failed |
| delivered | 席位 report：eval=accept | accepted |
| delivered | 席位 report：eval=stop / ignore / unavailable | failed（带理由） |
| accepted / waiting / blocked | 席位 report：progress | progress |
| accepted / progress | 席位 report：waiting | waiting |
| accepted / progress / waiting | 席位 report：blocked，或发来 ask | blocked |
| progress / waiting / blocked | 席位 report：ready（做完，等验收） | ready |
| ready | 人在关注队列里验收 | done |
| ready | 人退回 | progress |
| 任一非终态 | 席位 report：failed，或终态回执 outcome=failed | failed |
| 任一非终态 | 席位 report：dropped（必须同时有回执） | dropped |

- 终态：`done`、`failed`、`dropped`、`cancelled`。每个终态都要有一条回执或一条市场侧的明确记录（例如投递 dead），不允许静默消失。
- `held` 是市场的「先观察」：只记录本来会派给谁，不发出（现有机制）。
- `ready` 是席位说「做完了，等你验收」；`done` 只能由人在关注队列里验收后进入。
- `waiting` 表示席位在等外部条件；`blocked` 表示需要人介入（通常伴随一条 ask）。

## 四、三条约束

1. **事项是索引，不是第二份真相。** 投递细节仍在 `workbench_event_deliveries`，run 数据仍在 `sop_runs`，证据仍在 ygl-trees。事项只存 id 和摘要，原件各回各家。
2. **状态只由事实推进。** 只有投递结果、席位 report、回执、人的操作能改事项状态，不允许手动改状态。
3. **身份只认已验证来源。** 未验证（unbound）的 A2A 消息只当数据，不推进状态（与现行 A2A 规矩一致）。

## 附：阶段八的落地规格

分四个 PR，每个都由独立会话验收。前两个不改变任何对外行为；后两个只加新的入口，旧页面和旧接口照常能用。

排期上的一处修正：实现计划里写「八依赖六的留痕」。照下面的做法，「看」和「答」都交回各来源自己的守卫和自己的留痕，所以 8a ～ 8d 不必等阶段六切换；阶段六切换之后，再把可见性改成走统一判定（见 8c 的最后一条）。

### PR 8a：事项表与事项日志

- 两张表。事项表按第二节的字段组建，只存 id 和摘要，不存原件。事项日志只增不改：库里用触发器拒绝改写和删除。
- 多两个可选字段：对象和阶段。它们是观测层给的不透明标识，市场只存、只按它筛，不解释含义。
- 状态机写成一张表驱动的迁移表（第三节那张），放在事项服务里。服务只有一个改状态的入口：给一条「事实」，查表得到新状态，写一行日志。表里没有的迁移一律拒绝，没有「直接设状态」的接口。
- 第三节没写到、实现时补定的三处：
  - **原地重复的上报算合法。** progress 时又报 progress、waiting 时又报 waiting、blocked 时又来一个提问：状态不变，记一行日志，更新进展摘要。这几行明写进迁移表，表外的照旧拒绝。
  - **只记录、不改状态的事实另列一张表。** 人答了席位的提问：只在非终态、且答的是一条还没答过的提问时接受。回执（outcome 不是 failed 的）：在 ready 和任一终态都接受，终态之后到的标成「晚到」。终态之后只开这一个口子，别的事实一律拒绝。
  - **dropped 是一条事实带两部分。** 席位的 report 和回执一起来才接受，缺回执就拒绝。
- 事项是一个新的领域插件，自带服务。这个 PR 不注册任何路由，不接任何来源。
- 验收：第三节之外的迁移全部被拒，逐个有例；日志的改写和删除在库这一层被拒；终态之后不再接受任何事实；同一条事实送两次，状态和日志都只变一次。

### PR 8b：接上事实

- 事项服务监听现有的事实，不改它们：事件创建、搁置、放行、撤回；投递结果；席位的 report 和 ask；回执；人的验收和退回。来源各自照旧写自己的表，另外多发一个事件，事项服务听它。
- 这个 PR 只接市场里今天已有的事实：事件创建、搁置或排队、放行、撤回、投递结果、接单节点回写的决定。席位的进展上报、回执、人的验收和退回今天还没有入站的来源，事项服务先把这些种类收着，等事件契约 v2 和 8d 再接。
- 一个事件对应一个事项，哪怕它投给多个团队。任一团队接单，事项就进「已接手」；投递失败和拒接，只有在没有别的投递还活着时才把事项推到「没办成」。
- 接单前就可以提问：迁移表补三行，「已转交」时来提问进「在问你」；「在问你」时来接单进「已接手」；「在问你」时拒接、且没有别的投递还活着，进「没办成」（和「已转交」时拒接那一行对称）。
- 被拒绝的事实也要留痕：终态之后到的、表里没有的，状态不动，但在日志里记一行「收到，未采信」和原因，不能无声吞掉。
- 回填在事项服务装上时自动跑一次，之后可以手动重跑。
- 拒接没写理由的，理由记成「未写理由」，不因此卡住。没有目标团队的事件照建事项，停在草稿，日志记一行「未路由」。
- 回写决定凭的是那次投递的回复令牌，算已验证；对方自报的名字只记录。提交方未验证的事件照建事项，但之后的事实都只记「收到但未采信」，状态不动。
- 事项服务在来源的事务里用保存点应用事实；它出错不影响来源，但要打日志并计数，回填能把漏掉的补上。
- 未验证来源的消息不推进状态，只记一行「收到但未采信」。
- 乱序和重复：每条事实带来源自己的 id，按它去重；晚到的旧事实不把状态往回拉。
- 回填：从现有的事件表和投递表把存量事项建出来。可以重复跑，结果相同。
- 验收：现有的测试和录制回放零差异；把一段录下来的事实序列正放、打乱、重复各喂一遍，终态相同；未验证来源的对抗例不推进状态；回填跑两遍，表的内容逐行相同。

### PR 8c：「关注」的读

- 不合并表。每个来源向「关注」注册一个提供方：给定主体，列出等这个人处理的条目。注册可撤销，来源插件卸掉，它的条目就不再出现。
- 来源七个：变更申请、MCP 权限申请、席位的提问、任务中心收件、待属主看板、待对接清单、事项的验收和过目。阶段六的待核授予做完之后作为第八个接进来。
- 实现时补定的对应关系：
  - 席位的提问取事件层未答的那些，每条带上事项的 id；事项上的未答列表不另列，另有一条测试钉住两边条数相等。
  - 任务中心收件取统一待办那一套；它已经汇总了别的来源，别的提供方给过的条目在这里剔掉，同一条不出现两次。
  - 待属主看板的判断今天在前端。服务端写一份等价的，两边跑同一份用例表，钉住一致。
  - 事项的验收是「等验收」状态的事项，等的是建立人，管理员也能看到；过目是「等你过目」状态的事项，等的是管理员。
- 每条的形状统一：来源、来源里的 id、类别（提问、审核、验收、过目、授权）、标题、谁在等、等了多久、可选的答法、对象和阶段、原件的链接。
- 可见性先用各来源自己现有的守卫：提供方只返回这个主体本来就能在旧页面看到的条目。条数也按同样的规则算，看不到的不计数。
- 一个只读接口返回当前主体的全部条目和各类条数。
- 阶段六切换之后：提供方不再自己判，改成由统一判定决定这个主体能不能答这一条。
- 验收：七个来源各造一条待决，都出现在「关注」里；对同一个主体，「关注」里每个来源的条数等于那个来源旧接口的条数；换一个无权的主体，条目和条数都看不到，各有对抗例。

### PR 8d：「关注」的答

- 一个答复入口，按来源分发给来源自己的处理函数。检查、状态变化、留痕都是来源原来那一套，入口自己不判、不写业务表。
- 实现时补定的形状：提供方除了「列出」，再注册一个「答」。答复入口只认来源、确认这一条此刻在这个人的列表里，然后调提供方的「答」。过渡期里，已有旧入口的来源，它的「答」实现成在进程内把请求转给原来的路由：路径只来自写死的表，原请求的身份原样带过去、不提升，全部中间件和守卫照走，旧路由返回什么就返回什么。阶段三做完后逐个换成直接调用，接口不变。统一待办只在原系统里勾销，「关注」里不提供答法。
- 同一条答两次：第二次返回第一次的结果，不重复生效。两个人同时答：一个生效，另一个被告知已处理。
- 答复席位的提问时，按 [06](06-a2a-superagent-fusion.md) 作为同一事项的后续事件发回原团队。
- 界面：「关注」页一次处理一条；事项页的时间线直接渲染事项日志。旧页面保留，入口处标出「也可以在关注里处理」。
- 验收：每个来源，从新入口答和从旧入口答，得到的状态和留痕逐字段相同；无权的主体从新入口答，被拒的方式和旧入口一样；重复答和并发答各有例。

### PR 8e：建立人验收自己的事项

8d 的答复入口在写请求的总门后面，只有管理员过得去；而「等验收」等的是建立人。所以补这一个 PR，在 8d 合并后做。

- 一个不经管理门的入口，只接受「验收」和「退回」两种事实，只对「等验收」状态的事项。
- 由事项服务判：请求认出的主体必须就是事项的建立人，按主体标识比，不按显示名；要求已登录、同源、主体没有被停用。
- 建立人不是人（席位、工作台、系统）或来源未验证的事项，这个入口不接受，只能由管理员处理。管理员照旧能验收。
- 「建立人是谁」单独记一个字段：建事项时，提交那次请求经身份服务认出了主体、且提交方已验证，才记这个主体的标识；否则留空。原来的建立人名字只当显示用，任何判断都不读它。入口、「关注」的提供方、事项页用同一个函数判「是不是他的」。标识为空的事项没有「本人」，只有管理员能处理。存量回填时确定不了就留空，不按名字去对。
- 同一个事项被退回后再次进入「等验收」，要能再答一次：重复答的判断按「这一次进入等验收」来记，不按事项记。
- 验收：别人的事项、冒用显示名、被停用的建立人、跨站、不在「等验收」状态、未登录、拿这个入口送别的事实，各有对抗例并全部被拒。

### PR 8f：提交面认出提交人

8e 做完之后发现它还用不上：存量事项都没有建立人，新事项也只有管理员在页面上发布的能记上，真正提需求的人在任何通道都没被认出来过。所以补这一组。

- 建立人是提需求的人，不是发布的人。建录入时认出主体，记在那次录入上；发布时事项的建立人取它。发布的人另记，只留痕。没记到提需求的人就留空，不拿发布的人顶替。
- 任务中心是同源页面，请求本来就带着登录，直接认。
- 台页面跑在沙箱里，提交时带不上登录，也不靠放宽跨源去带。做法：服务端出台页面的那一刻知道是谁，认得出是启用的人，就在页面里放一张票据——服务端签名，绑定这个人、这个台和两小时的期限。提交时放在信封的一个字段里带回，服务端验过才记下这个人。
- 票据只能用来「在这个台的提交上记下这个人」，别的入口不认，换不出登录或别的权限。验不过就当没带，照今天一样放行、留空。带了票据的页面不许被缓存。
- 认不出人的提交照今天一样放行。对外行为只多不少。
- 分三个 PR：任务中心认人并加提交计数；服务端的票据；台页面带上票据（在私有仓）。
