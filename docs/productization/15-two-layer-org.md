## 一、要点

1. **系统里没有人的组织。** 部门、汇报线、人事关系只存在于飞书这类协同应用里，本系统不建、不存、不同步。
2. **系统里只有两条边界**：
   - **人与 AI 的边界**：人在这里触发任务、定规范、验收结果；
   - **AI 与 AI 的边界**：只有领域。AI 之间没有上下级。
3. **两层就是这两种角色**：
   - 管理层是人，负责触发和定义规范；
   - 业务层是 AI，按领域承接任务。
4. **任务是中心。** 系统运转的单位是任务（事项）。一件事是谁提的、归哪个领域、谁在做、做到哪、验没验，都记在任务上。
5. **领域是边界。** 一个领域是一类业务，有自己的 AI、技能、工作台和规范。任务按领域分派，规范按领域生效。
6. **人是自迭代循环里的一环**：人触发任务 → AI 在领域里执行 → 人验收 → 验收和打回沉淀成领域规范 → 规范约束下一轮执行。
7. **每个领域（团队）至少一个负责人**（属主 11-18）。负责人是人，由属主指定，能批什么由属主限定。他是领域在人与 AI 边界上的责任人，不是 AI 的上级，也不是部门里的职位。
8. **领域是业务流程上的一个环节**（属主 11-18）。上游的产出是下游的输入，一份产出可以同时供几个领域使用。领域之间经**公共区**衔接：读不限制；写以任务为驱动，按任务批次单次授权；下游需要时自己去取。见第九节。

## 二、模型

```
人（管理层）：触发任务 · 定领域规范 · 验收
────────────── 人与 AI 的边界：任务 ──────────────
AI（业务层）：  领域甲 │ 领域乙 │ 领域丙      ← AI 与 AI 之间只有领域边界
                   └──产出──→【公共区】←──取用──┘   ← 领域之间只经公共区衔接
```

| 对象 | 是什么 | 从哪来 |
|---|---|---|
| 领域 | 一类业务，分派和规范的边界 | 市场里建；对应 a2a-net 的一个团队 |
| 领域规范 | 这个领域接什么事、怎么做、什么要先问、怎么验 | 人在市场里定；节点确认后生效（14 第八节的编制变更） |
| AI | 领域里的成员，承接任务 | a2a-net 名册，市场只读 |
| 人 | 系统的一个主体，可以触发任务、定规范、验收 | 站内账号；权限按领域授予 |
| 领域负责人 | 对一个领域负责的人：批接入申请、过目放行、卡住的事冒给他、改派；每个领域至少一个 | 属主指定；能批什么由属主限定 |
| 公共区 | 领域之间交换产出的地方：读不限制，写按任务授权 | 市场里；见第九节 |
| 产出物 | 一件任务写进公共区的业务数据，带版本和来源 | 任务完成时写入 |
| 任务（事项） | 中心对象 | 市场的事项表 |

**人的权限按领域给，不按部门给。** 一个人能对哪些领域触发任务、定规范、验收，是 [11](11-identity-and-permission.md) 的一条授予，范围写成「域:<领域>」。系统里没有「部门」「部门负责人」「上级」这类对象；**领域负责人**是领域上的一个角色，由属主指定，不挂在部门下面（属主 11-18）。

## 三、任务怎么流

1. **触发**：人在市场里提一件事，可以选领域；不选的，由入口按领域规范判断归属，判断结果和理由写在任务上，提出人可以改。
2. **进领域**：任务经 a2a-net 路由进入领域对应的团队。领域内由谁接，是领域自己的事，市场不选具体的 AI。例外是分配给某个员工的成员：这个员工可以直接把事交给它（属主 11-18 定保留分配）。
3. **执行**：进展、提问、结果都走 a2a-net 回执（[06](06-a2a-superagent-fusion.md)「一之二补」的现行合同），落到这件任务上。提问由触发的人答。
4. **跨领域**：业务流程有上中下游。上游任务的产出写进公共区，下游领域的任务需要时自己去取，作为输入（第九节）；一份产出可以同时被几个领域取用。一件事同时涉及几个领域、要并行做的，仍然可以拆成几个子任务，各归各的领域，挂在同一件任务下，结果汇总回来。
5. **验收**：触发的人验收。触发人不在时，由对这个领域有验收权的人代验，留痕写明。
6. **沉淀**：验收和打回的理由，经人确认后写进领域规范，下一轮按新规范执行。这就是人在自迭代循环里「定规范」的那一环。

一个 AI 手上有什么、领域忙不忙、通过率多少，都从任务现算，不另存。

## 四、和 a2a-net 怎么对上

a2a-net 现在每个团队都要绑定画布和一个总工（router）才能开工。按「AI 之间只有领域边界、没有上下级」，采用下面的对法（根据 A2A 团队构建优化会话 11-17 对 next/0.8 的只读评估）：

- **领域 = a2a-net 的一个团队。** 跨领域拆单复用现成的根团队派单（`superagent-root-team`）：入口是一个只做分派的根团队，按领域把子任务派给各领域团队，回执回流到原任务。
- **根团队和各领域团队里的总工只做派工，不是上级。** 它不定规范、不验收、不改别的领域的事；能按规则直派的，配成直派、不经总工。
- 选这个对法而不是「全组织一个团队、领域是成员分组」：现成的根团队派单、回执回流、编制变更都能复用，a2a-net 要改的地方最少；成员分组是 a2a-net 里没有的新概念。

a2a-net 一侧要补的（由 dsh-open-a2a-net 项目接，协议说明写在那边）：

| 要补什么 | 现状 | 改动量 |
|---|---|---|
| 团队带领域标识，名册和名片里报出来 | 团队设置、名册快照、名片都没有这个字段 | 小；两个信封各加一个可选字段，旧版本忽略 |
| 分派结果带上「为什么」 | 进展回执已带承接席位和拆出的工单，缺分派理由 | 小；进展里加可选的分派项，理由截断、只给请求方 |
| 子任务带上原任务的标识 | 根团队派给子团队用的是新任务号，不带原任务的上下文 | 中；另加一个原任务字段，不复用对话的上下文标识，免得回执混进原对话；要非自评审 |

领域的建、撤和领域规范的变更，走现有的编制变更入口，不需要新协议。

## 五、权限

| 谁 | 能做什么 |
|---|---|
| 属主 | 建、撤领域；授予别人对某些领域的权限 |
| 领域负责人 | 在属主限定的范围内：批本领域的接入申请（[16](16-progressive-capability-access.md)）、过目放行、接住卡住的事、改派；不能批自己名下的申请（审批回避） |
| 对某领域有授予的人 | 在这个领域触发任务、答提问、验收 |
| 对某领域另有「定规范」授予的人 | 定或改这个领域的规范。这是单独的一个动作，不随触发、验收的授予一起给（属主 11-17 定） |
| 系统管理员 | 照旧看不到业务内容（两人制），只管账号、登记和配置 |

没有「部门负责人」「管理层看全部」这类按组织位置来的权限，一切按领域授予；领域负责人也是一条由属主放行的领域授予，不是从组织位置来的。

## 六、实现顺序

排在 Odoo 下线和登录持久化之后，因为人和授予要先落在站内账号上。

1. **领域对象**：领域表；授予的范围支持「域:<领域>」；领域规范作为领域的一部分，版本化保存。
2. **任务带领域**：建任务时选领域；没选的按领域规范判断，结果写回任务。
3. **a2a-net 对接**：领域对应团队；名册带领域标识；分派理由和原任务标识回到市场。需要 a2a-net 先发版本。
4. **界面**：按领域展示 AI 和任务；领域页上能看、能改规范。界面以原型为准，偏离先报属主。
5. **收掉人的组织**：部门这个对象，在 1～4 步验收后删除。现有的团队负责人（`team_leads`）**不删**，转成领域负责人；部门负责人在第 1 步迁移时转成领域负责人的授予草稿。成员分配给员工（`seat_assignments`）**保留**（属主 11-18）。删除前按「旧断言 → 新守护」核对，历史数据只读保留。
6. **公共区**（第九节）：产出物、按任务的写授权、版本和来源；排在第 2 步之后（写授权要挂在任务上），可以和第 3、4 步并行。

每一步都是身份与权限类改动，按 CONTRIBUTING 红线先验后合。

## 八、从 14 并进来的（仍然成立）

> 本节由第 14 篇并入（2026-11-18）。第 14 篇原文已归档到 [archive/productization/14-team-and-assignment.md](../archive/productization/14-team-and-assignment.md)。

### 1. 卡住的事往上冒

> 出自 14 第九节第 5 小节。

- 提问超过一段时间没人答（缺省一个工作日），除了建立人，负责人的「等你拍板」里也出现这一条，写明「某某一直没答」。
- 等验收超过一段时间没人验，同样冒给负责人。
- 成员从名册里消失而事项还在办，冒给负责人，由他改派或撤回。

### 2. 改派

> 出自 14 第九节第 6 小节。

负责人可以把一件在办的事从一个成员改给另一个成员，或者退回给总工重新分派。到节点上是同一件事的一条新派工，原来的成员停手。事项还是那一件，时间线上记一笔「负责人改派」。依赖指名能力，放在第 3 步。

### 3. 数字从事项来

> 出自 14 第九节第 7 小节。

团队页上每个成员的「在办几件、本周办结几件、验收通过率」都从事项和验收记录现算，不另存。通过率 = 验收通过的 ÷（验收通过的 + 被打回的）。

### 4. 编制变更：市场提、节点确认

> 出自 14 第八节第 3 小节「市场到节点这一步怎么走」。

市场不掌握节点的凭据，也不直接改节点上的东西（文档 06 的边界）。所以「建团队、加成员」是市场向节点**提出一个编制变更**，节点自己执行：

1. 市场把变更发给节点：建团队 / 加成员（岗位模板、名字）/ 改规矩 / 停用成员。带上是谁发起的。
2. 节点核对来源（是登记过的市场、签名对得上），按自己的规则决定执行还是拒绝。执行用的是节点自己的权限，市场拿不到。
3. 节点执行完，名册报回市场。市场看到名册变了，这次变更才算完成；没等到名册的，在团队页上显示「节点还没办完」或节点给的拒绝理由。

哪些变更节点直接照办、哪些要节点一侧的人点头，是节点的策略，每种变更在节点上单独设（照办 / 要点头 / 不接受）。缺省保守：建团队、撤团队、换岗位、改团队的规矩要点头；在配额之内加成员、停用成员照办。点头只能在节点一侧做，市场里的任何角色都不能替节点点头——否则市场被攻破就等于节点被攻破。

所以第 4 条表里「谁能做」说的是谁能在市场里**提出**这个变更；提出之后节点照办还是等人点头，看节点的设置。凭据、工具放行、跑在哪个系统用户这类东西，这条路一律改不了。

节点一侧的入口已经定了（2026-11-12，节点侧设计照提案批准），市场照这个走：

- 市场可以让节点新开会话（会花模型额度），但只在节点主人预先给的配额和岗位模板之内；模板里的预设、模型、工作目录都由节点主人写，市场只传模板。
- 缺省策略：建团队、撤团队、改岗位模板、改团队规矩要节点主人确认；配额内加成员、撤成员自动执行。
- 团队规矩也是市场提、节点确认（不是负责人在市场里改了就生效）：规矩授不了工具和凭据，但能左右团队在许可范围内做什么。
- 谁能点头：节点主人，加上他在节点上指定的审批人。市场一侧的任何角色都不能替节点点头，只记谁提的。
- 撤成员时它手上的事让它做完，不立即改派；要立即停，节点主人在节点上移除。

## 九、公共区：领域之间怎么衔接（属主 2026-11-18）

业务流程有上游、中游、下游。上游任务的产出是下游任务的输入，一份产出也可能同时是几个领域任务的输入。所以领域之间要有一个公共区。各领域的私域（自己的过程数据、接口、规范）别的领域进不来；领域之间的数据交换只经过公共区。

| 规则 | 内容 |
|---|---|
| 读 | 不限制。不再往深里设计读的范围（属主 11-18：「不需要考虑那么深远」）。读照样留痕 |
| 写 | 以任务为驱动：一件任务（一个批次）获批时，带一次性的写授权，只能把**这件任务的产出**写进公共区，写完或任务结束就用掉；不给领域长期的写授予 |
| 写什么 | 只能写授权通过的业务数据：符合事先声明的产出物格式，不符合的拒绝 |
| 改 | 只追加，不覆盖：更正就写新版本，旧版本保留；别的领域不能改 |
| 来源 | 每份产出物记下：哪个领域、哪件任务、谁批的写授权、用了哪些上游产出物作输入。从下游结果能一路追回上游 |
| 取 | 下游需要的时候自己去取（拉）；不做发布后自动给下游派任务 |

和别的东西的关系：

- 和 [16](16-progressive-capability-access.md) 的区别：16 讲的是 agent 接入某个领域的能力，授权跟随账户、没有时效；公共区的**写**跟随任务、单次有效，是两回事。公共区的**读**算 16 里的常驻能力，不用申请。
- 落地优先复用已有的数据视图和台库，不另起一套存储；数据视图这条线由协同开发独立推进，公共区落地时和它对齐。
- **按任务的单次写授权，复用现有的上传票机制**：任务获批时签一张「写票」，只能用一次、绑定这件任务、到期作废，发票时要授权、用票时再核会话没吊销。产出物的格式就是数据集的字段定义；来源多记两列（产出它的任务、用到的上游产出物）。不另造一套授权。
- 写进公共区就等于公开给所有领域。私域里的敏感内容不该出现在产出物的格式里，靠格式挡，不靠读权限挡。

## 已确认

- 领域规范单独授予「定规范」这个动作，不是对领域有授予就能改（属主 11-17：「单独授」）。理由：规范决定了 AI 在这个领域怎么干活。
- a2a-net 的对法用第四节的做法（属主 11-17 在 a2a-net 会话里确认）；那边的三项排在它清完遗留事务和 issue 之后。
- 有团队就一定会有负责人（属主 11-18）。领域负责人由属主指定，能批什么由属主限定。
- 公共区读不限制；写以任务为驱动，按任务批次单次授权；下游自己去取（属主 11-18）。
- 成员分配给员工保留（属主 11-18）。
