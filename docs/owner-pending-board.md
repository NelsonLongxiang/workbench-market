# 待属主看板（`/owner-pending`）

全机唯一一张「等属主决定或动手」的清单。属主回来时只看这一处，在页面上直接答复。

服务端不新增接口，全部用现成的工作台变量（#336）和常量的作者锁（#450）。页面在市场主站、和主站同源，不是沙箱自产台。

## 数据放在哪

数据放在一张专用外部台卡片的变量里。这张卡片的地址填本站的 `/owner-pending`，页面按这个路径找它；没登记，或登记了不止一张，页面都会报出来，不会去猜。外部台的变量只有管理员（口令或 Odoo 管理员）和获授权的 MCP 会话能读，台令牌和匿名请求都读不到。

| 键 | 谁写 | 内容 |
|---|---|---|
| `config.owner` | 属主本人的 Odoo 登录（第一次打开页面时登记） | `{owner_login, writers: ["mcp:<会话名>"]}` |
| `item.<NN>` | 登记身份（`writers` 中的会话） | `{question, checked, waiting_for, first_raised, last_change, source, status?: "withdrawn", history_answer?: {summary, date}}` |
| `answer.<NN>` | 属主本人的 Odoo 登录 | `{summary, date}` |

三类键都是**常量**。常量记作者，作者只认个人身份 `mcp:` 或 `odoo:`，只有作者本人能带 `override` 和 `reason` 修订。管理员口令、台令牌和别的会话都改不了。

页面只采信作者对得上的记录：
- `config.owner` 的作者必须正是 `odoo:<owner_login>`。
- `item.*` 的作者必须在 `writers` 里。
- `answer.*` 的作者必须是 `odoo:<owner_login>`。

对不上的一律列进「来源不符」并点名作者，不当作事项，也不当作答复。

状态有四种，排序依次是：
- **待办**；
- **历史答复**：迁移时由登记身份写进 `history_answer`，未经本页属主确认，标签和属主答复分开；
- **已答复**：有属主本人的 `answer.<NN>`；
- **撤回**：登记身份写了 `status: "withdrawn"`。行里会显示撤回者和 `withdraw_reason`。

**信任根**：页面顶部醒目显示「本看板属主：odoo:&lt;login&gt; · 登记身份：…」。服务端并不知道谁是真属主，`config.owner` 谁先登记就归谁。所以如果顶部显示的不是属主本人，本看板就作废：要在部署机本机用命令行清理 `config.owner`，再由属主重新登记。上线步骤因此要求属主当场建卡、当场登记，中间不留空窗。

## 答复的效力

页面上作者验证为属主的 `answer.<NN>`，可以当作属主对该事项的答复。但如果是生产或不可逆动作的授权，仍要在授权登记表里引用这条答复登记一笔，才能生效。页面顶部有一行提示。

属主答复时，页面只带浏览器的 Odoo 会话，**不带管理员口令**。口令是共享身份，用它写出来的常量没有作者，页面不认。

## 上线步骤

1. **建登记身份**（属主）：
   - 在「MCP 网关」页新建会话，名字定下来就别改，例如 `owner-board`。
   - 只授权三个工具：`workbench_vars_get`、`workbench_vars_set`、`workbench_list`。
   - 令牌只显示一次。属主本人把它写进登记方所在机器的 MCP 客户端配置，作为 `Authorization: Bearer` 请求头，配置文件权限设成 `0600`。
   - 任何代理都不读、不打印、不复制这个令牌；它不进仓库、文档或日志。
2. **建看板台并当场登记**（属主本人，连续完成，中间不留空窗）：
   - 用 Odoo 管理员账号登录市场，新建一张外部台卡片，类型 `web`，地址填 `<本站地址>/owner-pending`。
   - 紧接着打开 `/owner-pending`，点「我是属主，登记」，登记身份填第 1 步的会话名，例如 `mcp:owner-board`。
3. **核对信任根**：
   - 页面顶部显示的属主应是属主本人的登录名。
   - 用 `GET /api/workbenches/<看板台 id>/vars/config.owner/audit`（管理员）核对：`create` 那一行的 `actor` 应为 `odoo:<属主>`。
   - 两者有一项不对，就按上面「信任根」一节作废并重来。
4. **迁入事项**（登记身份）：
   - 用 `workbench_vars_set` 把事项逐条写成 `item.<NN>`（`kind: "const"`）。
   - 已经答复过的事项，在 item 里写 `history_answer`。
   - 撤回时带 `override`、期望 `revision` 和 `reason`，把 `status` 改成 `withdrawn`，并写 `withdraw_reason`。
5. 把看板台 id 告诉负责每天审计抽查的一方。

## 令牌吊销与轮换（属主执行）

- **吊销**：在「MCP 网关」页对该会话点「吊销」，令牌立即失效，审计行保留。
- **轮换**（例如怀疑令牌外泄，或定期更换）：
  1. 会话名不能重复，所以在「MCP 网关」页新建一个会话，例如 `owner-board-2`，授权同样的三个工具，令牌写进客户端配置后删掉旧令牌。
  2. 属主用 Odoo 管理员账号打开看板页，点顶部的「修订登记身份」，把 `mcp:owner-board-2` 加进列表后保存。页面带 `override`、当前 `revision` 和 `reason` 修订 `config.owner`，写完会回读核对。只有属主本人能改，别的管理员和口令都改不了。
  3. 确认新会话写入正常后，在「MCP 网关」页吊销旧会话。旧会话吊销后可以留在列表里：它写过的事项照常采信，它也写不进新内容。只有怀疑旧令牌泄露、要作废它写过的内容时，才从列表里去掉；去掉后它写过的事项会列为「来源不符」，需要用新会话重新登记。
  4. 新会话改不了旧会话写的事项（常量只有作者能改）。要修订旧事项时，有两个办法：用新编号重新登记、旧事项标撤回；或者在部署机本机用命令行把作者移交给新会话（REST `PUT …/vars/item.<NN>` 带 `owner`，只有本机命令行可以）。

## 已知限制

- MCP 授权还不能限定到单个台（#452）：登记身份能改所有台的**非常量**变量，常量不受影响。缓解办法：只授上面三个工具，登记身份只写本看板台的 `item.*`，每天按审计抽查 `mcp:<会话名>` 的全部写入。#452 做完后，马上把授权收紧成 `工具@看板台`。
- `config.owner` 谁先登记就归谁：服务端不知道谁是真属主。缓解办法是属主当场建卡、当场登记，并核对审计；抢先登记在页面顶部看得出来。冒烟 B7 覆盖了这种情况。
- 键可能被抢占：其他 Odoo 管理员，或获授权的会话，可能抢先建 `answer.<NN>` 或 `item.<NN>`。页面会把它列为「来源不符」并点名作者，属主在这个编号上写不进去，回 409。清理要在部署机本机用命令行带 `override` 和 `reason` 删除，删除会记审计。
- 审计：`GET /api/workbenches/<id>/vars/<key>/audit`，管理员可读，记录操作人、revision 和值的 sha256。
