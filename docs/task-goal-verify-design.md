# 任务目标的语义验收（接 ygl verify）——设计稿

> 状态：**设计稿，待属主认可**（#941）。不是实现授权，不排期。认可后再按常规流程拆 PR。
> 起草：作者会话，2026-11-21。事实核对基于 main `50712b42`。

## 一、由来

#263 原列「目标深验」，统筹 11-21 定为新功能、先立设计，拆成 #941。最早的设想在 #19（已关）的 P2「验收链」：

- 发布 → `verify submit` 得 material_id；构造方用 `verify prepare`（含盲审、红队）冻结 spec，经人工接口挂到任务上，服务端用 `verify trace` 核 spec 出自本任务的 material；
- 交付 `POST /api/tasks/:id/deliveries` → `verify run` → `archive` → `archive verify`；PASS 为 `accepted`，FAIL / NEEDS-MATERIAL / ERROR 为 `returned`；
- ygl-trees 钉为精确版本依赖、只经 CLI 子进程调；
- 已定取舍第 4 条：**验收不设人工确认，PASS 即自动通过**。

#19 写的是「录入模板 → 发布 → 任务」那条路。那条路已经退役，P2 没有实现。

## 二、现状（只列和本设计有关的事实）

**事项**（`server/src/task-center.ts`、`server/src/services/work-item.ts`、`server/src/routes/work-items.ts`）

- 只经「安排一件事」`POST /api/work-items` 建。目标相关的字段只有自由文字：`intent`（要做成什么）、`deliverable`（提交物要求），没有结构化的判据。`target` 现在是「派给的团队」。
- 状态里和验收有关的一段：做完回执（`receipt outcome=completed`）或团队报 ready → `ready`；`ready` 上人点「验收通过」进 `done`（事实 `verify`），点「打回」回 `progress` 并给团队派返工（事实 `return`，理由必填）。状态只经 `apply(fact)` 改，事实只增不改，库里有触发器守着。
- 谁能验：建事项的本人；打回另外允许团队负责人；持管理层授予的人可以代办（`server/src/work-item-access.ts` 的 `itemDecisionVerdict`）。`area.accept`（领域代验）已经登记，但一直判否，留到 4b。
- `work_items.evidence`（`[{kind,id}]`）已经有列，**现在没有写入方**。概念模型定的是：证据只存 ygl 的 id（claim / verify run id），不存正文（`docs/productization/02-concept-model.md`）。
- 附件按 sha256 钉住，绑到事项上以后不能再绑别处；没有版本。台库快照每个数据集最多留 5 份，旧的会被挤掉，钉不住。

**ygl-trees**

- 服务端经 `server/src/ygl-cli.ts` 的 `execYgl` 调 CLI：子进程、不经 shell、`--json` 契约、有超时。用在统一待办（`project list`、`task list`）和经验库（`library show`、`kb add`）。
- MCP 上游把 ygl 的 `verify` 暴露给会话，但子进程里 `YGL_VERIFY_ALLOW_CMD=''`，所以命令型检查一律判 ERROR。
- 版本：`deploy/ygl-trees` 钉 `0.126.0`，带锁文件和完整性校验。市场镜像自带 ygl 的是 #894，**还没进 main**。
- 仓库自己的开发验证器已经整条跑过 `verify submit → prepare → run`（README「验证器」一节），说明这几个命令在钉住的版本上能用。`verify trace`、`archive verify` 在市场里没有用过，需核。

**可借的模式**：报告第 1 步（`docs/report-step1.md`）的「判据类模板版本要作者以外、认得出的人复核过才能生效」，以及按判据内容（摘要）认复核。

## 三、七个问题，逐条给推荐

### 1. 「目标」现在是什么

**推荐**：目标 = 事项上建事项时写下的那段话（`intent` + `deliverable`），冻结成一份材料；不新加结构化字段，不跟团队走。

- 理由：业务的人只会写一段话，这正是 #19 的前提，今天的「安排一件事」也只收这两段。判据不让写事项的人写，由 ygl 从材料构造（见第 2 条）。
- 领域：事项已经能挂到领域（`area_id`）。**判据的复核权跟领域走**（见第 2、7 条），目标本身不跟领域走。
- 不做：「台上的一组数据」作为目标。那要的是报告（报告第 1 步已有冻结和论断），不是事项验收。两者以后可以接：事项的交付物就是一份冻结报告（第 3 条）。

### 2. 判据从哪来、谁确认

**推荐**：

- 建事项时，服务端用 `verify submit` 把冻结的材料交给 ygl，得到 material_id，记在事项上（只记 id）。
- 构造判据由 agent 用 `verify prepare` 做（含盲审、红队），产出 spec_id。谁来跑 prepare：**派到的团队的席位**，不是建事项的人，也不是市场自己。
- spec 挂到事项上之前，要**作者以外、认得出的人确认**。照报告第 1 步的复核规矩：
  - 挂 spec 的是团队（作者）；
  - 确认的是建事项的本人，或者事项所在领域里持「定规范」授予（`area-spec`）的人；
  - 本机命令行、只带管理口令的确认不了。
- 服务端挂 spec 时核来源：spec 必须出自这个事项的 material（`verify trace`，需核这个命令的现状）；不是就 400。
- 没有确认过的 spec 不参与验收（第 4 条）。

**取舍**：#19 设想「构造方挂、服务端核来源」就够了。现在多了「人确认」这一道，是因为判据决定了怎样算做成：让做事的团队自己定判据、自己判自己，就是报告里刚堵上的「自己复核自己」。代价是多一步人工，判据不确认时事项照旧走人工验收，不阻塞。

### 3. 交付物怎么进验收、怎么钉版本

**推荐**：交付物只认**钉得住的东西**：

- 事项附件（sha256 钉住、绑定后不变）；
- 冻结的报告（报告第 1 步的 `bs_reports`，带模板版本、来源视图版本、sha256、行数，建好不改）；
- 回执里带回的产出（`outputs`，按 kind+id）。

不认台库快照（会被挤掉）和「台上现在的数据」（会变）。

- 验收时，服务端把这几样交付物的标识和摘要列成一份清单（`submission manifest`），清单本身取 sha256，连同 spec_id 一起交给 `verify run`。复跑同一份清单、同一个 spec，结果要一样。
- 交付物的正文不进市场的库，照旧放在附件存储和台库里；ygl 那边按清单取。

### 4. 验收结果和事项状态

**推荐**：**机器判定只作证据，人点验收**；不照搬 #19「PASS 即自动通过」。

- 事项到 `ready` 时，有确认过的 spec 就跑一次 `verify run`，run id 写进 `evidence`（`{kind:'ygl-verify-run', id}`）。
- 页面上，验收按钮旁边列出判定结果：PASS / FAIL / NEEDS-MATERIAL / ERROR，各条判据的结论，报告链接。
- 状态不因判定自动变：
  - PASS：人点「验收通过」即可；
  - FAIL：默认带出未过的判据作为打回理由的草稿，人可以改，也可以仍然通过（必须写理由，见第 5 条）；
  - NEEDS-MATERIAL / ERROR：照人工验收走，页面说清楚是机器判不了，不是没过。
- 理由：现在的事项从建到验收都是人负责（谁建谁验、负责人可打回），领域代验还没开。直接自动验收，等于把「谁能验」的权力交给了判据，而判据的确认规矩（第 2 条）还是新的。先当证据跑一段，看误判率，再由属主决定要不要对某些领域开自动通过（留作开关，默认关）。

### 5. 和现有「人点验收」怎么共存

**推荐**：人点的是最终决定，机器判定是它的依据；冲突时听人的，但要留痕说清楚。

- 人点「验收通过」时，事实里记上当时最近一次 verify run 的 id 和结论。
- **判定不是 PASS 而人仍通过**：理由必填，事实里标 `override: true`。
- **判定 PASS 而人打回**：照旧要理由，同样标出。
- 页面的时间线上，机器判定和人的决定分两种样子显示，一眼看出这条验收是机器判的还是人定的。
- 元验证器（#19 的 M7）改成：每个 `done` 的事项，要么有 PASS 的 run，要么有带理由的人工决定（有 spec 时标 override）。

### 6. ygl-trees 怎么接

**推荐**：#19 的「钉精确版本、只经 CLI 子进程」照旧成立，沿用 `execYgl`。

- 前提是市场镜像自带 ygl（#894）。#894 不进 main，这个功能就不开（Config 开关默认关，起不来时启动自检报一行）。
- 调用都是异步的：`verify run` 可能很慢，放进能随模块停掉的后台任务，不在请求里等。事项页显示「判定中」。
- `YGL_VERIFY_ALLOW_CMD` 维持为空：命令型检查一律 ERROR。页面上 ERROR 写成「这条判据要跑命令，市场不跑，请人看」，不说成失败。
- 网关或 CLI 不可用（`no_cli`、`timeout`、`not_json`）：记一次 ERROR 证据，事项照人工验收走，不重试轰炸；恢复后可以由验收的人点「重新判定」。
- 判定报告正文留在 ygl（`archive`），市场只存 run id。`archive verify` 能用就在写入证据前核一次（需核）。

### 7. 权限

**推荐**：都按事项现有的权限走，不新开一套。

| 动作 | 谁能做 |
|---|---|
| 挂 spec | 派到的团队（席位或团队负责人） |
| 确认 spec | 建事项的本人；事项所在领域持 `area-spec` 的人（硬规则，同 `area.spec-set`） |
| 触发复跑 | 能验收这个事项的人（`itemDecisionVerdict` 那几种） |
| 看判定结果和报告链接 | 能看这个事项的人 |

- 报告正文可能含业务数据：市场只给 run id 和判据结论；正文要到 ygl 那边按 ygl 的权限看，市场不转发。
- 动作名照惯例新增：`work-items.verify-spec-attach`、`work-items.verify-spec-confirm`、`work-items.verify-rerun`。确认那一个按身份与权限类走独立验收。

## 四、要属主定的

1. **自动验收**：同意先「只作证据、人点验收」（第 4 条），自动通过留作默认关的开关吗？这推翻了 #19 的第 4 条取舍。
2. **谁确认判据**：建事项的本人或领域的 `area-spec` 持有人（第 2 条），可以吗？还是只认其中一种？
3. **前置条件**：这个功能等 #894（镜像自带 ygl）进 main 再开工，可以吗？
4. **范围**：第一步只做「附件 + 冻结报告」两种交付物（第 3 条），回执产出放第二步，可以吗？
