# 席位用签名换短期 MCP 令牌

团队不再拿长期的 MCP 令牌：节点宿主按需用签名换一张 1 小时的令牌，只放宿主内存，由宿主代成员调用 MCP。这里写设计取舍和给节点侧（宿主）实现用的格式。市场侧代码：`server/src/services/seat-tokens.ts`、`server/src/routes/seat-token.ts`。

## 签名用哪把私钥

**节点私钥**：宿主的 Ed25519 节点键，就是名片上那把（上游 `loadOrCreateNodeKey`）。

为什么用它：

- 上游每台宿主只有这一把键，团队、席位都没有自己的键（上游 master 和 CI 钉住的版本都一样）。
- 能把席位绑到宿主的只有这把键：名册里的 `host` 就是它公钥的指纹（sha256 前 8 位十六进制，`canvasOwnerFingerprint`）。名册入站时也由它验签。
- 市场钉住的也是它：对端登记表的 `public_key`，管理员确认过的那把。

隔离到什么程度：

- 一台宿主换不出别的宿主上的席位的令牌。
- 同一宿主上的几个团队共用这把键。它们本来就在同一个进程里，成员也由宿主代着跑。
- 以后上游给团队或席位发了自己的键，市场在名册里登记公钥、改成按那把验即可，令牌的形状不变。

属主已接受现状：成员读得到节点私钥，靠节点侧留痕发现。

**残余（存量差异 L22，见 docs/judgment-legacy-differences.md）**：同一宿主上的团队共用一把签名键，换令牌按宿主隔离，不按团队隔离；等上游给团队发了自己的键，名册登记那把公钥，市场改成按它验，令牌形状不变。

## 换令牌

请求：

```
POST <市场对外地址>/api/a2a/seat-token
Content-Type: application/json

{
  "v": 1,
  "root": "<本宿主登记在市场的根地址，origin，如 https://host.example>",
  "host": "<节点公钥指纹前 8 位十六进制，小写>",
  "seat_id": "<名册里宿主给成员位的稳定 id（上游 B1 起的 seatId），[A-Za-z0-9._:-]{1,64}>",
  "ts": <毫秒时间戳，整数>,
  "nonce": "<16～64 位 base64url 随机串，每次新生成>",
  "aud": "<市场的对外地址，origin>",
  "sig": "<base64(Ed25519(节点私钥, 规范串))>"
}
```

规范串（逐字节）：

```
JSON.stringify(["wm-seat-token/1", root, host, seat_id, ts, nonce, aud])
```

签名直接签这个串，不用 Content-Digest，也不用 OriginClaim 头。

市场核对，全部成立才发令牌：

1. `aud` 是市场的对外地址，或者请求实际到达的本端地址。
2. `ts` 在 ±5 分钟内。
3. 对端登记表里 `root` 这一行是 `active`。停用、公钥变了待确认、待登记的都不行。
4. 钉住的公钥指纹等于 `host`。
5. 名册里 `host` 的根地址等于 `root`，而且这台宿主的名册里有这个 `seat_id`（以最新一次名册为准）。
6. 签名用钉住的公钥验得过。
7. 同一个签名只认一次（时间窗结束后再保留 1 分钟）。
8. 席位的授权主体没被管理员吊销。

应答：

| 状态 | 正文 | 什么时候 |
|---|---|---|
| 200 | `{ token, token_type: "Bearer", expires_at: "<ISO>", expires_in: 3600, seat: { host, seat_id } }` | 换到了 |
| 400 | `{ "error": "seat_token_bad_request" }` | 请求体不成形：字段缺、类型或字符集不对（根本不是 JSON 的，由全局解析先回 400，正文不同，也不记录） |
| 401 | `{ "error": "seat_token_refused" }` | 上面任何一条不成立。一律这一句，不说是哪条，不透露节点、席位存不存在 |
| 429 | `{ "error": "seat_token_rate_limited" }`，带 `Retry-After`（秒） | 同一来源地址 10 分钟超过 60 次（成不成都算；来源在可信反代后面取它写进来的真实地址），或同一席位 1 小时已发 12 张 |

市场不往外发任何请求（不取名片），只用钉住的公钥。

## 用令牌

- `/mcp`（JSON-RPC）和 `/api/mcp-rest/*` 都认：`Authorization: Bearer <token>`。
- 令牌只放宿主内存，宿主代成员调用。
- 1 小时到期，不续期，到期前后重新换一张。旧的还没到期时可以同时持有新旧两张。
- 每次调用市场都复核：节点仍 active、钉住的公钥没换、席位仍在名册、主体没被吊销。任一不成立，这次调用就回 401，和无效令牌一样。
- `X-Team-Seat` 请求头不认作身份或授权。带了只记进审计的 `claimed_seat` 拿来对账；审计里的席位以令牌认出来的为准。

## 授权

- 每个席位（根地址 + 节点公钥完整指纹 + seat_id）在市场有一个长期的授权主体（MCP 网关页能看到，名字是 `seat-<host>-<12 位>`）。
- 主体按（根地址，节点公钥的完整指纹，seat_id）认，名字里的宿主号只是方便人看。根地址或公钥变了就是另一个主体，从空授权开始，要重新申请；每次调用也核令牌所属主体的根地址、完整指纹和登记表此刻钉住的一致。
- 工具授权、按台批的「工具@台」授予都记在这个主体上，换多少次令牌都保留。
- 申请照旧：用换来的令牌调 `access_request`，或申请台的授予，批给的是这个席位。
- 存量不自动放宽：现有长期会话上的授权不并到席位主体上。迁移办法如下：
  1. 各席位用新令牌重新申请；
  2. 管理员和台的管理层照常批；
  3. 团队全部切过来之后，管理员吊销旧的长期会话。

## 留痕

- 每次换令牌（成功、被拒、限频、不成形）单独记一行：节点、席位、根地址、来源地址、时间、结果、拒的原因，以及 verified。verified 表示签名验过了，host 和席位是证实的。
- 换到的那次另记令牌引用 `token_ref`（令牌 sha256 前 16 位）。
- 每次 MCP 调用的审计也记 `token_ref` 和令牌认出来的席位。
- 管理员查：`GET /api/a2a/seat-token/log?host=&seat_id=&since=&until=&limit=`，再用 `token_ref` 对 `GET /api/mcp/calls`。
- 节点侧报「有成员读了私钥」时，按那段时间查这两张表。
