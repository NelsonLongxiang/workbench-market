# 升级说明

升级之前先看这里：哪些改动会让旧的配置起不来、要先改什么。按版本倒序，最新的在上面。

## 角色预设（阶段六之后）

平台的内置角色从四个补成七个：`owner` 属主、`admin` 系统管理员、`management` 管理层、`dept-lead` 部门负责人、`member` 普通员工、`guest` 访客、`ai-staff` AI 员工。

**会起不来的情况：** 配了外部角色声明文件（`WM_ROLES_FILE`），而文件里有 id 或名字和新的内置预设相同的角色——比如原来按初始集合的样子自己声明过 `dept-lead`（部门负责人），或者声明过 `management`、`ai-staff`、名字叫「系统管理员」「管理层」「普通员工」「AI 员工」的角色。内置预设不能被覆盖，这时启动会拒绝，报错里写着是哪个 id 或名字。

**升级前怎么改（二选一）：**

1. **改用内置预设：** 从声明文件里删掉这个角色。存量授予引用的是 id，id 和内置预设一样的（比如 `dept-lead`），删掉之后这些授予直接指向内置预设，不用动。注意内置预设的权限不一定和你原来声明的一样（内置的 `dept-lead` 是读、写、决定，范围由授予给）。
2. **保留自己的定义：** 在声明文件里给这个角色改一个不冲突的 id 和名字；引用旧 id 的授予要同时迁过去（撤销旧的、按新 id 重新起草放行）。

没配 `WM_ROLES_FILE` 的部署不受影响：初始集合里只剩 `dept-member`，`dept-lead` 改由内置预设提供，id 没变，存量授予照常。

**另外两处变化（不影响启动）：**

- `admin` 的显示名从「管理员」改成「系统管理员」，`member` 从「成员」改成「普通员工」；id 没变，授予不用动。
- 预设的定义在阶段六切换判定之前不生效：放不放行照旧由各处的旧守卫决定。切换之前，属主要在迁移清单里决定现有管理员各留哪条（见 [judgment-legacy-differences.md](judgment-legacy-differences.md) 的 F）。
