# 数据视图：模块化的渲染组件 + 每台一份数据

> 属主 2026-11-11 定方向：工作台不再一台一份手写页面。市场提供一组模块化的数据视图组件，台只管「往里填数据」；数据经 MCP 更新；每个工作台有自己的一份库。改台不走评审：各团队改自己团队范围内绑定的工作台，靠版本化管理兜底（原话：「大家可以各自修改自己团队范畴内绑定的工作台」「做好版本化管理方案就行」）。开源项目（Datasette、SQLPage、Evidence 等）只作参考，自己做。本篇是设计稿，还没开工。

## 一、要解决什么

现在一个自产台就是一份 HTML：布局、样式、提交逻辑、读数据的脚本都在里面。同一件事在每个台各写一遍，各错一遍。改一处规矩，要改所有台。

换成三样东西：

| 东西 | 谁提供 | 多久变一次 |
|---|---|---|
| 组件：表格、指标卡、图表、表单…… | 市场，做一次 | 很少 |
| 视图描述：这个台摆哪些组件、各读哪份数据 | 台所绑部门的人和 AI 成员，一份 JSON | 偶尔 |
| 数据 | agent 经 MCP 写，人经表单写 | 经常 |

台里不再有 HTML 和脚本。提交、幂等、留痕、无障碍、读不到时怎么说，都在组件里做一次。

这是一种新的台，下文叫**视图台**。现有的 HTML 台和它的规矩（只从仓库 main 同步）不变，两种并存。

## 二、数据：每台一份库

- 每个视图台一份自己的库，和市场主库分开。轻量部署下是数据目录里的一个 SQLite 文件，一台一个；企业部署下是 PostgreSQL 里的一个 schema，一台一个。
- 这个台的全部内容都在这份库里：数据集、列定义、视图描述、它们的历史版本、写入记录。所以备份、搬走、删除一个台，就是处理这一份。
- 库里放的是**数据集**：有名字、有列定义的表。列有名字、类型（文本、整数、小数、日期、时间、布尔）和可选的显示名。
- 一台坏了不连累别的台。

**台库和主库的关系**

| 放在主库 | 放在台库 |
|---|---|
| 台的登记：有这个台、绑在哪个部门 | 数据集和里面的行 |
| 谁改了哪个台的留痕（只有摘要） | 列定义和它的版本 |
| 授予、部门、人和席位（都不是台的东西） | 视图描述和它的版本、生效的是哪一版、快照、写入记录 |

台库不引用主库的行，主库也不引用台库的行：两边只靠台的标识对上。删台时先删主库的登记，再删台库。删台库是「等排着的读写跑完、关掉、删文件」；从开始到删完，这个台取不到，之前拿到手的连接也不能再用，删完可以重新建一个空的。

**和数据库规划（产品化文档 13）守同一条纪律**

- 台的作者和 agent 都**不写 SQL**。读用第五节的小查询描述，写用第四节的工具。
- 台库经一个专门的数据访问服务读写，接口是异步的，后面是哪种库由部署形态定；别的代码不直接打开库文件。这个服务在工作线程里跑（台按标识固定分到几个线程上），市场进程只排队、等结果（第十一节）。
- 时间由代码生成后当参数传进去，不在 SQL 里取。
- 只用两种库都认的写法；两边不一样的地方（有则改无则加、取新行编号）收进这个服务里的小函数。
- 验收和文档 13 一样：同一组请求，两种存法应答相同。PostgreSQL 一侧随主库的那一步一起落地，在那之前只有 SQLite 实现，但接口和写法从第一天就按上面的来。

**和「表结构只在 `db.ts` 里改」怎么相容**：台库的表结构也登记在 `db.ts`——固定的那几张表（列定义、版本、快照、写入记录），和数据集的表、主键索引、加列删列的语句模板，都在那里，带版本号。台库的服务在工作线程里跑，线程不能引用 `db.ts`（一引用就会在线程里再开一次主库），所以这些写法由市场进程取出来，起线程的时候递给它。执行它们的只有台库的数据访问服务，而且只在台自己的库上执行；别处不建表、不改表。库的结构比代码认识的新时拒绝打开，不去动它；版本号对得上但结构对不上的（定稿之前旧代码建的文件）同样明确拒绝。结构现在还叫第 1 版、改了没写迁移，是因为还没有任何部署建过台库；**从开放入口那一步起，任何结构改动都走迁移、版本号往上加**。

**备份和升级冒烟**

- 备份：台库在数据目录里，整目录备份自然带上。库文件的一致性由服务给：提供「给这个台取一份一致的副本」的入口，备份脚本调它，不直接拷正在写的文件。
- 升级冒烟：现有的升级冒烟（旧版本的数据目录 → 新版本启动 → 再回旧版本）要加上台库：造一个带数据集、视图版本和快照的台，升级后数据和生效版本不变；回到旧版本时旧版本不认识台库，但也不能因为它启动失败或把它删掉。

限额（防一个台把磁盘写满），超了拒收并说清超的是哪一项：每台 50 个数据集；每个数据集 60 列、5 万行、32 MB；一个台的在用数据合计 256 MB；一次写入 16 MB（整份替换可以到数据集的上限）；追加、按主键更新、删行一次 5000 行（整份替换可以到数据集的行数上限）；一格文本 1 万个字符；每个数据集留 5 份快照、列定义留最近 100 版；视图描述 200 KB、留最近 100 版；一次查询最多取 5000 行，取回的内容（各格的字符数加起来）最多 800 万。

时限：读 3 秒，写 15 秒，从轮到它开始跑算起，排队的时间不算；排着队等的读写最多 200 件，再多的当场回「正忙」。

## 三、谁能改

团队的规范见产品化文档 14：部门（人）→ AI 团队（负责人、总工、成员）→ 成员可以分配给员工。这里不另造关系，用身份线定的那一套。

**一条原则（事项、团队、数据视图共用，写在规范 14「关系由谁说了算」）：权限由已放行的授予给，关系只用来收窄，不单独放行。** 部门成员表、部门负责人、团队认领、团队负责人这些关系，都是系统管理员一个人写得出来的；要是它们直接等于「能读写这个部门的台」，系统管理员把自己加进成员表就读到了业务数据。

- **绑定。** 每个视图台可以绑到一个部门（部门表里的标识），必要时再细到这个部门下已认领的一个团队。存在主库的台登记表里，改动留痕（谁、何时、从哪到哪）。
  - 登记时就可以绑。管理层可以绑到任何部门，也可以先不绑；有某个部门拍板授予的人可以把新台登记到这个部门，而且必须绑。
  - 改绑、解绑只有管理层：绑到哪个部门决定了谁进得来，不交给部门自己。
  - 部门变了（含解绑、从没绑到绑上），这个台上已经批给 MCP 会话的授予全部收回、没定的申请全部驳回：那些是原来管这个台的人批的，要用的重新申请。只是在同一个部门里细到团队或放开，不动。
  - 台的个数上限（500）现在是全局共用的；以后可以按部门设额度。
  - 没绑的台只有管理层进得来。
- **谁进得来，两档。**
  1. 管理层：问统一判定（它现在只认范围是「全部」的授予）。读和写是同一道门，都按「能不能写」问——迁移出来的普通员工授予（范围全部、只带「看」）进不来。
  2. 部门：台绑了部门 D，这个人有一条已放行、没过期的授予，范围是 `dept:D`，盖住这个动作（`judgment.ts` 的 `scopedVerdict`）。带业务写的授予要管理层或属主放行、带拍板的只有属主放行，所以系统管理员造不出来。
- **读和写是同一批人。** 别的部门默认读不到。「全员可读」的台这一步不做，等试点看有没有这个需要。
- **拍板**（批 MCP 授予、把新台登记到部门）：要 `dept:D` 范围、带拍板的已放行授予（部门负责人这类）。部门成员不行。
- **细到团队的台**：在有 `dept:D` 授予的人里，写再收窄到这个团队的负责人、成员的主人，或者有这个部门拍板授予的人。关系在这里只会让人更少；没有授予的人当了团队负责人也进不来。
- **系统管理员、管理口令**照旧进不来：台里是业务数据。
- **席位（MCP 会话）** 还不按部门认：席位没有授予这一层，只能等「团队认领到部门」这件事本身要业务侧放行之后才可信。在那之前继续走第十节 3b 的按台申请（遗留差异 L18）；审批人从「管理层」放宽到「管理层，或这个台所绑部门上有拍板授予的人」。
- 没权限的人看不出台存不存在：对登记过、没登记过的台都是 403。台的清单只列这个人进得去的台。

**怎么判**：路由登记成「状态码不代表授权」，由这个域自己判——先问统一判定，没放行再问 `scopedVerdict`。对象范围接进统一判定（L13）之后，这两档并成一步。

## 四、写数据

新增一组 MCP 工具：

| 工具 | 做什么 |
|---|---|
| `dataset_define` | 建数据集，或改列定义。加列、改显示名随时可以；改成必填、改主键之前核对现有的行；删列会先自动留一份快照（见第七节）；改列的类型不支持（新建一列，由写入方重写数据） |
| `dataset_replace` | 整份替换：给全部行，原子切换。适合「每次算好一整份」的快照式数据 |
| `dataset_upsert` | 按主键列有则改、无则加：每行给主键列和必填列，其余给了哪些列就改哪些列。适合增量 |
| `dataset_append` | 只追加。适合流水 |
| `dataset_delete_rows` | 按主键删行。给的主键一行也没对上时什么都不做（结果里删除数是 0） |
| `dataset_query` | 用第五节的查询描述读，和页面读到的一样 |
| `dataset_list` | 列出本台的数据集、列定义、行数、上次更新时间和更新者 |
| `dataset_snapshots` | 列出一个数据集现有的快照：编号、为什么留的、多少行、谁、什么时候 |
| `dataset_snapshot` | 手工留一份快照 |
| `dataset_restore` | 把数据退回到某一份快照 |

规矩：

- 每行按列定义校验，不合格整批拒收，逐条说明哪一行哪一列。
- 写入带幂等键；同键同内容返回原结果，同键不同内容拒绝。幂等键在这个台最近 5000 次写入之内有效。
- 每次写入留一行记录：谁、哪个数据集、哪种操作、多少行、内容摘要。只记摘要，不记内容。
- 写入后发一个事件，开着的页面据此刷新。
- 出错只有几种：不合格、没有这个东西、冲突、超限、不支持、内部错误。库报了意料之外的错，对外只说「内部错误」；库的报错原文里有表名、列名和语句片段，只进日志，不往外带。
- 工具里不收 SQL，不收文件路径。
- 写入的工具要给的东西：`bench`（台的标识）、`dataset`、`rows`（删行是 `keys`）、`idempotency_key`、`note`。给后来的 agent 看的用法在技能 `skills/wm-data-views/` 里，例子由脚本用真实现逐个跑。

人在页面上通过表单组件提交，走的是同一个数据集服务，同样校验、同样留痕。

## 五、读数据：小查询描述，不写 SQL

组件读数据时给一份描述：

```json
{
  "dataset": "runs",
  "filter": [{ "col": "month", "op": "=", "value": "$month" }],
  "group": ["status"],
  "measures": [{ "as": "n", "fn": "count" }, { "as": "total", "fn": "sum", "col": "amount" }],
  "sort": [{ "col": "n", "dir": "desc" }],
  "limit": 50
}
```

- 比较符：等于、不等、大于小于、在列表内、为空、包含（区分大小写）、前缀（日期列按月筛选用）。
- 聚合：计数、求和、平均、最大、最小、去重计数。
- `$名字` 引用页面上筛选栏的当前值。
- 行数有硬上限；数据集本身的行数也有上限，所以一次查询的代价有界（现在没有单独的时限）。列名、数据集名只认已定义的，其余一律拒绝；服务端把描述翻成参数化语句，值不拼进语句。
- 筛选栏的某个值没填，引用它的那条筛选就不生效，相当于「全部」。

先不支持连表。真要跨数据集，由写入方算好再写一份。

## 六、视图描述

每台一份视图描述，存在台自己的库里，经 MCP 工具或页面上的编辑入口改：

```json
{
  "title": "示例台",
  "views": [
    { "key": "overview", "title": "总览", "blocks": [
      { "type": "filter-bar", "fields": [{ "name": "month", "kind": "month", "default": "last-month" }] },
      { "type": "stat", "title": "本月完成", "query": { "dataset": "runs", "measures": [{ "as": "v", "fn": "sum", "col": "done" }] }, "value": "v" },
      { "type": "bar", "title": "按状态", "query": { "dataset": "runs", "group": ["status"], "measures": [{ "as": "n", "fn": "count" }] }, "x": "status", "y": "n" },
      { "type": "table", "title": "明细", "query": { "dataset": "runs", "limit": 200 }, "columns": ["started_at", "status", "done", "failed"] }
    ] },
    { "key": "report", "title": "提报", "blocks": [
      { "type": "form", "dataset": "reports", "fields": ["title", "kind", "note"] }
    ] }
  ]
}
```

- 一个台有一到多个视图，对应顶栏的菜单项；每个视图是一列组件，按 12 栏网格排。
- 保存时校验：组件类型认得、数据集和列存在、查询合法。不合格就拒，不产生新版本，逐条说明哪里不对。评审没有了，这道校验就是不让坏描述上线的那一关。
- 表单的字段规则沿用现有数据契约的写法（必填、枚举、格式、条件规则），不另造一套。

工具：

| 工具 | 做什么 |
|---|---|
| `view_get` | 读当前生效的视图描述，或指定的某一版 |
| `view_put` | 保存一份新的视图描述，成为新版本并生效 |
| `view_versions` | 列出历史版本：版本号、谁、什么时候、说明、改了什么 |
| `view_diff` | 两个版本之间的差异 |
| `view_rollback` | 让某个旧版本重新生效 |

## 七、版本化管理

不走评审之后，出错靠版本兜底：每一次改动都留得下、看得清、退得回。

**视图描述**

- 每次保存产生一个新版本，版本不可改：版本号、内容、内容摘要、谁改的（人或 AI 成员）、什么时候、一句说明（必填）。
- 当前生效的是哪一版，是一个指针。回退只移指针，不产生新版本、不删任何版本；退错了再移回来。
- 保存时要带上「我是基于第几版改的」。如果这期间别人已经存了新版本，拒绝并返回最新版，由改的人合并后再存。两个人同时改，不会有一方被悄悄盖掉。
- 页面上能看任何一版的效果（预览，不生效），能看两版之间的差异。
- 保留最近若干版（数字开工时定）；被回退指向的版本不清理。

**列定义**

- 列定义的每次改动同样是一个版本，和视图描述分开计。
- 删列是破坏性的：做之前自动给这个数据集留一份快照。改列的类型不支持。

**数据**

- 数据不逐行留历史（量太大）。留的是写入记录：谁、何时、哪种操作、多少行、内容摘要。
- 整份替换保留前几代，可以一步退回上一代。
- 破坏性操作（按主键删行、删列）之前自动留快照。也可以手工留快照。快照有个数上限，旧的先清。
- 不改变数据的操作不占快照的名额：内容和这个数据集最近一份快照相同，就不再存一份，返回那一份的编号；按主键删行一行也没对上，不留快照。否则几次空操作就能把还用得上的那几份挤掉。
- 真的改了数据的破坏性操作，每次占一份。所以连着做了几次之后，更早的会被清掉：能退回的是「最近几次破坏性操作之前」，不是任意远。例外是最近一次整份替换留下的上一代：它不参与淘汰，直到下一次整份替换。
- 退回到某份快照之前，把当时的数据也留一份快照：退错了能再退回来。
- 追加和按主键更新不自动留快照；要退回只能退到最近一份快照，再由写入方重放之后的数据。这是为了不让快照撑满磁盘，写在明处。

**整台**

- 导出：一个台可以导出成一个包（视图描述和它的版本、列定义、可选带数据），再导入到同一个或另一个部署。用途是备份、搬家、从一个台起一个新台。
- 删除整个台不在「不用评审」之内：仍走现有的人审规矩。

**留痕与通知**

- 每次版本变化（保存、回退、列定义变更、退回上一代数据）都记一条：谁、哪个台、从哪版到哪版。
- 变化之后给这个台所绑部门的负责人发一条通知，事后可见。这不是审批，不拦。

## 八、组件

所有组件吃同一种数据形状：**一组行，加一份列的角色**（哪列是分类、哪列是数值、哪列是系列）。同一份数据换个组件就能换一种看法。

每个组件自带四种状态：读取中、有数据、没有数据、读不到。读不到要明说原因，不显示成「没有数据」。颜色、字号、间距只用设计 token；成功、警告、危险的颜色语义固定，台不能自己配色。只按桌面宽屏设计。图表都有等价的表格视图，读屏和键盘可用。

图表用 Apache ECharts（Apache-2.0）打底，按需引入，只封装成下面的统一组件，不把它的配置项直接暴露给视图描述。图表的主题（颜色、字号、网格线）从设计 token 生成，不单独配一套。

| 批次 | 组件 |
|---|---|

## 九、页面怎么出

视图由市场自己的前端渲染，是市场的一个页面，长在新外壳里，不沿用旧界面的组件形态，也不再是沙箱里的一份外来 HTML：

- 不需要给页面注入台令牌；看得到看不到由登录的人的权限判定，和别的页面一样。
- 提交时知道是谁提交的，不用再让页面带票据。
- 数据只当数据渲染，一律转义；视图描述里不能放 HTML 和脚本。

老的 HTML 台一个一个迁，迁完一个删一个。报告类页面不在迁移范围内。

**表格里的取值怎么说**：表格可以带一份「取值 → 说法」对照（`value_labels`：列名 → 取值 → 说法，说法可以带颜色）。有对照的取值显示说法；没给对照的显示成灰色的原文，不报错。用来把库里的状态代号换成人话。

**按值着色**：柱状图（只有一个系列时）和统计卡可以带最多两条规则（`tone_rules`：列、比较符、值 → 语气）。语气只有三种语义色——危险、提醒、正常——不能给任意色值；图下自动带一行说明（「红 = 毛利率低于 20%」）。用来把「低于阈值」这类信号直接画出来。

**取数和表单提交（已做，在台库的服务里，还没有入口）**

- 取数：给定视图和筛选栏当前的值，一次把这个视图各组件要的数据都取齐，页面和 `view_get` 共用。筛选栏只认声明过的字段，没给的用字段的默认值；选项写成「取某个数据集某一列」的，这时把不同取值查出来。各组件在同一时刻的数据上取数。
- 一个组件的查询出了错（筛选值的写法不对、取回的太多、引用的列后来被删了），只这个组件带一条错误，别的照常显示。超时是整个这一次的。整个视图取回的内容合计不超过一次查询的上限。
- 可以指定看旧的一版（预览、对比用）。
- 表单提交：往表单绑定的数据集追加一行，只收表单里列出的字段——数据集有但表单没列的列，不能经表单写。校验、幂等键、上限和追加一样。写入记录里记成「表单提交」，和直接追加分得开。表单引用的列后来被删了的，取数时说这个表单坏了，提交同样拒绝。提交时带着页面拿到的视图版本：这期间视图换了版就拒绝，由页面刷新后再提交。

## 十一、开放入口的前置

第二步做完时台库没有任何入口，运行中的市场进程不碰它。在第三步给它开任何入口（路由或 MCP 工具）之前，下面三件必须先有，写进那一步 PR 的验收条件。

**1. 台库的读写不能卡住市场进程（已做）**

问题：台库是同步访问的，一条语句跑多久，所在的线程就停多久。留在市场进程里，这期间所有人的所有请求都不动。行数上限挡得住「结果太多」，挡不住「算得久但结果少」；写入同样卡，而且更久。

做法：台库的全部读写放到一个工作线程里跑，市场进程只排队、等结果。对外接口本来就是异步的，调用方不用改。

实测（一台开发机，5 万行、每行一格 2000 个字符的文本，约 100 MB 数据；以验收实测的数字为准）：

| 操作 | 原来：市场进程停顿 | 现在：操作用时 | 现在：市场进程最长停顿 |
|---|---|---|---|
| 「包含」无命中，全表扫 | 约 80 毫秒 | 88 毫秒 | 3 毫秒 |
| 长文本列去重计数 | 约 410 毫秒 | 491 毫秒 | 3 毫秒 |
| 分组聚合（7 组，带长文本列的最大值） | 约 240 毫秒 | 292 毫秒 | 4 毫秒 |
| 整份替换 5 万行（含留上一代快照） | 约 1.2 秒 | 1687 毫秒 | 95 毫秒 |

写入时市场进程还有一小段停顿：要写的行得复制一份递给线程，这一步在市场进程里，和数据量成正比（上表整份替换的那一格就是它，约 100 MB 的行）。它由第 2 条的请求体上限封顶。

时限分两层：

- 第一层在线程里：每次读写带着时限过去，到时限自己停下、整批回滚，回「超时」。查询靠语句里的守卫当场停下（库每扫过约 256 行回到服务里看一眼时限）；写入在行与行之间看，提交之前再看一次——过了就不提交。所以这种超时是确定的：没有生效。报错的细目里带着停在哪一步（扫描数据的中途、写第几行之前、提交之前），排查时看得出慢在哪。
- 第二层在市场进程里：时限加 2 秒宽限过了还没回话，说明卡在一条中途回不到服务里的语句上（整库备份、读全表留快照）。这时强行终止线程，等它真的退出，另起一个；排在后面的读写接着做。

中止之后这个台照常可用，下一次读写正常；线程自己意外退出也一样，手上那件事马上报错，下一件事另起线程。

写在明处的限度：

- **强行终止不保证回滚。** 实测：线程被终止时，如果事务正好走到提交，这次提交会落盘。提交之前有一道时限检查，所以只有「提交本身卡了 2 秒以上」才会碰上；碰上时报错里写明「是否生效不确定」，调用方带同一个幂等键重试，或者读一次确认。
- **强行终止不是立刻的。** 线程要等手上那条语句跑完才退得出来。这段时间市场进程不受影响，但别的台的读写在排队。
- **台分到几条「道」上，一道一个线程、一次只做一件事（11-13 改，原来所有台共用一个线程）。** 台按标识固定落在一道上：同一个台的读写永远在同一个线程上、按顺序做；一个台的慢操作只让同一道上的台排队，别的道不受影响。道数默认是可用核数减一，至少 1、至多 4。实测（一台 10 核的开发机，1.5 万行、每行约 2000 字符的台做长文本去重计数，一次约 160 毫秒；另一个台连着发小查询）：只有 1 道时，小查询每次要等约 158 毫秒（中位数）；两个台分在不同道上时降到 0.2 毫秒。
- **大写入全局一次一件，做完换线程。** 体量超过 4 MB 的写入算大写入。体量按原始字节数；给的是行数组时，按各格估：文本算字符数，别的每格算 8。不按行数，因为一行最多 60 列、一格最多 1 万字符，不到两千行的宽行也能到数据集的上限。量到 4 MB 就停，不量完。先拿全局唯一的许可，拿不到就在自己那一道的队头等（只挡同一道上的台），读和小写入照常并行。每个线程的堆各攒各的，做完大写入之后还没回收的几百 MB 留在线程里；所以做完一次大写入就换掉那个线程，内存随旧线程一起放掉。实测（每份约 29 MB 的整份替换，各在独立的进程里量）：4 道同时来 4 份，内存增量 372 MB；只有 1 道时排队做完同样 4 份，增量 366 MB——和单线程时一样有界。不加这两条时，4 道各 1 份增量 1171 MB。宽行也一样：4 道同时各做一份 1999 行、每行两格各约 7900 字符的整份替换（约 30 MB），增量 420 MB；1 道 394 MB；判定只看行数时这种写入漏判，增量 1042 MB。
- **扫描守卫管不到扫完之后的分组和排序。** 守卫只在扫描行的时候回到服务里；行扫完之后库自己做的分组、排序中途停不下来。验收实测：一条读跑到 4.4 秒还返回了结果（时限 3 秒）。兜底的是第二层：时限加宽限（5 秒）一定被强行终止。要隔离得更细（按台分线程、读写分连接），等有实测需要再做。
- **查询不走主键索引了。** 守卫把整段筛选条件包了起来，库只能全表扫：实测 5 万行、每行约 2 KB 时，按主键取一行约 24 毫秒。不在市场进程里，先接受；要快再把主键上的等值条件单独拿出来。
- **线程的内存上限不设。** 验收实测：线程内存不够时，线程退出、手上这一件事失败并报「工作线程意外退出」，下一件事另起线程，市场进程不垮。早先的探针里见过另一种情况——一次性拼一段很大的文本时整个进程被带垮（分块之前的快照就是这种写法）；快照分块之后台库里已经没有这种写法。内存主要靠第 2 条的数据量上限来防。

**出站闸和工作线程（已做）**

实例设了 `WM_OUTBOUND=off`（对外断开的总开关，预发实例用）时，出站闸原来拒绝一切新开的工作线程，台库会整个不可用。现在：

- 出站闸只放行登记过的线程入口（现在只有台库的这一个）。别的文件、`eval` 的代码、字符串路径、带查询串的地址照旧拒绝并计数。入口的地址只读一次，线程按核对过的这个地址另起，不用调用方递来的对象——对象自己报的地址可以是假的。
- 放行的入口自己第一件事就是装上出站闸；起它的时候强制带着「对外断开」，调用方给的环境变量和启动参数一概不带过去。线程起来先真的往一个不可路由的地址连一次，确认在连之前就被拦下，不然不干活。
- 所以对外断开的实例上台库照常读写，线程里同样一个字节都不往外发。

启动自检的那一行留到第三步：现在运行中的服务还不起这个线程，起的时候才有东西可检。

**2. 数据量有上限（已做）**

原来的上限是分项的（数据集个数、行数、列数、一格文本的长度），乘起来仍然很大。现在加三道，都按 UTF-8 字节算（文本按字节数，数字和布尔算 8，空算 1），超了整批拒收并说清是哪一项：

| 上限 | 数值 | 怎么量 |
|---|---|---|
| 单个数据集 | 32 MB | 每次写入之后在库里量一遍（一次扫描），是准数，不是累加出来的 |
| 一个台的在用数据合计 | 256 MB | 各数据集的数加起来 |
| 一次写入 | 16 MB（整份替换可以到数据集的上限） | 给原始字节的在解析之前按字节数卡；给数组的校验时数 |

- 只拦「变大」的写入：已经超了的（上限后来调小）还能删行、换成更小的一份，不会卡死。
- 快照不算在「在用数据」里，另有个数上限：每个数据集最多 5 份，每份不超过数据集的上限。所以一个台在磁盘上最坏约是在用数据的六倍。
- 数据集的上限同时管住了内存（第 1 条里说了，线程的内存上限靠不住，只能在这里防）。快照不把数据读进服务的内存：先逐行扫一遍只算摘要，不重复才在库里直接从数据集的表复制到快照的表，一行数据一条；退回时一批 500 行地放回去。所以留快照、退回占的内存不随数据集变大，也没有「整份拼成一段文本」的长度硬顶。
- 内存实测（数据集 31 MB，做一次含留快照的整份替换）：进程内存峰值约 850 MB，分块前后差不多——大头是递进来的那批行和还没回收的垃圾，不是快照。把可用内存限死了试，多数时候 100～120 MB 就做得成，但结果不单调（验收复测 96、120、170 MB 成，140～160 MB 败），这个量法不可靠，不拿它定上限。
- **数据集上限保留 32 MB（验收裁定）。** 理由：大写入全局一次一件、做完换线程（原来是所有台共用一个线程），内存需求全局有界；线程内存不够时进程不垮；分块去掉了长度硬顶。条件两个：第三步的写入口对大请求体走原始字节（不在市场进程里解析）；部署时给市场进程至少留约 1 GB 的内存余量。
- **写入可以直接给原始字节**（JSON 文本）：在线程里解析。第三步的写入口对大的请求体就这么用——市场进程不解析、不逐个复制对象，只把字节递过去，第 1 条里「整份替换时市场进程停 95 毫秒」的那一段就没有了。请求体的大小上限按上表的「一次写入」定。
- 列定义的历史版本每个数据集留最近 100 版。

**快照的名额**（#597 验收时留到这一步的问题）：最近一次整份替换留下的那一份（上一代）不参与淘汰。整份替换之后又删了多少次行，替换前的数据都退得回去，直到下一次整份替换；总数仍是 5 份。

**3. 升级冒烟覆盖台库（已做，随 3a）**

从第三步起，运行中的服务才会打开台库。那一步的 PR 要把台库加进升级冒烟：造一个带数据集、视图版本和快照的台，升级后数据和生效版本不变；回到旧版本时，旧版本不认识台库，但不能因为它启动失败，也不能动它；再上线之后台库原样可用。

## 十三、台的数据层：一台一库，Redis 可选（2026-11-13 改口径）

属主 11-13 定：数据层优先。**每个工作台都有一份 SQLite 持久化数据；Redis 做热层，是可选项，没有就写入 SQLite。以后的工作台以数据视图为主，HTML 台可以继续存在，但不再是主要的呈现形式。** 本节在第二节「每个视图台一份库」的基础上放大范围，第二节的纪律（不写 SQL、经数据访问服务、时间当参数、两种库都认的写法、限额、时限）照旧适用。

### 1. 现状：一个台的数据散在四处

| 东西 | 现在放在哪 |
|---|---|
| 台的常量和变量 | 主库 `workbench_vars`（`kind` 分 `const` / `var`，写入带版本号做并发防护，改动进 `workbench_var_audit`） |
| 自产台提交的数据 | 主库 `app_data`，一条一个 JSON |
| 数据集、视图描述 | 台库，只有登记过的数据视图台才有；登记（`bench_views`）和市场卡片是两套，靠 `workbench_id` 对上 |
| 热数据 | Redis，只给 SOP 执行实例用（`redis.ts`） |

### 2. 改成什么样

- **一台一库，用市场卡片的 id 标识。** 市场上登记的每个工作台（自产台、SOP 台、外部地址台、视图台）都可以有一份台库，第一次写入时才建文件。数据视图不再另有一套登记：「有台库」是工作台的一个属性。
- **台库里放这个台的全部数据**：常量、变量、提交记录、数据集、视图描述，以及它们的历史版本和留痕。备份、搬走、删除一个台，就是处理这一份。企业部署下每台一个 schema，和第二节一致。
- **SQLite（或 PG）是真源；Redis 只是热层。** 把 `redis.ts` 从 SOP 专用收成一个共用的状态层服务（Cordis 服务），SOP 执行实例和台的常量、变量都经它（先共用连接，SOP 改走服务排在第 5 条的第 5 步）。没配 Redis、或者连不上时，所有读写直接落台库，结果和有 Redis 时一样，只是慢一些。轻量部署不需要 Redis。

### 3. 三种东西，读写各走各的

| | 是什么 | 写 | 读 |
|---|---|---|---|
| 常量 | 配置：阈值、对照表、负责人、台号等。改动要授权、要留痕、能回滚 | 只写台库，带版本号；写完让 Redis 里的缓存失效 | 先读 Redis，没有再读台库并回填 |
| 变量 | 运行时状态：进度、计数、当前状态、上次同步时间等，agent 和页面会频繁改 | 默认先写台库、再更新 Redis，不丢写入；标成「高频」的变量才先写 Redis、定时落盘（SOP 执行实例那套：版本号防旧快照覆盖、落盘前留「待落盘」标记） | 先读 Redis |
| 数据集 | 明细数据：记录、流水 | 直接写台库，不经 Redis | 直接查台库 |

- 写入带版本号做并发防护的规矩不变：变量和常量的写都带「我看到的版本」，对不上就拒，不静默覆盖。
- Redis 的键都带台的 id 做前缀；台删了，它的键一起清掉。这一条要有测试守住：删台之后，按这个台的前缀在 Redis 里一个键都找不到。
- 常量和变量有变化时可以经 Redis 发通知，让驾驶舱和台页面不用轮询。没有 Redis 时退回轮询。

### 4. 对外不变的

- `workbench_vars_get` / `workbench_vars_set` 等 MCP 工具、`/api/workbenches/:id/vars` 一组接口、台数据提交的接口，入参和应答都不变，只换底下的存法。验收用录制回放：迁移前后零差异。
- Redis 的地址只从环境变量或数据目录里的文件读，不进仓库（`redis.ts` 现在的做法）。

### 5. 分步和排期（统筹 11-13 定）

每一步一个 PR，按下面的先后做：

1. **Redis 收成共用的状态层服务**（#680，统筹 11-13 认定完成）：新服务和 SOP 执行实例共用 `redis.ts` 里同一条连接，SOP 的代码不动。验收包括三种情况：有 Redis、没有 Redis、中途断开；外加 SOP 执行实例原有的几组测试，以及全量录制回放零差异。
2. **台库的工作线程撑得住全部工作台。** 台库的读写早已不在市场进程里（第十一节第 1 条），但现在所有台共用一个线程、一次只做一件事，一个台的慢操作会让别的台排队，最长等到时限加宽限。全部工作台都有台库之后这就不够了：改成几个线程，同一个台的读写固定落在同一个线程上（保持一台一次一件、顺序不乱），不同的台可以同时做。线程数先实测再定。这是下一步的硬前置。
3. **台库对全部工作台开放**，以卡片 id 为标识；数据视图的登记改成「这张卡片有台库」，原来的台标识保留为别名。做法（11-13）：
   - 不改文件名、不搬数据：卡片和台的对应只记在登记表的 `workbench_id`。路由和 MCP 的 `@bench:` 写卡片 id（纯数字）或台标识都认，先换成台标识再往下走。纯数字的标识不许登记；`wb-<n>` 留给卡片 n。
   - 开台库：管理层登记时只给 `workbench_id`，标识定成 `wb-<卡片 id>`、名字用卡片的；库文件照旧第一次读写才建。SOP 台、外部地址台在第 5、6 步第一次写常量、变量或提交时才由系统代建。
   - 删卡片连带删台（统筹定的规矩）：台库里有数据时，删的人要持管理层授予（或本机命令行），并且带 `confirm_bench_data: true`；只有管理口令、系统管理员身份、MCP 会话的一律 409，提示找管理层；409 只给规模（几个数据集、多少行、多大、几版视图），不给名字和数值。删前备份进 `bench-stores/.deleted/`，留 30 天，留痕写明谁删的、备份、到期。**恢复没有入口：需要时由运维从备份手工恢复。**
   - 顺序：主库一个事务（台的登记、授予、没定的申请、卡片、常量变量、驾驶舱面板）→ 删库文件、清 Redis 键。后两步失败不回滚，由清扫（每天一次）补：没登记的库文件先备份再删、过期备份删掉、Redis 里卡片已不在的键清掉。
   - 写入的行里有对象或数组的格，在递给线程之前就拒（说明第几行哪一列）。
4. **视图台自己的页面**（开放入口，见第 6 条）。技能和入门指引在这一步之后再改成「以数据视图为主」：入口没开之前，台照着做也做不出来。
5. **常量、变量迁进台库**，接上状态层；**SOP 执行实例的热态也在这一步改为经由状态层服务**（第 1 步只共用了连接）。迁移可以重复跑；主库的旧表保留到确认无误后再删。
6. **提交记录（`app_data`）迁进台库。**

几条规矩：

- **换 PostgreSQL（产品化文档 13）排在第 6 步之后**，换库时搬的就是最终的形状，只搬一次。从现在起，第 3～6 步的代码按两种库都认的写法写：时间当参数传，不新增 SQLite 特有的写法，SQL 只写在领域服务里。
- **不进当前这次上线。** 这条线的 PR 都排在当前上线之后；碰服务端入口文件、常量变量路由的，照合并热点的排队规矩合。
- **第 5、6 步要在生产库的副本上演练。** 这是生产上的动作，由属主和开发席安排，实现方不自己发单。

### 6. 呈现形式：以数据视图为主

- 新的工作台默认做成视图台：数据进台库，页面由视图描述加市场的组件出。HTML 台照旧可以登记、同步，但不再是推荐的做法；技能和入门指引按这个口径改。
- 这样一来，视图台需要**自己的页面**，不能只经驾驶舱呈现：员工从市场目录直接打开一个台，看到的就是它的数据视图，也能在上面填表。这就是第十一节的「开放入口」，从「暂缓」改成第 5 条排期里的第 4 步。
- 驾驶舱照旧可以挂任意台的视图，两处读的是同一份台库。
- HTML 台也可以有台库（常量、变量、提交都在里面），只是页面自己画。HTML 台能不能读台库的数据集，等视图台的页面做出来后再定，先不开。

### 7. 已认的默认

- 变量默认「不丢写入」（先写台库）。只有在变量上**显式标成「高频」**的，才允许丢最近一个落盘周期的写入；不标就不丢。
- 台库按需建：SOP 台、外部地址台在用到常量、变量或提交之前不建文件。


### 8. 以后

- **只有管理层的人删带数据的台**（统筹 11-13 定，现在不做）：删卡片要先过写入总门，所以现在要删带数据的台，得同时是管理员和管理层，或者用本机命令行。删台少见，先这样严一点。以后真要让只有管理层授予的人也能删，走规范 14 的提议确认模式：管理员发起删除，生成一条「等你拍板」，由管理层经 `answer_via` 确认之后才执行。不给管理层另开一个绕过写入总门的删除入口。
