# 数据视图：模块化的渲染组件 + 每台一份数据

> 属主 2026-11-11 定方向：工作台不再一台一份手写页面。市场提供一组模块化的数据视图组件，台只管「往里填数据」；数据经 MCP 更新；每个工作台有自己的一份库。本篇是设计稿，还没开工。开源项目（Datasette、SQLPage、Evidence 等）只作参考，自己做。

## 一、要解决什么

现在一个自产台就是一份 HTML：布局、样式、提交逻辑、读数据的脚本都在里面。同一件事在每个台各写一遍，各错一遍。改一处规矩，要改所有台。

换成三样东西：

| 东西 | 谁提供 | 多久变一次 |
|---|---|---|
| 组件：表格、指标卡、图表、表单…… | 市场，做一次 | 很少 |
| 视图描述：这个台摆哪些组件、各读哪份数据 | 台的作者，一份 JSON | 偶尔 |
| 数据 | agent 经 MCP 写，人经表单写 | 经常 |

台里不再有 HTML 和脚本。提交、幂等、留痕、无障碍、读不到时怎么说，都在组件里做一次。

## 二、数据：每台一份库

- 每个工作台一份自己的库，和市场主库分开。轻量部署下是数据目录里的一个 SQLite 文件，一台一个。
- 库里放的是**数据集**：有名字、有列定义的表。列有名字、类型（文本、整数、小数、日期、时间、布尔）和可选的显示名。
- 一台坏了不连累别的台；按台备份、按台删除就是处理一个文件。

**和「后面换 PostgreSQL」怎么相容**（见产品化文档 13）：台的作者和 agent 都**不写 SQL**。读用下面第四节的小查询描述，写用第三节的工具。SQLite 只是轻量部署下数据集的存法；企业部署下同一套接口后面换成 PostgreSQL（每台一个 schema）。验收办法和文档 13 一样：同一组请求，两种存法应答相同。

**和「表结构只在 `db.ts` 里改」怎么相容**：主库照旧。台的库是另一样东西，由一个专门的数据集服务管，只有它能建表改表，而且只碰台的库。体检里给它单立一项计数。

限额（防一个台把磁盘写满）：每台数据集个数、每个数据集的行数和列数、单次写入的行数、库文件大小，都有上限，超了拒收并说清超的是哪一项。具体数字开工时定。

## 三、写数据：经 MCP

新增一组工具，授权可以限定到单个台（沿用 `工具@台` 的写法）：

| 工具 | 做什么 |
|---|---|
| `dataset_define` | 建数据集或改列定义。改列只许加列、改显示名；删列和改类型要管理员 |
| `dataset_replace` | 整份替换：给全部行，原子切换。适合「每次算好一整份」的快照 |
| `dataset_upsert` | 按主键列有则改、无则加。适合增量 |
| `dataset_append` | 只追加。适合流水 |
| `dataset_delete_rows` | 按主键删行 |
| `dataset_query` | 用第四节的查询描述读，和页面读到的一样 |
| `dataset_list` | 列出本台的数据集、列定义、行数、上次更新时间和更新者 |

规矩：

- 每行按列定义校验，不合格整批拒收，逐条说明哪一行哪一列。
- 写入带幂等键；同键同内容返回原结果，同键不同内容拒绝。
- 每次写入留一行记录：谁、哪个数据集、哪种操作、多少行、内容摘要。只记摘要，不记内容。
- 写入后发一个事件，开着的页面据此刷新。
- 工具里不收 SQL，不收文件路径。

人在页面上通过表单组件提交，走的是同一个数据集服务，同样校验、同样留痕。

## 四、读数据：小查询描述，不写 SQL

组件读数据时给一份描述：

```json
{
  "dataset": "runs",
  "filter": [{ "col": "month", "op": "=", "value": "$month" }],
  "group": ["status"],
  "measures": [{ "as": "n", "fn": "count" }, { "as": "total", "fn": "sum", "col": "amount" }],
  "sort": [{ "col": "n", "dir": "desc" }],
  "limit": 50
}
```

- 比较符：等于、不等、大于小于、在列表内、为空、包含。
- 聚合：计数、求和、平均、最大、最小、去重计数。
- `$名字` 引用页面上筛选栏的当前值。
- 行数有硬上限，查询有时限。列名、数据集名只认已定义的，其余一律拒绝；服务端把描述翻成参数化语句，值不拼进语句。

先不支持连表。真要跨数据集，由写入方算好再写一份。

## 五、视图描述

每台一份 `views.json`，放在台的源目录里，和现在一样从仓库 main 同步（来源收敛的规矩不变）：

```json
{
  "version": 1,
  "title": "示例台",
  "views": [
    { "key": "overview", "title": "总览", "blocks": [
      { "type": "filter-bar", "fields": [{ "name": "month", "kind": "month", "default": "last-month" }] },
      { "type": "stat", "title": "本月完成", "query": { "dataset": "runs", "measures": [{ "as": "v", "fn": "sum", "col": "done" }] }, "value": "v" },
      { "type": "bar", "title": "按状态", "query": { "dataset": "runs", "group": ["status"], "measures": [{ "as": "n", "fn": "count" }] }, "x": "status", "y": "n" },
      { "type": "table", "title": "明细", "query": { "dataset": "runs", "limit": 200 }, "columns": ["started_at", "status", "done", "failed"] }
    ] },
    { "key": "report", "title": "提报", "blocks": [
      { "type": "form", "dataset": "reports", "fields": ["title", "kind", "note"] }
    ] }
  ]
}
```

- 一个台有一到多个视图，对应顶栏的菜单项；每个视图是一列组件，按 12 栏网格排。
- 同步时校验：组件类型认得、数据集和列存在、查询合法。不合格就拒，和现在的数据契约一样在合并前拦下。
- 表单的字段规则沿用 `data-contract.json` 的写法（必填、枚举、格式、条件规则），不另造一套。

## 六、组件

所有组件吃同一种数据形状：**一组行，加一份列的角色**（哪列是分类、哪列是数值、哪列是系列）。同一份数据换个组件就能换一种看法。

每个组件自带四种状态：读取中、有数据、没有数据、读不到。读不到要明说原因，不显示成「没有数据」。颜色、字号、间距只用设计 token；成功、警告、危险的颜色语义固定，台不能自己配色。只按桌面宽屏设计。图表都有等价的表格视图，读屏和键盘可用。

| 批次 | 组件 |
|---|---|
| 第一批 | 指标卡、数据表格、柱状图（含分组、堆叠、横向）、折线图（含面积）、饼图与环形图、进度条、筛选栏、表单 |
| 第二批 | 漏斗图、金字塔图、瀑布图、日历热力图、排行榜、柱线组合图、状态徽章、详情卡、文件清单、时间线 |
| 按需 | 桑基图、甘特图、透视表、热力矩阵、散点与气泡图、雷达图、直方图、箱线图、矩形树图、仪表盘、子弹图、看板、树 |

## 七、页面怎么出

视图由市场自己的前端渲染，是市场的一个页面，不再是沙箱里的一份外来 HTML：

- 不需要给页面注入台令牌；看得到看不到由登录的人的权限判定，和别的页面一样。
- 提交时知道是谁提交的，不用再让页面带票据。
- 数据只当数据渲染，一律转义；视图描述里不能放 HTML 和脚本。

现有的 HTML 台不动，两种形态并存：新台用视图；老台一个一个迁，迁完一个删一个。报告类页面不在迁移范围内。

## 八、分步

1. **本篇定稿。**
2. **数据集服务和 MCP 工具。** 服务、限额、留痕、事件；对抗组（越权写别的台、超限、坏行、注入形态的列名和值）；启动自检加一行。
3. **第一批组件和视图页。** 先用合成数据把八个组件做出来，在浏览器里逐个看过。
4. **试点一个台。** 选一个现有的台照新形态重做，新旧并排对一遍数。
5. **第二批组件**，以及老台逐个迁移。

每一步单独成 PR；第 2 步动鉴权和写入面，按安全面的规矩走。

## 九、等属主定的

1. **图表库。** 自己画图工作量大，建议用一个成熟的开源图表库打底，只封装成上面的统一组件。候选：Apache ECharts（Apache-2.0，图种最全，上面清单都覆盖）；或 antd 同一家的图表库（和现有界面库同源）。我倾向 ECharts，按需引入。这是新的运行时依赖，要先登记。
2. **视图描述放哪。** 本篇写的是放仓库、走同步（改视图要过评审）。另一种是也允许经 MCP 改（agent 能自己调页面，快，但少一道评审）。我倾向先只走仓库。
3. **台的库在企业部署下的形态。** 本篇写的是每台一个 schema。如果希望企业部署也保持每台一个 SQLite 文件，接口不变，只是少一处要迁。
4. **试点选哪个台。**
