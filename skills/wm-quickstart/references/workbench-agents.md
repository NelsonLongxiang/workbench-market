# 台的读写约定：工作台常量 `AGENTS.md`

每个台在自己的工作台空间里放一个常量，键名固定为 `AGENTS.md`，值是一段 markdown，写清本台的数据放在哪、谁可以写什么、怎么写。作用和代码仓库里的 AGENTS.md 一样：人和 agent 读写这个台之前先读它。

## 读

```
GET /api/workbenches/${WM_WORKBENCH_ID}/vars/AGENTS.md      （带本台 X-App-Token）
MCP：workbench_vars_get { key: "AGENTS.md" }
```

- 读写一个台的变量、数据面、文件面之前，先读本台的 `AGENTS.md`。它和你手里的旧认识冲突时，以它为准。
- 返回 404 表示本台还没写约定。这时按 [data-layer.md](data-layer.md) 的通用规范做，不要自己猜键名或记录格式，先问台的属主。

## 内容

按下面的节写，没有的节写「无」，不要省略。值不超过 64KB。

1. **本台**：做什么用，属主是谁（人或席位），页面入口。
2. **工作台变量与常量**：逐个键写清 kind、内容、谁写、多久更新。数据集指针（比如 `xxx.datasets`）写出每一项是什么。
3. **数据面**：每种记录类型（比如按 `form` 或 `record_type` 区分）写清用途、必填字段、谁写，以及是只追加还是可以改；本台有数据契约（`data-contract.json`）的，说明契约会拒什么。
4. **文件面**：哪些文件会放在这里，命名规则，记录里怎么引用（比如 `file:<id>` 或 `/api/apps/<slug>/files/<id>`）。
5. **写的规矩**：署名（`created_by` 或提交人字段），交付物要带哪些字段页面才认得，不允许做的事。
6. **改这份约定**：源文件放在哪，谁可以改，改完怎么生效。

只写本台的约定。平台通用的规则（数据层规范、发布纪律）写一句链接就行，不要整段抄过来，免得两边不一致。

## 写入与修订

- 第一次写：用本台令牌，或 MCP 带 `kind: "const"` 创建。
- 常量写入后不能改、不能删。要修订，只能由管理员或本机命令行带 `override` 和修订原因（`reason`），修订会留审计。MCP 不能修订常量。
- 约定会随台演进，所以源文件要放在台的代码仓库里，和台页面一起评审；评审通过后由管理员把新内容修订进常量。不要直接在生产上手写。
